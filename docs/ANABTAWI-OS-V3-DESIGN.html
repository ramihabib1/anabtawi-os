00What changed in v3

You set the constraint plainly: no lock-in to one vendor's platform, no API-only billing as the foundation, use the subscriptions you already pay for on a machine you control, open-source where possible, and scalable. Five more research surveys, about 32,000 words, went into this revision. The architecture is now built on one principle:

No vendor owns the runtime. A department is a folder of text that any agent CLI can run. The model behind it is a config line. The orchestrator is open source and replaceable. Tools are MCP. Knowledge is markdown in git. If Anthropic, OpenAI, or xAI changes a rule tomorrow, you edit one line, not the company.

The findings that shaped it, each verified against a primary source unless noted:

  • Subscriptions can only be spent through each vendor's own CLI. Anthropic's compliance page permits signing in to the unmodified Claude Code binary with your own subscription, including when a platform hosts it, and provides a one-year token for scripts. The Agent SDK and any third-party harness must use API keys. OpenCode, Goose, Crush, and the other open harnesses are all API-key only. So the design runs Claude Code and Codex as subprocesses of an open-source control plane.
  • Grok Build is excluded from anything that touches credentials. Six outlets reported in July 2026 that it uploaded full repositories, including unredacted secret files, to xAI storage, and that the upload path remains in the open-sourced code behind a remote flag. It may run one credential-free research department in isolation, or nothing.
  • Gemini CLI for individuals was shut down on June 18, 2026 and Google enforced its ban on subscription use with account suspensions. It is off the table.
  • Paperclip is the only open-source orchestrator built as a company: org chart, heartbeats, budgets, approvals, immutable audit log, multi-organisation isolation, and adapters that run Claude Code and Codex on your logins. It is six months old with a single maintainer. It is chosen with a written exit path, because the departments do not depend on it.
  • Authentication is the real maintenance cost, not hosting. Neither Claude Code nor Codex has a clean headless login, so periodic re-authentication is unavoidable. A machine you can walk up to turns that into five minutes. The honest contract is one to three hours a month.
  • OpenClaw is out. A localhost-exploitable remote code execution flaw, a quarter million exposed instances, and 800 malicious skills in its marketplace this year. Its markdown-memory convention is borrowed; the product is not.

01Why v1 failed, and the rule for v3

Version 1 was a software project you had to feed: custom sync, custom memory, custom bot, a VPS to babysit. It produced infrastructure, not decisions, and you stopped using it. The loop that worked was you, a Claude session, and live account data through DataDoe's MCP.

The rule: every component is a hosted tool we buy, an open-source tool that runs from one Docker Compose file, or a plain text file in a git repo. Custom code is limited to three small scripts, listed in section 11, and nothing else.

Three ideas survive from v1: humans approve money, business rules live in one constitution file, and knowledge compounds from observations into playbooks.

03Authority tiers and the trust ratchet

Tier 0
Observe and report
Read data, write findings to the brief and the wiki. No account writes. Every department starts here for its first week.
Tier 1
Act inside guardrails, logged
Reversible, bounded actions without asking. Today that is Advertising only, through Amazon's own Ads MCP: bids within ±15%, negatives past a statistical threshold, budgets within +25% per action up to a daily cap, one change per target per 24 hours. Money never moves on Tier 1; a bid change spends ad budget you already set.
Tier 2
Propose, Rami approves
Price changes, purchase orders, new campaigns, listing text or images, FBA shipment creation, coupons and deals, buyer messages, Vine enrolment, reimbursement claims. Proposals arrive in the morning brief as a numbered list. You answer in one message in your session, and the session executes.
Tier 3
Rami only
New marketplaces, brand or supplier contracts, payment terms, spend above the monthly PO ceiling, appeals and plans of action to Amazon, IP complaint responses, anything legal or regulatory. Agents prepare the packet; the decision and the submission are yours.

The ratchet. An action class moves from Tier 2 to Tier 1 when 30 days have passed, you approved at least 20 proposals of that class, and you rejected fewer than 5%. The Chief of Staff proposes, you confirm. Any class demotes by editing one line in the constitution. Amazon's own floor is human authorization for price moves over 20% in 24 hours and bulk edits of 500 or more ASINs; every tier here is stricter than that, so the ratchet can never drift below the policy.

04How departments communicate

You were right that v2 had no inter-department communication, and that this would cap quality. Supply Chain cannot size a purchase order without Finance's cash forecast and Advertising's launch plan. Pricing cannot cut a price while Advertising is buying rank on that SKU. The fix is not agents chatting freely. Free-form conversation between agents is expensive, unauditable, and drifts. The design uses three channels with increasing cost, and Anthropic's own guidance for multi-agent systems is the same: share state for independent work, hand off typed requests, and coordinate only when the decision genuinely crosses boundaries.

Shared statealways on · the blackboard

Every department writes to a fixed file others must read before proposing anything. Refreshed each run.

  • state/inventory.md cover per SKU, inbound ETAs, capacity
  • state/cash.md position, 8-week forecast, PO ceiling left
  • state/ads.md launches in ramp, pacing, ACOS by SKU
  • state/prices.md price, floor, competitor positions, tests
  • state/catalog.md changes in flight, suppressed listings
  • state/health.md account status, open violations
  • state/calendar.md launches, deals, blackout dates
Typed requestsasynchronous · the inbox

One file per request in requests/<dept>/inbox/ with a fixed schema and an enumerated type. Each department answers its inbox before its own work. Unanswered past the needed-by date escalates to the Chief of Staff.

  • need-cash-check Supply Chain → Finance
  • need-forecast Advertising → Supply Chain
  • need-margin-floor Pricing → Finance
  • blackout Advertising → Pricing: hold price on SKU until date
  • stockout-risk Supply Chain → Advertising: throttle spend
  • competitor-oos Pricing → Advertising: raise bids
  • quality-issue Customer → Supply Chain, Catalog
Meetingssynchronous · coordinated

One headless Chief of Staff run that spawns a subagent per department. The coordinator poses the decision, collects positions, resolves against the constitution, writes minutes to meetings/, and queues anything Tier 2 or above for you.

  • Monday business review, all departments
  • Monthly sales and operations planning: demand → supply → cash → launch calendar. POs are sized here.
  • Launch review for every new SKU or market
  • Event meetings: hero SKU stockout imminent, competitor out of stock, account health drop

Where each channel runs

Shared state and the inbox are files in the company repo, which every department's CLI starts in and commits to. Typed requests are also mirrored as tickets in the control plane so they carry deadlines, assignment, and escalation. Meetings are a single headless Claude Code run by the Chief of Staff that spawns one subagent per department; each subagent reads its department's state, inbox, and memory, argues its position, and reports back; the Chief of Staff resolves against the constitution, writes minutes, and queues anything Tier 2 or above. Claude Code supports subagents in headless mode on a subscription, so a meeting costs one department run. Your Monday session opens the minutes and the pack, and you decide.

What you see

  • The morning brief lists unresolved cross-department conflicts as decisions, with each department's position in two lines.
  • Every meeting produces one page of minutes. You can join any meeting live from your session or read the minutes later.
  • The Chief of Staff rejects proposals that ignore relevant state, for example a price cut during a ranking push, and says why in the brief.

05Architecture: six layers, none owned by a vendor

1. Departmentsportable text
A department is a folder: AGENTS.md for its charter and rules, read natively by Claude Code, Codex, Cursor, and most 2026 agents (Claude Code imports it from a one-line CLAUDE.md); skills/ in the open Agent Skills format, adopted by some 40 tools, for procedures and validated playbooks; .mcp.json for the exact tool servers it may use; memory/ for what it has learned. The same folder runs unchanged on any of the CLIs below.
2. Brainsfirst-party CLIs on your subscriptions
Claude Code with a one-year setup token on Claude Max. Codex CLI signed in to ChatGPT with device auth. Both run headless with JSON output and local MCP servers. A self-hosted LiteLLM router provides the third path for any department you want on an API key or a local open-weight model, with per-department budgets and fallbacks in one YAML file. Allocation and the rules are in section 06.
3. Control planePaperclip, open source
Paperclip holds the org chart, fires each department's heartbeat on schedule, enforces a hard budget per agent, records every tool call in an immutable audit log, and routes requests as tickets. Its Claude Code and Codex adapters spawn the real CLI binaries with your logins. It runs from one Docker Compose file on the box, bound to the private network only. Section 07 compares the alternatives and states the exit path.
4. Handsthe only writes to Amazon
Amazon's official Ads MCP for advertising, called directly by the Advertising department within Tier 1 guardrails. For prices, listings, and FBA shipments, a private SP-API app you own, executed by a small hands runner that only acts on approval files flipped to approved by the Telegram bot. Approvals are durable files in the repo, so they survive any restart or a change of orchestrator. Section 08.
5. The boxa machine you can walk up to
A Mac mini at home or the office, sleep disabled, auto-login, four to six watts idle. launchd runs the control plane and the hands runner as user agents so the CLIs find their credentials. Docker for the control plane and MCP servers. Tailscale so nothing is ever on the public internet. 1Password service accounts or self-hosted Infisical inject secrets at run time, no plaintext env file. healthchecks.io as an off-box dead-man switch. Git to GitHub plus restic to Backblaze for everything else. Section 09.
6. Knowledge and interfacemarkdown, a static wiki, Telegram
The company repo is the memory: constitution, charters, state files, dossiers, playbooks, ledgers as JSONL and CSV queried with DuckDB, briefs, minutes. MkDocs builds a private wiki on every push, hosted on Cloudflare Pages behind Cloudflare Access so your father and brother read it with an email link. The morning brief and every approval reach your phone through one Telegram bot with inline buttons. Section 10.

The allocation

Departments are spread across two subscription pools so that no single weekly cap stops the company, the most sensitive departments run on the most mature approval tooling, and every department has an API fallback through the router.

DepartmentBrainWhy
Chief of StaffClaude Code, MaxRuns meetings with subagents and compiles the brief; needs the strongest reasoning and the subagent feature.
Finance, Supply Chain, PricingClaude Code, MaxThey produce the money proposals. Claude Code's MCP and permission tooling is the most mature.
AdvertisingCodex, ChatGPTActs through the official Ads MCP within guardrails; spreads the daily Tier 1 workload off the Claude pool.
Catalog, Customer, Account HealthCodex, ChatGPTAnalysis-heavy, long reads, few writes. Suits the looser Pro window.

Capacity, honestly

  • A department run with 20 to 40 tool calls plausibly consumes 150k to 500k tokens. Eight runs a day is 1 to 4 million tokens, 8 to 28 million a week. Neither vendor publishes token ceilings for subscriptions.
  • Claude Max 20x is the right fit for four departments plus your own daily use. It is very likely not enough for eight, which is why half the company runs on ChatGPT.
  • If the whole workload were API-billed on Sonnet 5, it would cost roughly $90 to $300 a month. That number is the ceiling of the fallback, not the plan.
  • Week one measures real consumption from the CLIs' own status output and Paperclip's cost tracking, and the allocation is adjusted on real numbers.

The gray area, stated once. Anthropic's limits "assume ordinary, individual usage." Four unattended department runs a day on one Max account is a heavier pattern than most subscribers. The design keeps it inside the letter of the policy by running only the unmodified binary with your own login, keeps the load moderate by splitting providers, and keeps the API fallback funded so an enforcement action would cost money, not the company. If you want certainty, one email to Anthropic sales describing the use is the cheapest insurance available.

Recommendation: Paperclip, with an exit path written before day one

Paperclip is the only candidate whose model of the world is the model in this document: agents as employees with roles, heartbeats, budgets, and approvals, and a company that can hold several organisations. Its adapters do the one thing you asked for that no open harness does, which is run Claude Code and Codex on your logins. The MCP tool gateway gives governed tool access per agent, which is the credential isolation the shared-box threat model needs. The risks are its age and its bus factor. They are mitigated by the design rather than argued away: nothing that matters lives inside Paperclip. Departments are folders in git, knowledge is markdown, approvals are files, the hands runner is separate, and Paperclip's own Postgres holds only schedules, budgets, and its audit copy of the ledger.

Exit criteria. If Paperclip goes two months without a release, ships a security issue that is not patched within a week, or the adapters break on a CLI update and stay broken for two weeks, the company moves to n8n, whose Telegram approval node and MCP node already cover the mechanics, or to a launchd runner of about 150 lines that fires each department's CLI in sequence. Either move is a weekend, and the departments do not know it happened.

Why not n8n first. It is the more mature product and it would work. It has no idea what a department is, no per-agent budget, no org chart, and no multi-organisation isolation, so the company model would be rebuilt by hand in workflow JSON. That is the software project you do not want. It is the right fallback precisely because it is boring.

08The write path and Amazon's Agent Policy

Amazon added Section 19, the Agent Policy, to the Business Solutions Agreement effective March 4, 2026, with a grace period that ended in early June. As reported across seller law firms and analysts, it requires:

  • Agents identify as automated in every request, with Agent/[name] in the User-Agent header, and never mimic humans or bypass CAPTCHAs.
  • All automated actions flow through registered SP-API applications. Browser automation, scraping, and undocumented endpoints are prohibited.
  • Every automated action is logged with timestamp, type, inputs, and outputs, retained at least 12 months.
  • A real human authorizes bulk edits of 500 or more ASINs, price changes above 20% in 24 hours, and account configuration changes.
  • No pricing decisions driven by scraped competitor data. Agents cease access when Amazon asks.

The policy text itself was not fetchable from this environment; the obligations above are consistent across six independent summaries and should be confirmed against the live agreement before go-live.

Why not DataDoe for unattended writes

DataDoe's writes are genuinely well designed: off by default per action type, dry run, audit history, and the company reports SOC 2 Type II and a cleared Amazon Data Protection Policy assessment. It is the most credible hosted write path found. Three reasons it is the read layer and not the unattended write path:

  • It cannot create FBA inbound shipments, submit feeds, or file reimbursement cases, so a second write path would be needed anyway.
  • Writes would run under DataDoe's SP-API app identity, not yours. The Agent Policy's identification and logging obligations are cleaner when the app is yours.
  • The audit trail would live in DataDoe rather than in your ledger. The ledger in git is the 12-month log the policy asks for and the one thing every department reads.

DataDoe writes are still useful in your interactive session for a one-off price or listing edit while the private app is being registered in week one. Enable only the listing action type, keep dry run on, and record the action in the ledger by hand.

The Telegram bot, long polling, allowlisted to your chat ID, posts it with Approve and Reject buttons and a second confirm tap for anything that moves money. A tap flips the file's status and commits. The hands runner executes only files in the approved folder. This survives any restart and any change of orchestrator, and git is the audit trail.
  • Brief. Short chunked Telegram messages within the 4,096-character limit, linking to the full brief page on the wiki.
  • Wiki. MkDocs with the Material theme, built by a GitHub Action on every push, hosted on Cloudflare Pages on a custom domain behind Cloudflare Access with an email allow-list. Free for up to 50 users, no server, no VPN for your father and brother.

  • Compounding. Weekly synthesis of observations into patterns with provenance links; automatic confidence decay for anything not reinforced in 90 days; the monthly review tries to falsify each playbook against the last 30 days of outcomes rather than only confirm it; a validation verdict is stored as its own record.
  • Search. ripgrep until the repo outgrows it, then a local index such as memsearch or sqlite-vec. Never a hosted memory vendor.
  • Second brand. One repo per brand, shared skills as a pinned git submodule, one Paperclip organisation per brand, separate credentials and a separate Telegram chat per brand.

11The only custom code

Three scripts, together under 500 lines, each replaceable in an afternoon. Everything else is bought, open source, or text.

  1. Hands runner, Python, about 200 lines. Watches approvals/approved/, executes each file's action through the private SP-API app with the Agent/AnabtawiOS header, writes the result to the ledger, moves the file. Secrets injected by the vault at run time.
  2. Telegram bot, Python, about 120 lines. Long polling, one allowlisted chat ID, posts pending approvals with buttons, second tap for money, flips file status and commits, posts the brief in chunks, relays failure alerts.
  3. Ops check, shell, about 60 lines. Weekly: diffs installed CLI, image, and MCP server versions against upstream, checks disk and healthchecks status, posts a report. Never applies anything.

Anything beyond this is a sign the design is drifting back to v1, and should be questioned in the Monday review.
