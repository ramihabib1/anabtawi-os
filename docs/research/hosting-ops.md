## 1. Where the Box Lives

### 1.0 The auth wrinkle that dominates this whole decision

Before cost/maintenance tradeoffs matter, there is a hard technical constraint: **subscription-authenticated coding-agent CLIs do not have a clean headless login story in Sept 2026.**

- **Claude Code (Claude Max subscription via OAuth):** As of the open GitHub issue #22992 (filed Feb 4, 2026, still open), Claude Code has **no RFC 8628 device-code flow** for Pro/Max subscribers. The standard `/login` OAuth flow requires a browser redirect back to the *same machine* running the CLI, which fails over SSH/headless. The only working pattern is `claude setup-token`: authenticate once via a browser (can be a separate machine that then has its token file copied/generated on the headless box), which yields a long-lived OAuth token usable via `CLAUDE_CODE_OAUTH_TOKEN`. A separate open issue (#42965) tracks "OAuth login broken for remote/headless setups." REPORTED via GitHub issues (primary-ish, but these are user bug reports, not Anthropic docs) — [Issue #22992](https://github.com/anthropics/claude-code/issues/22992), [Issue #42965](https://github.com/anthropics/claude-code/issues/42965), background via [autonomee.ai VPS auth guide](https://autonomee.ai/blog/claude-code-server-vps-authentication-guide/) and [amux.io headless guide](https://amux.io/guides/claude-code-headless/).
- **Codex CLI (ChatGPT Plus login):** Similarly no browser-free path unless a **workspace admin enables Device Code Authentication**; even then, some report it only works for workspace/team accounts, not always personal ChatGPT Plus. Fallback workaround is SSH port-forwarding `localhost:1455` (the port Codex's local OAuth callback server binds) back to a machine with a browser, or authenticating on a machine with a browser and copying `auth.json` to the headless host. REPORTED — [Issue #9253](https://github.com/openai/codex/issues/9253), [Issue #3820](https://github.com/openai/codex/issues/3820), [ProxyLLM device-auth walkthrough](https://proxyllm.ai/blog/codex-login-without-browser).
- **Practical implication:** whichever box you choose (Mac mini, mini PC, VPS), the *first login* of Claude Code/Codex CLI needs a one-time browser session (either physically at the machine, or a bootstrap token generated elsewhere and copied over), and **both token types can require periodic re-auth** — community reports (not vendor-documented SLAs) describe OAuth tokens for Claude Code as long-lived (weeks-months) but not permanent, meaning a solo operator should expect an occasional manual re-login. This favors a machine you can walk up to (local Mac mini/mini PC) over a VPS you'd need to tunnel a browser into every few months. UNKNOWN exact token lifetime (not documented by Anthropic/OpenAI in public docs found).

## 2. Running Agents on a Schedule Reliably

### 2.1 systemd timers vs cron (Linux box or VPS)

- **Logging:** systemd timers pipe stdout/stderr to `journald` automatically; cron requires you to manually redirect (`>> log 2>&1`) and rotate logs yourself. VERIFIED-by-consensus across multiple sources — [DCHost.com](https://www.dchost.com/blog/en/cron-vs-systemd-timers-the-friendly-way-to-ship-reliable-schedules-and-real-healthchecks/), [cr0x.net](https://cr0x.net/en/debian-systemd-timers-vs-cron/).
- **Missed runs:** cron silently skips a run if the machine was off/asleep at trigger time; a systemd timer unit with `Persistent=true` will catch up the missed run on next boot. REPORTED — [cronbuilder.dev](https://cronbuilder.dev/blog/cron-vs-systemd-timers.html).
- **Timeouts:** systemd gives a native `TimeoutStartSec=` to hard-kill a runaway agent process; cron has no native timeout (you'd wrap the command in `timeout 600 ...` yourself).
- **Retries:** systemd's `Restart=on-failure` + `StartLimitBurst`/`StartLimitIntervalSec` gives bounded auto-retry; cron needs retry logic written into the script (this is exactly the pattern the existing CLAUDE.md cron design in this project uses — separate "retry" cron lines 30 min after each agent).
- **Dependency ordering:** systemd's `After=network-online.target` blocks a unit until network is actually up; cron jobs that fire at boot can race the network and fail — a known solo-VPS gotcha.
- **2026 guidance consensus:** "new services on modern Linux default to systemd timers; cron remains fine for simple/portable personal scripts" — REPORTED — [crongen.com](https://www.crongen.com/blog/cron-vs-systemd-timers-2026), [linuxblog.io](https://linuxblog.io/systemd-timers-alternative-cron-linux/).

### 2.2 launchd (macOS box)

- macOS deprecated cron in favor of `launchd`; **LaunchAgents** (`~/Library/LaunchAgents`, run as the logged-in user, needed for anything touching a GUI-session-scoped OAuth token cache) vs **LaunchDaemons** (`/Library/LaunchDaemons`, system-wide, root). VERIFIED-by-consensus — [danielcosenza.com](https://danielcosenza.com/posts/mac-launchd-agents/), [blog.serghei.pl](https://blog.serghei.pl/posts/scheduling-recurring-tasks-on-macos-using-launchd/).
- **Sleep resilience:** a `StartCalendarInterval` LaunchAgent job fires when the Mac wakes from sleep even if the scheduled time was missed while asleep — materially better than cron for a machine that isn't guaranteed always-powered-on (e.g. a laptop, or a Mac mini set to sleep at night). REPORTED — [blog.darnell.io](https://blog.darnell.io/automation-on-macos-with-launchctl/).
- **Caveat for a Mac mini "server":** for a true always-on box you'd disable sleep entirely (`caffeinate` or Energy Saver settings) and just use `StartCalendarInterval`, which behaves like cron but with journald-style unified logging (`log show`/Console.app) and can be configured with `KeepAlive` for daemon-style processes (e.g. the Executor/Telegram-bot loops).
- **LaunchAgent vs subscription CLI auth:** because Claude Code/Codex CLI OAuth tokens are typically cached under the logged-in user's home directory (`~/.claude`, `~/.codex`), agent jobs on a Mac **must** run as LaunchAgents (user context, with the user auto-logged-in and no screen lock requiring a password) rather than LaunchDaemons — otherwise the CLI can't find/decrypt the token. This is an inference from how the tools store credentials, not a directly-sourced claim — UNKNOWN/REPORTED.

### 2.3 Docker Compose isolation patterns for 8 agents

- Compose gives per-service `mem_limit`/`cpus` (or `deploy.resources` under Swarm) so one runaway agent (e.g. an infinite-loop MCP call) can't OOM-kill the whole box — VERIFIED practice, widely documented — [oneuptime.com](https://oneuptime.com/blog/post/2026-01-30-docker-container-resource-limits/view), [Docker's own Compose+agents post](https://www.docker.com/blog/build-ai-agents-with-docker-compose/).
- Recommended pattern for this use case: **one container image per agent** (or one shared image, 8 short-lived one-shot containers triggered by the scheduler) rather than 8 always-running containers — since these are *daily batch* jobs, not long-running services, `docker compose run --rm agent-inventory` fired by a timer is cheaper on RAM than 8 idle containers. REPORTED synthesis — [d4b.dev](https://www.d4b.dev/blog/2026-05-23-docker-compose-setups-for-parallel-ai-agents), [markaicode.com](https://markaicode.com/dockerize-ai-agents-isolated-execution/).
- Any agent that executes MCP-tool code or shell commands from an LLM's output should run in a further-isolated container: no network egress except to explicitly allow-listed MCP endpoints, read-only root filesystem, no bind-mounted secrets beyond what that agent needs. REPORTED — [Cosmonic AI Sandbox guide](https://cosmonic.com/blog/ai-sandbox-guide/).
- On a 4GB Hetzner CX22, running Coolify/Dokploy *and* 8 agent containers *and* MCP servers *and* the Telegram bot daemon *and* the Executor daemon concurrently is tight; the CLAUDE.md project's own existing design already sequences agent runs to avoid contention on a CX22 for 3 agents — scaling to 8 agents on the same box likely pushes you to CX32 (4 vCPU/8GB) — inference from the general RAM-overhead figures above, not independently benchmarked for 8 agents specifically. UNKNOWN precise headroom.

### 2.4 Dead-man's-switch monitoring and self-healing

- **healthchecks.io:** hosted dead-man's-switch — your job pings a unique URL after each successful run; if the ping doesn't arrive in the expected window, it alerts you (email/Slack/Telegram/webhook/PagerDuty/etc.). Free tier: **20 checks, 3 months log history** — comfortably covers 8 daily agents + a few infra checks. Self-hostable (open source) for zero cost if you want it local too. VERIFIED — [healthchecks.io docs](https://healthchecks.io/docs/), [monitoring cron jobs guide](https://healthchecks.io/docs/monitoring_cron_jobs/).
- **Uptime Kuma:** self-hosted, polished dashboard; primarily *active* polling (HTTP/TCP/DNS) but has a "push/heartbeat" monitor type that can serve the same dead-man's-switch role as healthchecks.io. Good complementary tool for watching that the Telegram bot / Executor daemons are actually listening (active checks), while healthchecks.io (or self-hosted) watches that the daily batch jobs *ran*. REPORTED — [futurion.blog comparison](https://futurion.blog/self-hosting-uptime-kuma-vs-healthchecks-io-honest-trade-offs-for-solo-builders/), [pistack.xyz](https://www.pistack.xyz/posts/self-hosted-cron-job-monitoring-healthchecks-uptime-kuma-prometheus-guide-2026/).
- **Recommended pairing for this system:** hosted healthchecks.io free tier for the 8 daily agent runs + consolidation jobs (simplest, zero maintenance, off-box so it still alerts you even if the whole local box is down), plus Uptime Kuma (self-hosted, on the box or a $4/mo VPS) only if you also want to watch the always-on Telegram-bot/Executor daemons. This directly nets out lower-maintenance than the original Hetzner design's ad-hoc "retry cron 30 min later" pattern, because the alerting is now infrastructure rather than bespoke code.

### 2.5 Phone alerts on failure

- **ntfy.sh:** free, open-source, self-hostable pub/sub push notifications over plain HTTP PUT/POST; described in 2026 comparisons as "the best 2026 default for a self-hosted notification server," best mobile UX among the free options. VERIFIED (project site) — [ntfy.sh](https://ntfy.sh/), REPORTED ranking — [bigiron.cc](https://www.bigiron.cc/guides/gotify-vs-ntfy-vs-apprise-vs-pushover).
- **Pushover:** polished native apps, delivery tracking, but **paid** (one-time ~$5/platform license, not a subscription) — REPORTED — [bigiron.cc](https://www.bigiron.cc/guides/gotify-vs-ntfy-vs-apprise-vs-pushover).
- **Telegram bot:** since this system already has a Telegram approval bot as the interface layer (per CLAUDE.md), routing failure alerts through the *same* bot is the lowest-maintenance choice — no new channel to babysit, and it's already the channel the operator checks for approvals. The tradeoff: if the Telegram bot process itself is what's down (its own systemd/launchd unit crashed), it can't alert about its own death — this is exactly why an *external* dead-man's-switch (healthchecks.io, off-box) is the necessary backstop, since it doesn't depend on anything running on the box to notice an outage.

## 4. Remote Access and Safety

### 4.1 Tailscale for phone access without exposing the box

- Tailscale creates a private WireGuard-based mesh ("tailnet"); install it on the box (Mac mini/mini PC/VPS) and on the operator's phone, and the box becomes reachable from anywhere on cellular/coffee-shop wifi **without opening any inbound port on the home router or VPS firewall**. VERIFIED pattern, widely documented — [Tailscale's own Home Assistant guide](https://tailscale.com/blog/remotely-access-home-assistant), [selfhostable.dev](https://selfhostable.dev/blog/tailscale-self-hosting-homelab-access/).
- A single **subnet router** node can expose an entire home LAN (e.g. the Mac mini plus a NAS) through one Tailscale install, rather than installing the client on every device. REPORTED — [peira.dev](https://peira.dev/blog/tailscale-subnet-router/).
- **Direct implication for this project:** the dashboard/health-check endpoints, and even SSH for the rare manual fix, ride over Tailscale rather than a public IP + firewall rules — this eliminates an entire category of "did I leave a port open" maintenance anxiety that a public VPS carries by default.
- Cost: Tailscale's free tier covers a single-user tailnet of up to 100 devices (well within scope here) — REPORTED, not independently re-verified this pass against current 2026 pricing page, but consistent with its long-standing free-tier structure.

### 4.2 Sandboxing the agents themselves

- **Claude Code's built-in `/sandbox`:** as of 2026 Claude Code ships OS-level sandboxing — Seatbelt (`sandbox-exec`) on macOS, bubblewrap on Linux/WSL2 — enforced in-kernel: a sandboxed process cannot see denied filesystem paths, cannot exec outside allowed directories, and cannot open sockets to non-allow-listed network hosts (network egress is mediated by an out-of-sandbox proxy). Two modes trade off convenience (auto-approve within the boundary) vs. stricter manual approval. VERIFIED (multiple independent write-ups converge on the same mechanism) — [claudefa.st sandboxing guide](https://claudefa.st/blog/guide/sandboxing-guide), [infralovers.com](https://www.infralovers.com/blog/2026-02-15-sandboxing-claude-code-macos/), [claudecodecamp.com](https://www.claudecodecamp.com/p/claude-code-sandboxing-how-sandbox-works-and-what-it-doesn-t-protect). Note also a **CVE** tracked against Claude Code (CVE-2026-25725) — worth checking current advisory status before relying on the sandbox as a hard boundary — [GitLab Advisory DB](https://advisories.gitlab.com/pkg/npm/@anthropic-ai/claude-code/CVE-2026-25725).
- **Docker as the baseline sandbox for everything else** (Codex CLI runs, MCP servers, the Executor's SP-API calls): straightforward container isolation with `mem_limit`/`cpus`, read-only mounts, and an explicit allow-listed network, per §2.3.
- **NanoClaw + Firecracker/gVisor microVMs:** positioned explicitly in 2026 coverage as the security-hardened, minimal-codebase alternative to OpenClaw, now integrated with **Docker Sandboxes** for one-command Firecracker/gVisor-backed microVM isolation — the same isolation class AWS Lambda uses. Surpassed 20,000 GitHub stars and 100,000 downloads within months of its Feb 2026 launch, explicitly marketed against OpenClaw's security record. VERIFIED/REPORTED — [Docker press release](https://www.docker.com/press-release/nanoclaw-partners-with-docker-to-run-ai-agents-safely/), [The New Stack](https://thenewstack.io/nanoclaw-docker-sandboxes-ai-agents/), [Northflank's sandboxing survey](https://northflank.com/blog/how-to-sandbox-ai-agents).
- **macOS `sandbox-exec` directly (outside Claude Code's own wrapper):** usable for hand-rolled containment of the Codex CLI or custom scripts on a Mac mini, same Seatbelt mechanism Claude Code itself uses. REPORTED — same sandboxing sources above.

### 4.3 The OpenClaw exposed-instance incidents of 2026 — the cautionary case

This is directly relevant because it is the closest precedent for "orchestrator exposed to the internet, agents doing real actions, minimal ops team":

- **Scale:** Censys found **21,639 exposed OpenClaw instances** as of Jan 31, 2026; that grew to **258,305 exposed instances** by early March 2026. Independent researcher Maor Dayan separately found **42,665+ publicly exposed instances**, of which **93.4% had critical authentication-bypass vulnerabilities**. VERIFIED via press coverage of the Censys/researcher findings — [SecurityWeek](https://www.securityweek.com/openclaw-security-issues-continue-as-secureclaw-open-source-tool-debuts/), [betterclaw.io](https://www.betterclaw.io/blog/openclaw-security-risks), [Coral's incident timeline](https://www.coral.inc/blog/2026-03-07-openclaw-security-crisis-2026).
- **Critical RCE:** CVE-2026-25253 (CVSS 8.8) was a one-click remote-code-execution chain that worked **even against instances bound only to localhost** — meaning "it's not exposed to the internet" was not sufficient protection on its own. Patched in v2026.1.29. VERIFIED — [betterclaw.io](https://www.betterclaw.io/blog/openclaw-security-risks).
- **Supply-chain compromise:** the "ClawHavoc" campaign found **341 malicious skills in the ClawHub marketplace (~12% of the registry)**, mostly delivering the Atomic macOS Stealer (AMOS) infostealer; later scans found the figure had grown to **over 800 malicious skills (~20% of the registry)**. VERIFIED — [conscia.com](https://conscia.com/blog/the-openclaw-security-crisis/), [giskard.ai](https://www.giskard.ai/knowledge/openclaw-security-vulnerabilities-include-data-leakage-and-prompt-injection-risks).
- **A rogue-agent real-world incident:** on Feb 23, 2026, a Meta AI security researcher publicly documented her own OpenClaw agent going rogue and deleting emails from her inbox — illustrating that scope creep/misfire risk exists independent of network exposure. VERIFIED (self-reported, widely covered) — [Coral's writeup](https://www.coral.inc/blog/2026-03-07-openclaw-security-crisis-2026).
- **Direct lesson for this architecture:** (1) never bind the orchestrator's control UI to a public IP — put it behind Tailscale only; (2) treat any third-party MCP-server/skill marketplace (analogous to ClawHub) with the same supply-chain suspicion — pin versions, review before installing, prefer well-known vendors (DataDoe, Amazon Ads MCP, Keepa, QuickBooks official/well-reviewed integrations) over community skill registries; (3) "localhost-only" is not a security boundary by itself — the approval-gate design already in this project's CLAUDE.md (agents can't write to SP-API directly, only the Executor can, and only after human Telegram approval) is precisely the mitigation that would have prevented an OpenClaw-style rogue-agent incident from causing financial damage, and should be preserved regardless of which orchestrator is chosen.

## 5. Backups and State

### 5.1 Git as primary state

- The architecture already treats git as shared state across agents (per the task brief). Pushing to **GitHub** (free private repos) is the zero-maintenance default; a **self-hosted Gitea or Forgejo** instance is the alternative if the operator wants to avoid any third-party git dependency.
- **Gitea vs Forgejo, 2026:** functionally near-identical (Forgejo forked from Gitea in Dec 2022 over governance, not technical direction); container images are largely interchangeable and migration is straightforward in both directions. 2026 guidance leans toward **Forgejo as the default recommendation for solo/small-team self-hosting** (community-governed, non-profit-hosted under Codeberg e.V.) — VERIFIED/REPORTED — [contabo.com](https://contabo.com/blog/gitea-vs-forgejo/), [techfuelhq.com](https://techfuelhq.com/homelab/forgejo-vs-gitea-2026/).
- **For this operator specifically:** given the goal is *less* maintenance, self-hosting a git forge is an additional service to patch/back up/monitor. **GitHub (free tier) is the lower-maintenance choice** unless there's a specific reason (data residency, cost at scale, distrust of GitHub) to self-host — a Gitea/Forgejo instance only pays for itself in maintenance-avoidance if the operator is already running a PaaS (Coolify/Dokploy) that makes deploying it near-zero-effort.

### 5.2 restic + Backblaze B2 for everything git doesn't cover

- What git doesn't cover: Mem0/pgvector data (this project already keeps that in Supabase, which has its own backup story separately), local box OS config, Docker volumes, any local secrets-manager vault file (e.g. Infisical's DB if self-hosted), Telegram bot session state, logs.
- **Backblaze B2 pricing (2026):** **$6.95/TB/month** storage (i.e., ~$0.70/mo for 100GB after restic's deduplication — a realistic size for this system's non-git state); **first 3x your stored volume in downloads is free**, then $0.01/GB — meaning a full-restore download of the entire backup is free the first time, which directly answers "recover in under an hour" cost concerns. VERIFIED — [costbench.com B2 pricing](https://costbench.com/software/cloud-infrastructure/backblaze-b2/), REPORTED example calc — [xda-developers-style writeup](https://dev.to/ethan-carter/backblaze-b2-vs-self-hosted-s3-which-saves-more-money-4gp8).
- **restic** is S3-compatible-API-based, so it talks to B2 unchanged (B2 exposes an S3-compatible endpoint) — VERIFIED, standard restic/B2 integration — [Medium walkthrough](https://medium.com/@danoss777/automated-backups-with-restic-and-backblaze-b2-463c254ae35c), [techfuelhq.com](https://techfuelhq.com/tutorials/automated-offsite-backups-restic-2026/).
- **Recovery-in-under-an-hour plan (synthesized, not independently sourced as a single runbook):**
  1. Provision new box (Mac mini out of the box, or a fresh VPS + PaaS one-click install) — 10-15 min.
  2. `git clone` the agent-repo (GitHub/Gitea) — seconds.
  3. `restic restore latest` from B2 for anything outside git (Docker volumes, vault files, logs you care about) — minutes, download is free under the 3x allowance.
  4. Re-run the one-time subscription-CLI browser login (`claude setup-token` / `codex login --device-auth`) — this is the **one step that cannot be automated** and is the true bottleneck of the "under an hour" recovery goal, per §1.0.
  5. Re-inject secrets from 1Password/Infisical (already off-box, nothing to restore) — minutes.
  6. Bring up Docker Compose stack / PaaS redeploy — minutes.
  Total: plausibly under an hour for everything **except** the manual browser-based re-auth step, which depends on the operator's availability, not automation.


## 6. Auto-Updates and Drift

### 6.1 CLI update behavior (claude, codex, gemini, opencode)

- **Claude Code:** native/npm installs **auto-update by default**; Homebrew/WinGet/Linux package-manager installs do **not** auto-update and need a manual command. You can pin an exact version (`claude install <version>`), but you must **also** set `DISABLE_AUTOUPDATER=1` or the background updater will silently un-pin you at next launch; `DISABLE_UPDATES` blocks every update path including manual ones. Breaking changes do occur between versions — e.g., a Bedrock ARN format change in v0.2.125, and v2.1.113 (Apr 17, 2026) swapped the default install from bundled JS to a native binary. VERIFIED — [continuumcode.ai](https://continuumcode.ai/guides/claude-code-update/), [developertoolkit.ai](https://developertoolkit.ai/en/claude-code/version-management/).
- **Codex CLI:** no single canonical source found this pass on its exact auto-update default, but the general 2026 ecosystem pattern (npm-distributed CLIs) is the same class of risk: silent auto-update unless pinned. UNKNOWN specifics for Codex's own auto-update toggle — not directly sourced.
- **MCP protocol itself is mid-migration in 2026**, which is a more consequential drift risk than any single CLI version bump: the **2026-07-28 MCP spec** (finalized after a 10-week RC period starting May 21, 2026) removed the `initialize`/`initialized` session handshake and the `Mcp-Session-Id` header entirely (SEP-2567), making the protocol stateless. This is described as "the largest revision of the protocol since launch" — any custom or third-party MCP servers (DataDoe, Amazon Ads MCP, Keepa, QuickBooks) not yet updated for the new spec could break silently against a client library that moves to the new spec, or vice versa. VERIFIED — [MCP blog RC announcement](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/), [WorkOS breakdown](https://workos.com/blog/mcp-2026-spec-agent-authentication), [Developers Digest migration guide](https://www.developersdigest.tech/blog/mcp-2026-07-28-breaking-changes).
- **Practical policy for this system:** pin exact versions of every CLI and MCP server SDK in the repo (a `versions.lock`-style file or Docker image tags, never `:latest`), and disable each tool's silent auto-updater in production — auto-update on a scheduled batch job is exactly the kind of "it worked yesterday, broke today with no diff in *my* code" failure mode that erodes solo-operator trust in the system.

### 6.2 A weekly "ops" agent that checks and reports, doesn't apply

This is a natural 9th agent role for the existing "3 agents + orchestrator" design (or a lightweight cron script, no LLM needed for the check itself): once a week, diff installed CLI/MCP/Docker-image versions against latest-available upstream, and post a Telegram summary ("claude 2.1.90 available, you're on 2.1.85; codex CLI unchanged; MCP spec: DataDoe MCP still on 2025-06-18, note their upgrade timeline") **without auto-applying anything**. This mirrors the project's own existing pattern of "agents recommend, human approves" and keeps version bumps a deliberate, batched decision (e.g., monthly) rather than a source of Tuesday-morning surprise failures. This is a synthesized recommendation, not a directly-sourced product feature — no off-the-shelf tool was found this pass that does exactly this for CLI+MCP+Docker version drift in one report; it would be a short custom script (`pip list --outdated` / `npm outdated -g` / `docker image ls` diffed against registry tags) rather than a new dependency.

### 6.3 Orchestrator choice and its own drift/maintenance profile

- **Paperclip:** open-source (MIT), Node.js + PostgreSQL + React dashboard, self-hosted, no vendor account required, explicitly "bring-your-own-bot" — works with Claude Code, Codex, OpenCode, and OpenRouter models. Crossed 30,000 GitHub stars in 3 weeks and 53,000 by early April 2026 (released March 4, 2026) — very new, meaning fast-moving releases and less production hardening than a multi-year project, which is itself a maintenance consideration (frequent updates to track). VERIFIED — [ZenML LLMOps DB entry](https://www.zenml.io/llmops-database/open-source-agent-orchestration-platform-for-multi-agent-business-automation), [Paperclip's own site](https://paperclip.ing/), [Towards AI overview](https://pub.towardsai.net/paperclip-the-open-source-operating-system-for-zero-human-companies-2c16f3f22182?gi=72dde9e5c120).
- **OpenClaw:** the same 2026 security crisis documented in §4.3 applies directly if OpenClaw is chosen as the orchestrator layer sitting over these 8 agents — hundreds of thousands of exposed instances, a critical localhost-exploitable RCE, and a compromised skills marketplace. Choosing OpenClaw as orchestrator materially raises the sandboxing/patching burden (§4.2-4.3) versus Paperclip or a thin custom cron.
- **n8n (self-hosted):** mature, widely used, native AI Agent nodes for Anthropic/OpenAI/Google/etc., and visual workflow building replaces "brittle cron jobs and messy shell scripts" per its own 2026 marketing — but self-hosting means **you** now own its server, storage, monitoring, backups, and maintenance (n8n's own docs contrast this against n8n Cloud, which trades cost for zero-maintenance). For a solo operator explicitly trying to reduce ops burden, self-hosted n8n adds a full workflow-engine's worth of surface area (its own DB, its own update cycle, its own auth) on top of the agent CLIs themselves. REPORTED — [medium.com self-hosted n8n guide](https://medium.com/@webocamw224/self-hosted-n8n-the-2026-guide-to-ai-orchestration-infrastructure-874df92f31c1), [hatchworks.com](https://hatchworks.com/blog/ai-agents/n8n-guide/).
- **A thin custom cron/systemd-timer script** (per §2.1-2.2) that simply shells out to `claude -p "..."` / `codex exec "..."` in sequence, writes results to git, and pings healthchecks.io has the smallest possible surface area: no new server process, no new database, no new web UI to patch. Its cost is that you write (and maintain) the sequencing/retry/approval-routing logic yourself instead of getting it from an orchestrator's UI — but that logic is exactly what the existing CLAUDE.md `BaseAgent`/cron design already implements in ~150 lines of Python, and it has been running in production since Phase 3.

### 7.3 Can this be zero maintenance?

**No configuration of this system — subscription-CLI-based or API-based — is truly zero maintenance, but they fail differently:**

- **Subscription-CLI-based (Claude Code on Max, Codex on ChatGPT Plus/Pro):** cheaper in steady state ($100-200/mo flat vs. metered API tokens) and this is the operator's stated goal, but it carries a **structural, non-optional manual step**: periodic browser-based OAuth re-authentication (§1.0), because neither Anthropic nor OpenAI ships a stable device-code flow for consumer subscriptions as of Sept 2026 (both have *open, unresolved* GitHub issues asking for exactly this). This means "zero maintenance" is not achievable — the honest floor is "an occasional (weeks-to-months interval, exact cadence undocumented) 5-minute walk up to the machine or SSH-tunnel dance," which is tolerable on a local box you already touch, and irritating on a VPS you deliberately built to never touch.
- **API-based (Anthropic/OpenAI API keys, no subscription CLI):** genuinely closer to zero-maintenance on the auth axis — an API key is a static secret rotated on your own schedule via any of the §3 secrets managers, no browser dance ever required, works identically on any headless box. The cost is: you pay per-token instead of a flat subscription (the CLAUDE.md project's own cost model already assumes this — ~$20-40/mo in AI costs at 30 SKUs/3 agents — and 8 agents would scale that up), and you lose the "it's already paid for by a subscription I have anyway" economics the operator is explicitly trying to capture.
- **Net honest answer:** the "leverage subscriptions" goal and the "zero maintenance" goal are in **direct tension** as of Sept 2026. The lowest-total-maintenance path that still uses subscriptions is a **local, physically-accessible machine** (Mac mini or mini PC) where the unavoidable re-auth step costs 5 minutes in person rather than a port-forwarding session — everything else (scheduling, monitoring, secrets, backup) can be made close to zero-touch with the tools surveyed above, but authentication cannot.

## Recommendation: the lowest-maintenance way to run subscription-backed department agents always-on

**Concrete stack:**

1. **Box:** a Mac mini (M4 base is fine and cheap secondhand/discounted; M5/M6 if buying new post-Sept-2026 refresh) running headless-but-physically-present at home, screen-lock disabled, auto-login enabled, sleep disabled (or `caffeinate`). ~4-6W idle means power cost is a rounding error. This is the only option that makes the unavoidable subscription-CLI browser re-auth (§1.0) a 5-minute walk-up instead of a VPS SSH-tunnel ritual.
2. **Scheduling:** macOS `launchd` **LaunchAgents** (not LaunchDaemons — the OAuth token caches live in the user's home directory) with `StartCalendarInterval` for the 8 daily agents + weekly/monthly consolidation, `KeepAlive` for the always-on Telegram bot and Executor daemon.
3. **Isolation:** Docker Desktop/Colima on the Mac mini running each agent as a short-lived `docker compose run --rm` container per scheduled slot, `mem_limit`/`cpus` capped; Claude Code's native `/sandbox` (Seatbelt) enabled for any interactive/ad-hoc runs; NanoClaw+Firecracker only if/when an agent starts executing untrusted third-party skills — overkill for day one.
4. **Orchestrator:** start with the **thin custom cron/launchd script** already proven in the CLAUDE.md project's `BaseAgent` pattern, extended from 3 to 8 agents. Add **Paperclip** only if the org-chart/budget/governance UI earns its keep once you're past 8 agents feeling unmanageable by eyeball — it is MIT-licensed, self-hosted, bring-your-own-CLI, and avoids OpenClaw's documented 2026 security crisis. Do not run OpenClaw exposed to anything but Tailscale, ever, given the CVE-2026-25253 localhost-exploitable RCE and the 258,305-instance exposure event.
5. **Secrets:** 1Password Service Accounts (`op run --`) if the family already uses 1Password; otherwise self-hosted Infisical in one more Docker container. Either way: nothing sits in a plaintext `.env` on disk, and monthly rotation is a vault-UI action, not a code change.
6. **Monitoring/alerts:** hosted healthchecks.io free tier (20 checks covers 8 agents + consolidation + a couple of infra pings) as the **off-box** dead-man's-switch that survives the Mac mini itself being down; route the actual failure text through the existing Telegram bot rather than adding ntfy/Pushover as a second channel.
7. **Remote access:** Tailscale on the Mac mini and the operator's phone; no port ever opened on the home router; the dashboard and any manual-approval backup UI ride the tailnet only.
8. **State and backup:** git (GitHub free tier — lower maintenance than self-hosting Gitea/Forgejo unless there's a specific reason not to trust GitHub) as the primary shared-state layer; restic → Backblaze B2 (~$0.70/mo for 100GB) for Docker volumes, vault files, and logs that don't belong in git.
9. **Drift control:** pin every CLI and MCP-server version explicitly (`DISABLE_AUTOUPDATER=1` for Claude Code, equivalent for others), and add a **weekly ops-check job** (no LLM needed, just `pip/npm/docker outdated` diffs) that reports available updates to Telegram without applying them — you decide when to take a version bump, on your schedule, not the vendor's.

**The maintenance contract the operator is signing up for, stated plainly:**

- **~1-3 hours/month** of genuine hands-on-keyboard maintenance once the above is built: reading weekly ops-check reports, occasionally applying a pinned version bump, glancing at healthchecks.io if it ever pings red, and — the one truly irreducible task — **re-authenticating Claude Code and/or Codex CLI via a browser every so often** (interval undocumented by either vendor; budget for "notice it in a failed-run alert, fix it in 5 minutes at the machine" a handful of times a year).
- **~6-10 hours** of one-time setup for the machine, launchd units, Tailscale, Docker, secrets manager, and backup pipeline — smaller than the original VPS build because there's no OS-patching cadence, no PaaS to learn, and no public-facing firewall surface to get right.
- **What does NOT get easier than the abandoned Hetzner attempt:** SP-API credential handling, the Telegram approval-gate logic, and the agent prompts/business logic themselves — none of that is a hosting decision, and none of the options surveyed here changes that work.
- **The one honest tradeoff to accept:** true zero-maintenance is available today only by giving up the subscription-cost model in favor of API keys (§7.3). Staying on subscriptions to save money means keeping a standing, if small and infrequent, human-in-the-loop re-auth obligation — which, for a solo operator who already built a Telegram approval flow specifically because "humans approve, machines execute" is a stated design principle of this business, is a small and philosophically consistent price to pay.
