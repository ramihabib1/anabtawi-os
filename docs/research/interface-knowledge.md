## 1. Approval and Chat Channels

### Telegram Bot API

- **Inline keyboards**: Telegram messages can carry an `InlineKeyboardMarkup` of buttons; taps trigger a `CallbackQuery` carrying `callback_data` (e.g. `"approve:<uuid>"`), which a `CallbackQueryHandler` (python-telegram-bot) or equivalent listens for. This is the standard way to build Approve/Reject buttons attached to a message. VERIFIED — [Telegram Bot API](https://core.telegram.org/bots/api)
- **Webhook vs polling**: Telegram exposes exactly two mutually exclusive update-delivery modes — `getUpdates` long polling, or a registered HTTPS webhook. Long polling is simplest to run behind a NAT/firewall (a solo operator's Hetzner box with no public path needed) and is recommended for getting started/small deployments; webhooks reduce latency and server load but require a public HTTPS endpoint with a valid cert. VERIFIED — [Telegram Bot API](https://core.telegram.org/bots/api); REPORTED (2026 practitioner consensus: "start with long polling, switch to webhook only if you need lower latency/scale") — [Statiko Blog, Telegram Bot Development 2026](https://statiko.io/blog/telegram-bot-development)
- **python-telegram-bot**: async-first, mature, ships `JobQueue` for repeating/scheduled tasks (used for e.g. polling Supabase for new notifications) and `ConversationHandler` for multi-step flows; most popular Python-side library. VERIFIED — [python-telegram-bot vs grammY comparison](https://grammy.dev/resources/comparison)
- **grammY**: TypeScript-first, strong typing, plugin ecosystem, Deno-compatible; a good option if the harness/company is Node-based rather than Python-based. Higher weekly npm downloads than node-telegram-bot-api despite fewer GitHub stars. VERIFIED — [grammY vs node-telegram-bot-api npm trends](https://npmtrends.com/grammy-vs-node-telegram-bot-api-vs-telegraf-vs-telegram-bot-api), [grammY comparison page](https://grammy.dev/resources/comparison)
- Given this repo's stack is Python end-to-end (Section: Technology Stack), **python-telegram-bot stays the correct choice** for a vendor-agnostic-but-Python operator; grammY would only make sense if the harness were Node/TS.

### WhatsApp Business API

- **Meta Cloud API** moved from conversation-based pricing to **per-message billing on July 1, 2025**; by category (marketing/utility/authentication) and destination country. Examples: marketing ~$0.025 in the US, ~$0.0625 in Brazil; authentication ~$0.0034 in the US. All non-template replies inside a 24-hour customer-service window remain free, and messages within 72h of a click-to-WhatsApp ad are free. From **Oct 1, 2026** Meta begins charging per business message (including service replies/utility messages) inside that 24h window too — closing the "free window" loophole solo operators currently rely on. VERIFIED — [WhatsApp Business API Pricing 2026 guide](https://www.engagelab.com/blog/whatsapp-business-api-pricing), REPORTED (Oct-2026 policy change, country-rate table) — [Blueticks WhatsApp Pricing 2026](https://blueticks.co/blog/whatsapp-business-api-pricing-2026)
- **Approval to send**: The Cloud API requires Meta Business verification and template message pre-approval for anything sent outside the 24h window — friction for a fast-moving daily-brief use case (you'd need Meta to approve a "daily inventory brief" template before you can push it, and any format change may need re-approval).
- **Twilio's WhatsApp API** is a hosted wrapper over the same Meta Cloud API with added reliability/billing tooling — same approval and per-message cost structure, plus Twilio's own markup, but easier onboarding.
- **Baileys (unofficial WhatsApp Web client library)**: reverse-engineers the WhatsApp Web protocol; **not affiliated with or endorsed by Meta**. 2026 practitioner consensus: substantial ban risk — WhatsApp's ML ban models weight low reply-ratio, contact-graph distance from strangers, and robotic/regular timing; unofficial clients "typically last 2-8 weeks before detection," and ~1 in 5 unofficial-API numbers get banned within a year, with **no appeal** once banned. A widely-installed "anti-ban" npm package (`lotusbail`, 56k downloads) was found in April 2026 to be exfiltrating session credentials. **Verdict: do not use Baileys for a business-critical approval channel.** VERIFIED — [SporeSec: WhatsApp unofficial API ban risk](https://sporesec.com/en/blog/whatsapp-unofficial-api-ban-risk), [Whatsapp Checkleaked: What Is Baileys](https://whatsapp.checkleaked.cc/blog/what-is-baileys)

### Slack

- Block Kit "Actions" blocks render Approve/Deny buttons; Bolt SDK (`@app.action("approve_button")` in bolt-python) handles the resulting `block_actions` interaction payload. Good audit trail if paired with a logging middleware (message text + actor + timestamp), but Slack is built for teams/channels, not phone-first single-user push — notifications are usually less prominent/naggy on mobile than Telegram or a native push app. VERIFIED — [Slack: Creating an interactive message](https://api.slack.com/automation/interactive-messages), [slack_bolt docs](https://tools.slack.dev/bolt-python/api-docs/slack_bolt/)
- HumanLayer's primary channels today are **Slack and email**, with Discord "coming" — i.e. the most mature open OSS human-in-the-loop tooling is Slack-first, not Telegram-first. REPORTED — [ChatGate: HumanLayer overview](https://chatgate.ai/post/humanlayer/)

### Signal (signal-cli)

- signal-cli (AsamK) is the standard open-source CLI/daemon binding to the Signal protocol; Python wrappers (`signalbot`, `Signal-Bot`) build simple chatbots atop it. Fully self-hosted, no per-message cost, strong privacy — but it's a personal messenger, not built for rich interactive components: no native inline buttons/callback data equivalent to Telegram, so "approve" flows have to be emulated with reply-keyword parsing (e.g. reply "YES 123") rather than a tap. VERIFIED — [pblaas/signalbot GitHub](https://github.com/pblaas/signalbot), [Signal-Bot docs](https://signal-bot.readthedocs.io/)
- OpenClaw (see below) ships a Signal channel with a pairing/allowlist model (`openclaw pairing approve signal <CODE>`), giving Signal a workable access-control story despite the lack of native buttons. VERIFIED — [OpenClaw Signal docs](https://docs.openclaw.ai/channels/signal)

### Discord

- Slash commands/buttons need either a running bot process listening on the Gateway (WebSocket) or an HTTP-interactions endpoint (public URL) — webhooks alone can *post* a button but cannot *receive* the click, so a lightweight bot process is unavoidable if buttons are wanted. Good ephemeral-message support (reply visible only to the approver) and free. Typically favored when the "company" already has a Discord presence for other reasons; adds no benefit over Telegram for a pure solo phone-approval flow. VERIFIED — [Discord Webhook Guide 2026](https://discord-webhook.com/en/discord-webhook-guide/), [Latenode: interactive buttons from webhook](https://community.latenode.com/t/adding-interactive-buttons-to-discord-bot-messages-from-webhook/25852)

Launched March 2026, crossed 50k+ GitHub stars within weeks — signals real practitioner demand for exactly this "approve financial actions from a dashboard" pattern the CLAUDE.md architecture already describes by hand. VERIFIED — [Paperclip GitHub](https://github.com/paperclipai/paperclip), [Paperclip open-source product page](https://paperclip.ing/product/open-source/)
- **n8n Telegram/Slack/Discord "Send and Wait for Approval" nodes**: n8n's messaging nodes have a built-in operation that sends a message with Approve/Decline buttons (or a form) and pauses the workflow (see Section 2). Useful if the orchestrator is n8n rather than a custom cron+bot stack. VERIFIED — [n8n Waiting docs](https://docs.n8n.io/flow-logic/waiting/)
- **Claude Code's own mobile approvals**: As of Claude Code v2.1.110 (Apr 16, 2026), the official Claude mobile app can receive **push notifications when Claude needs approval to continue** ("Remote Control" + `/config` → "Push when Claude decides"), directly modeling the exact pattern this project needs, but it is Anthropic-account/Claude-app-specific, not vendor-agnostic. A pre-existing community workaround (`claude-push`, using **ntfy.sh**) achieves the same Allow/Deny-from-phone flow with a fully open, self-hostable notification channel — closer to the vendor-independence goal. VERIFIED — [Claude Code mobile docs](https://code.claude.com/docs/en/mobile), [coa00/claude-push GitHub](https://github.com/coa00/claude-push)

## 2. Approval Flow Design

### The core pattern: pause, persist, resume

The most rigorously documented open framework for this is HumanLayer's **12-Factor Agents**, distilled from "100+ production implementations." The relevant factors:

- **Factor 5 — Unify execution state and business state**: keep a single append-only event/thread log as the one source of truth for both "what the agent has done" and "the data it gathered" — this is what makes an in-flight approval resumable after a restart, because the whole state is reconstructable by replaying the log rather than living in an in-memory stack. VERIFIED — [12-factor-agents, factor-05](https://github.com/humanlayer/12-factor-agents)
- **Factor 6 — Launch/Pause/Resume with simple APIs**: an agent should be able to stop (e.g. to wait on a human) and resume "exactly where it left off" by reloading its thread from a `ThreadStore`; serialize state → pause → resume later when conditions (the human's answer) change. This is precisely what CLAUDE.md's `approval_requests` table + Executor polling loop already implements: the "thread" is a Postgres row, the "pause" is `status = 'pending'`, and "resume" is the Executor's 60-second poll picking up `status = 'approved'`. VERIFIED — [12-factor-agents, factor-06-launch-pause-resume.md](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-06-launch-pause-resume.md)
- **Factor 7 — Contact humans with tool calls**: model asking a human as a structured, high-latency "tool call" (`request_approval(...)`) rather than a side-channel — this keeps the whole interaction inside the same auditable event log instead of out-of-band Slack/Telegram history that isn't tied back to the run. VERIFIED — [12-factor-agents repo, DeepWiki summary](https://deepwiki.com/humanlayer/12-factor-agents/3-the-12-factors)
- **Factor 12 — Stateless reducer**: each step is `(state, input) → new state`; this is what makes "restart-safe" easy — a crashed process just re-derives state from the log/DB rather than needing in-memory recovery logic.

### What survives an orchestrator restart

Only **durable, external-to-the-process state** survives a restart: a database row (Supabase `approval_requests`), a file in git, or a message already delivered to Telegram/Slack (the platform holds it, not your process). Anything held only in a Python object's memory (an in-flight `asyncio` task, a LangChain/agent-loop stack frame) is lost. Concretely, for a cron-triggered, non-daemon agent architecture like CLAUDE.md's:
- The **agent process itself does not need to survive restart** — it runs once, writes a proposal row, and exits. There is nothing "paused" inside it.
- The **Executor daemon** is the one persistent process; it is restart-safe by design because it re-derives everything to do from `SELECT * WHERE status='approved' AND execution_result IS NULL` on every 60s tick — a crash mid-loop just means the next tick picks up where it left off. This is a stateless-reducer/idempotent-poll pattern in practice, matching Factor 12.
- The **Telegram bot's** pending-approval watcher is likewise safe as long as "have I already posted this approval to Telegram" is tracked in the DB (`telegram_msg_id IS NULL` as the not-yet-sent marker, exactly as in CLAUDE.md section 8.1) rather than in bot memory — a bot restart just re-scans and re-posts nothing extra.

### n8n's Wait node as an alternative substrate

n8n's Wait node offloads the entire execution's data to n8n's own database when a workflow pauses, and reloads it on resume — so a **properly configured (non-SQLite, persisted) n8n instance** gives restart-safety "for free" without hand-rolling a Postgres approval table, at the cost of coupling the approval mechanism to the n8n runtime (less vendor-agnostic than a plain Postgres table + any bot). The "Send and Wait for Approval" operation on the Telegram/Slack/Discord/Email nodes packages the whole pattern (button, pause, resume) in one node. VERIFIED — [n8n Waiting docs](https://docs.n8n.io/flow-logic/waiting/), [n8n Human Approval Workflow guide](https://rills.ai/blog/n8n-human-approval-workflow)

### File-based / git-based approval queues

An emerging pattern for "harness-agnostic, no DB required" setups: a proposal is a **Markdown file with YAML frontmatter** committed to a git repo (`status: pending`), a bot or CI job watches for new files/PRs, and a human flips `status: approved` either by editing the frontmatter and pushing, or by clicking Approve on a linked PR review. Git gives free audit trail (commit history = who/when/what), free diffing, and free restart-safety (the filesystem/git object store is the durable state). GitHub's own **GitHub Agentic Workflows (gh-aw)**, in technical preview since Feb 2026, formalizes a version of this: agent-run automations "never merge automatically," and any change proposal surfaces as an issue/comment/PR that a human must explicitly review and approve/merge — making **the PR-review mechanism itself the approval gate**, with GitHub's own audit log (reviewers, timestamps, required-approval branch protection) doing double duty as the approval ledger. VERIFIED — [GitHub Agentic Workflows about page](https://docs.github.com/en/copilot/concepts/agents/about-github-agentic-workflows), [github/gh-aw](https://github.com/github/gh-aw)
- Tradeoff vs. a Postgres `approval_requests` table: git/PR-based approval is a very good fit for *code and content* changes (listing copy edits, prompt tweaks, playbook edits) but is a poor fit for *time-sensitive financial* approvals from a phone (no push notification, no one-tap mobile button, git push friction) — so a hybrid is sensible: **Telegram/chat for time-sensitive $ actions, git-PR for content/knowledge changes**.

### Enforcing that only the human can approve

Concrete, verifiable mechanisms in use in 2026 practitioner writeups:
1. **Allowlisted chat ID / user ID** — the bot process hard-codes (or reads from env) a single numeric Telegram user ID (or WhatsApp/Signal number) and ignores/logs any callback or command from any other ID; this is the baseline every OSS chat-agent project (OpenClaw, Hermes-agent) implements as `allowed_users`/`allowFrom`. VERIFIED — [Hermes-agent Telegram allowed_users issue](https://github.com/NousResearch/hermes-agent/issues/36702), [OpenClaw Telegram docs](https://docs.openclaw.ai/channels/telegram)
2. **Executor-side status gate**: even if a chat message were somehow spoofed, only a row with `status='approved'` is ever executed, and only the bot's approve-callback handler (itself allowlist-gated) is permitted to write that status — i.e., defense in depth across two independent components (Telegram bot + Executor), matching CLAUDE.md §13.2's access-control table.
3. **Two-step confirm for money**: 2026 BFSI/agent-governance writeups converge on a **"maker-checker"/four-eyes pattern for high-value or irreversible actions** — propose → a first tap moves it to "confirm?" state showing the same payload again → a second, distinct tap actually executes; separately, some guides recommend genuinely distinct **approver identity** for high-risk actions (not just two taps by the same person) as the gold-standard control, though for a true solo operator this collapses to "tap twice," which still guards against fat-finger taps and message-preview auto-actions. REPORTED — [Pinksheep: AI Agent Approval Workflows](https://www.pinksheep.ai/guides/ai-agent-approval-workflows), REPORTED (maker-checker mapping) — [Agent UX Patterns for BFSI](https://proud-finch-3vb4.here.now/)
4. **Signed messages / cryptographic proof of approver**: not commonly implemented in the OSS projects surveyed — HumanLayer, OpenClaw, and n8n all rely on **platform-level identity** (Telegram/Slack's own auth binds a callback to a specific numeric account) rather than an additional signature scheme. For a solo operator this is proportionate: the chat platform's login already is the "signature," and adding e.g. a TOTP code inside the approval reply is the pragmatic upgrade if stronger non-repudiation is wanted, rather than building bespoke crypto.
5. **Expiry**: CLAUDE.md's own `expires_at` + `expire_stale_requests()` pattern (approvals auto-expire after 24h) is itself a documented safety control — a stale, un-acted-on proposal should not silently execute later just because someone taps an old notification. This matches general HITL guidance to bound the "authorization window."

## 3. Daily Brief Delivery

### Rendering to Telegram

- Hard limit: **4096 UTF-8 characters per message**, counted **after** entity parsing — i.e. Markdown/HTML formatting characters (`*bold*`, `<b>`) don't count against the limit, only the rendered visible text does. A brief that runs long must be **chunked** into a sequence of messages (~4000 chars each, split on section boundaries) rather than truncated. VERIFIED — [Telegram Bot API](https://core.telegram.org/bots/api), [conferbot Telegram limits](https://www.conferbot.com/limits/telegram)
- Supported inline formatting: bold, italic, underline, strikethrough, spoiler, block quote, inline links, and pre-formatted code, via either MarkdownV2 or HTML `parse_mode` — CLAUDE.md's convention of `parse_mode="HTML"` with `<b>` labels avoids MarkdownV2's notoriously fussy escaping rules (every `.`, `-`, `!`, `(` etc. must be backslash-escaped in MarkdownV2), which is the correct practical choice. VERIFIED — [Telegram Bot API](https://core.telegram.org/bots/api)
- Practical daily-brief pattern seen in the wild: keep the **chat message short** (headline alerts + stats, as in CLAUDE.md §8.1's Daily Brief Format) and link out to the full wiki page for anything long-form, rather than trying to cram the whole brief into Telegram's 4096-char box.

### Rendering to a static wiki site

Five markdown-to-site generators compared for a "generate the company wiki automatically on push" use case:

| Generator | Language/stack | Best fit | Popularity (2026) | Notes |
|---|---|---|---|---|
| **MkDocs** (+Material theme) | Python | Hierarchical docs/knowledge bases | Most popular of the five by a wide margin — "9x more popular than Obsidian Publish" | Simple `mkdocs.yml` nav, huge plugin ecosystem, trivial GitHub Pages/Actions deploy; Python-native fits this project's stack. VERIFIED — [InfoWorld: Popular Markdown documentation tools compared](https://www.infoworld.com/article/3526306/text-in-docs-out-popular-markdown-documentation-tools-compared) |
| **Docusaurus** | React/Node | Large, complex, versioned docs | High, especially in JS-heavy orgs | More setup overhead than warranted for a 4-page/30-SKU wiki; React toolchain is unnecessary weight for a Python shop. VERIFIED — [wmtips Docusaurus vs Quartz](https://www.wmtips.com/technologies/compare/docusaurus-vs-quartz/) |
| **Quartz** | Node/TS, Obsidian-native | "Digital garden" of interlinked notes, backlinks, graph view | Smaller but purpose-fit for note-graphs | Explicitly designed by creator Jacky Zhao for publishing an **Obsidian-style vault of notes** (not top-down docs) — closest conceptual match to a Mem0-derived wiki of interlinked product/competitor/playbook pages, since it renders `[[wikilinks]]` and backlinks natively; ~30-60 min initial setup. VERIFIED — [wmtips MkDocs vs Quartz](https://www.wmtips.com/technologies/compare/mkdocs-vs-quartz/) |
| **Obsidian Publish** | Hosted SaaS (Obsidian's own) | Direct vault-to-web publishing, zero build step | Least popular of the five, paid ($) | Only sensible if the wiki *is* an actual Obsidian vault the operator edits directly; not a good fit for a Postgres/Mem0-generated wiki with no human ever opening Obsidian. |
| **mdBook** | Rust | Rust project docs | Niche outside Rust ecosystem | Not a good fit unless the team already uses Rust tooling. |

**Recommendation for this project**: MkDocs (Material theme) for the primary docs-style wiki structure the CLAUDE.md dashboard already models (products/competitors/playbooks/briefs categories), because it is Python-native (matches the stack), the most battle-tested, and deploys to GitHub Pages/Cloudflare Pages with a one-line GitHub Actions job (`mkdocs gh-deploy` or `mkdocs build` + Pages artifact upload) triggered on every push to `main` — i.e., **the `wiki_pages` table's generated markdown can be dumped to files and rebuilt on every consolidation run with zero manual site maintenance**.

### Automatic build-and-deploy on push

- Standard pattern: a GitHub Actions workflow triggered on push to `main` (or on a schedule after the wiki-compiler cron writes new markdown and commits it) runs `mkdocs build`/`quartz build` and deploys the output either to **GitHub Pages** (native `actions/deploy-pages`) or **Cloudflare Pages** (native Git integration; Cloudflare rebuilds automatically on push, no Actions workflow strictly required). VERIFIED — [GitHub - cloudflare-static-site-demo](https://github.com/dilatchi/cloudflare-static-site-demo)

### Private access with zero hosting maintenance

Two credible, low-maintenance options to give the family (father, brother) private read access without running an auth server:

1. **Cloudflare Access (Zero Trust)** in front of Cloudflare Pages: free tier covers **up to 50 authenticated users** at no cost; Access intercepts requests at Cloudflare's edge and gates them behind an email-based **One-Time-PIN login** (no OAuth app, no user database, no server code) — you just add each family member's email to an allow policy. Important caveat: **Cloudflare does not let you protect the default `*.pages.dev` subdomain** — a custom domain is required for full Access protection. VERIFIED — [Cloudflare Community: Pages protected by Zero Trust/Access](https://community.cloudflare.com/t/pages-protected-by-cloudflare-zerotrust-access-possible/393299), [kf7i.net: Locking Down a static site with Cloudflare Access](https://www.kf7i.net/posts/social-auth-static-site/)
2. **Tailscale** (or self-hosted **Headscale** if avoiding any third-party control-plane account): puts the wiki on a private mesh network reachable only by devices the operator has explicitly added — no public URL exists at all. Tailscale's 2026 personal-plan update raised the free tailnet cap to **6 accounts**, comfortably covering operator + father + brother. Headscale trades Tailscale's OAuth-based (Google/Microsoft/GitHub/Apple) login for pre-shared keys and its own user model, fully removing any third-party SSO dependency — the more "vendor-independent" of the two. VERIFIED — [Tailscale: sharing with friends and family](https://tailscale.com/blog/tailscale-sharing-friends-family), [XDA: Tailscale plan changes](https://www.xda-developers.com/tailscale-plan-changes-make-it-easier-to-share-your-home-lab-with-friends/), [juanfont/headscale GitHub](https://github.com/juanfont/headscale)

**Verdict**: for "give the family read access to the wiki with zero hosting maintenance," **Cloudflare Pages + Cloudflare Access** wins on convenience (no VPN client install for non-technical family members, just click an email link) while staying essentially free; **Tailscale/Headscale** wins on privacy/vendor-independence (nothing is ever internet-reachable) at the cost of every family member needing the Tailscale app installed. Given the father/brother are non-technical, **Cloudflare Pages + Access with a custom domain** is the pragmatic default; Tailscale is the fallback if the operator wants zero public exposure of any kind.

## 4. The Company Repo as Wiki and Memory

### AGENTS.md vs CLAUDE.md — the vendor-agnostic instruction layer

- **AGENTS.md** originated as a cross-vendor convention among OpenAI Codex, Amp, Google Jules, Cursor, and Factory teams who wanted one shared "how to work in this repo" file instead of five competing per-tool filenames. It was formalized as an open spec in August 2025 and, in **December 2025, donated to the Linux Foundation's new Agentic AI Foundation** alongside Anthropic's Model Context Protocol and Block's Goose — i.e., by late 2025/2026 it is genuinely vendor-neutral, foundation-governed infrastructure, not any one company's format. By December 2025, 60,000+ open-source projects had adopted it and 20+ coding tools support it. VERIFIED — [morphllm AGENTS.md Guide 2026](https://www.morphllm.com/agents-md-guide)
- **Claude Code specifically does not read AGENTS.md natively** — it reads `CLAUDE.md`, but supports **importing** the shared file with an `@AGENTS.md` reference line inside CLAUDE.md, so the two can coexist without duplication. REPORTED — [gist: Does Claude Code read AGENTS.md?](https://gist.github.com/yurukusa/d36197848911f025add142abefcde685)
- **Practical convention for a vendor-agnostic company repo**: put the portable, harness-independent rules (business rules, coding conventions, architecture) in `AGENTS.md` at repo root, and make `CLAUDE.md` (and any `.cursorrules`, `GEMINI.md`, etc.) a thin pointer/import into it — this repo's own CLAUDE.md is currently the reverse (all content lives directly in CLAUDE.md), which is workable for a Claude-only harness today but would need inversion if a second, non-Anthropic harness (e.g. Codex or an open-source OSS harness like OpenClaw) is added later, per the CLAUDE.md brief's own "vendor-agnostic" goal in this task.

### Claude Code's built-in auto-memory (contrast point, not itself vendor-agnostic)

- Since **v2.1.59 (Feb 26, 2026)**, Claude Code ships **auto memory**, enabled by default: distinct from the CLAUDE.md you write, Claude itself writes notes to `~/.claude/projects/<project>/memory/MEMORY.md` when it discovers a build command, gets corrected, or learns a recurring pattern — but this store is **local to the machine and Claude-Code-specific**, not something an open-source harness (n8n, a raw cron+Python agent, OpenClaw) can read. It's useful context on why a vendor-agnostic company should keep its actual knowledge store in Mem0/Supabase/plain files rather than relying on this. VERIFIED — [Claude Code docs: How Claude remembers your project](https://code.claude.com/docs/en/memory)

### OpenClaw's memory-file convention — the closest OSS analogue to the "wiki as memory" idea

OpenClaw stores **all agent memory as plain Markdown on disk** in the agent's workspace, split into layers:
- `USER.md` — stable operator preferences/relationships/active-project context, loaded every session.
- `MEMORY.md` — durable long-term facts and decisions, loaded every session (this is the closest analogue to CLAUDE.md's "L1 rules always loaded" idea, generalized beyond business rules to accumulated facts).
- Dated daily-note files, `memory/YYYY-MM-DD.md` (or `-<slug>.md`), holding running context/observations for that day — directly analogous to CLAUDE.md's Tier-1 "observations."
There is deliberately **no hidden database, no background process** — "the model only remembers what has been written to those files," which is precisely the vendor-independence property this project's operator wants (any harness pointed at the same folder can read the same knowledge). VERIFIED — [OpenClaw memory concepts docs](https://docs.openclaw.ai/concepts/memory), [Easton: OpenClaw Local Memory System](https://eastondev.com/blog/en/posts/ai/20260205-openclaw-memory-system/)
OpenClaw's team subsequently **extracted and open-sourced this indexing/retrieval layer as a standalone project, "memsearch"** (hybrid full-text + semantic search over a folder of Markdown), which is directly reusable by *any* harness, not just OpenClaw — a good candidate to bolt onto a Habib-OS-style repo if/when the wiki outgrows simple `grep`. VERIFIED — [Milvus blog: We extracted OpenClaw's memory system, memsearch](https://milvus.io/blog/we-extracted-openclaws-memory-system-and-opensourced-it-memsearch.md)

### Suggested folder conventions for a harness-agnostic company repo

Drawing on the OpenClaw/Zettelkasten/AGENTS.md patterns above, a structure any harness (Claude Code, an open-source cron+Python agent, n8n, OpenClaw) can read without special tooling:

```
company-repo/
├── AGENTS.md              # portable instructions (imported by CLAUDE.md, .cursorrules, etc.)
├── L1_RULES.md            # immutable business rules, always loaded (small, <1 page)
├── inbox/                 # unprocessed raw agent outputs, one file per run, dated
│   └── 2026-09-03-inventory-run.md
├── ledgers/               # append-only structured logs (see Section 5) — JSONL/CSV/SQLite
├── dossiers/              # one file per entity: products/sku-017.md, competitors/b0xxx.md
├── playbooks/             # validated, promoted strategies (Tier 3 knowledge)
├── briefs/                # dated daily/weekly briefs, e.g. briefs/2026-09-03.md
└── memory/
    ├── MEMORY.md          # durable cross-cutting facts (OpenClaw-style)
    └── YYYY-MM-DD.md      # daily observation logs (Tier 1)
```
This is structurally identical to CLAUDE.md's own Mem0-backed three-tier model (observations → patterns → playbooks), just expressed as files-on-disk instead of (or in addition to) Postgres+pgvector rows — the two are not mutually exclusive: Mem0/pgvector can remain the *searchable* store while the wiki-compiler job (already planned in CLAUDE.md §10.3) periodically materializes it to this same file layout for harness-agnostic, human-readable access and git history.

### File-size / context limits to design around

- Claude Code's context window is commonly 200K tokens by default (1M-token mode available on Opus 4.6+/Sonnet 4.6+/the Fable-5 family), but **CLAUDE.md itself is loaded in full on every single session start**, so practitioner guidance is to keep it to roughly **200 lines** and push everything else into files loaded on demand (imports, or agent-triggered reads). REPORTED — [Unblocked: Claude Code Context Window 2026](https://getunblocked.com/blog/claude-code-context-window/), REPORTED (200-line guidance) — [glama.ai CLAUDE.md archive discussion](https://glama.ai/mcp/servers/@szeider/consult7/blob/da46e756007b587b2d2b781cd4e414aed1848423/CLAUDE-archive.md)
- Implication for this project: keep `AGENTS.md`/`L1_RULES.md` short and stable; put per-product dossiers, playbooks, and daily observation logs in **separate small files** the agent fetches only when relevant (via its own retrieval step, e.g. grep/ripgrep or a Mem0 query), never concatenated wholesale into the system prompt.

### Search as the wiki grows

- **ripgrep (`rg`)** is the baseline, zero-infrastructure search every harness's shell tool can already use — sufficient for a wiki of low hundreds of files.
- **sqlite-vec**: a SQLite extension adding a native vector type/virtual table (`vec0`) for embeddings directly inside a single `.db` file — brute-force (not ANN), reported as **2-3 orders of magnitude slower than an ANN index like LanceDB's IVF-PQ**, but that's "fine for offline/batch/local-CLI workloads" at this business's scale (tens of products, not millions of vectors), and it keeps the whole vector store as one portable file with no server process. VERIFIED — [shaharia.com: Embeddable Vector DB comparison 2026](https://shaharia.com/blog/choosing-embeddable-vector-database-go-application/)
- **LanceDB** is the better choice once genuine approximate-nearest-neighbor speed matters (larger corpora, sub-second latency requirements) but adds a heavier dependency (pyarrow) than a single SQLite file.
- **sqlite-memory** (sqliteai/sqlite-memory, OSS): purpose-built "Markdown-based AI agent memory with semantic search, hybrid retrieval (vector + FTS5), markdown-aware chunking, offline-first sync between agents" — worth evaluating directly as a drop-in local alternative to Mem0+pgvector if the operator ever wants to decouple the knowledge layer from Supabase entirely. VERIFIED — [GitHub: sqliteai/sqlite-memory](https://github.com/sqliteai/sqlite-memory)
- **Recommendation**: ripgrep is sufficient until the wiki exceeds roughly a few hundred files; at that point, add sqlite-vec (not LanceDB) first, since it needs zero new infrastructure and stays inside the git-friendly single-file philosophy — only move to LanceDB if query latency at that point actually becomes a problem.

## 5. Ledgers and Structured Data Without a Database

### Plain-file ledgers

- **JSONL append logs**: one JSON object per line, append-only. Trivially git-diffable line-by-line, trivially streamed/tailed, trivially parsed by any language in any harness — the natural format for an "observation ledger" (each agent run appends one line) or an audit trail. No schema migration ceremony; a new field just appears in newer lines. Weakness: no query engine natively — needs to be loaded into DuckDB/pandas/jq for anything beyond `grep`/`tail`.
- **CSV snapshots**: good for periodic full-state dumps (e.g. "inventory_snapshot_2026-09-03.csv") that a human or Excel/Numbers can open directly with zero tooling — the most "readable by anyone, including non-technical family members" of all options — but bad for incremental appends (whole-file rewrite) and merge conflicts are essentially unresolvable at the git level beyond "pick one side."
- **SQLite in the repo**: gives real SQL query power in a single portable file, but is **binary and not git-diff-friendly by default** — `git diff` on a `.sqlite` file shows an opaque binary blob. Workarounds exist: git `textconv` filters that pipe the file through `sqlite3 .dump` to produce an SQL-text diff, or dedicated tools like **gitsqlite** (clean/smudge/diff filters storing SQLite as plain-text SQL in git, converting back to binary on checkout) and **git-sqlite**. Even with these, **true concurrent merges of a binary/dump-based SQLite file remain fragile** — acceptable for a solo operator committing sequentially, risky the moment two processes might write and commit in parallel. VERIFIED — [gitsqlite GitHub](https://github.com/danielsiegl/gitsqlite), [ongardie.net: SQLite Database in Git](https://ongardie.net/blog/sqlite-in-git/)
- **DuckDB over CSV/Parquet**: DuckDB is an in-process analytical SQL engine that queries CSV/Parquet files **directly by referencing them in a `FROM` clause** — no import/ETL step, no separate database file to keep in sync with the ledger. This is the best fit for "finance queries without a database": keep `sales_daily.csv`/`profit_daily.parquet` as the source-of-truth ledger files (git-friendly, human-readable in CSV form), and run ad hoc or scheduled DuckDB SQL (`SELECT sku, sum(revenue) FROM 'ledgers/sales/*.csv' GROUP BY sku`) for any analysis — combining git-friendliness with real SQL power, and DuckDB itself needs no server process. VERIFIED — [DuckDB: Querying Parquet Files](https://duckdb.org/docs/lts/guides/file_formats/query_parquet), [DuckDB File Formats guide](https://duckdb.org/docs/current/guides/performance/file_formats)
- **sqlite-utils / csvs-to-sqlite** (Simon Willison's Datasette ecosystem): CLI tools to pipe CSV/JSON/TSV directly into a fresh SQLite file, and to manipulate SQLite databases from the shell — useful glue for converting the append-only JSONL/CSV ledgers above into a queryable SQLite file on demand (regenerated, not hand-edited, so the git-diff problem above is moot — the generated `.db` doesn't need to be committed at all, only the CSV/JSONL sources).
- **Datasette**: point it at a SQLite file (or even a raw CSV/SQL file via "Datasette Lite," which runs entirely client-side via WebAssembly with no server) and get an instant browsable, filterable, API-exposing web UI over the data — a good zero-maintenance way to let the operator (or, cautiously, family) browse the raw ledgers without building a custom dashboard page. VERIFIED — [Datasette docs: Getting started](https://docs.datasette.io/en/stable/getting_started.html), [Datasette Lite](https://datasette.io/)

### When a real Postgres becomes necessary

The plain-file approach (JSONL/CSV + DuckDB) stops being sufficient once any of these hit:
- **Concurrent writers** — more than one process needs to append/update the same ledger at the same time (this project already has this: sync jobs, agents, and the executor all write concurrently — which is exactly why CLAUDE.md already specifies Supabase rather than files for the core operational tables).
- **Row-level access control** needed per viewer (RLS for the dashboard's different user roles) — file-based ledgers have no concept of this.
- **Relational integrity / foreign keys** across many growing tables (orders ↔ order_items ↔ products ↔ inventory) — manageable in flat files up to dozens of files, painful beyond that.
- **Real-time subscriptions** (a dashboard that live-updates) — needs a database with change feeds, not a static file.

### Least-maintenance ways to get a real Postgres (2026 comparison)

| Option | Model | Free tier (2026) | Maintenance | Best for |
|---|---|---|---|---|
| **Supabase** | Postgres + full backend (auth, storage, realtime, pgvector, edge functions) in one dashboard | 500MB storage, 2 projects, weekly pause after inactivity | Lowest for "need auth+DB+vectors+realtime together" | Exactly this project's existing choice — RLS, pgvector for Mem0, and a JS client for the dashboard all in one place |
| **Neon** | Pure serverless Postgres, compute/storage separated, instant branching | 0.5GB storage, 100 projects, no inactivity pause | Lowest for "just need Postgres, nothing else" | If the operator wants Postgres without any of Supabase's other bundled services |
| **Turso (libSQL)** | SQLite fork, edge-replicated, per-user/per-branch databases | 100 databases, 5GB storage, 500M row reads/mo — most generous by volume | Very low; still SQLite semantics (no native pgvector) | A second-brand/per-client SQLite database when Postgres is overkill (see Section 7) |

VERIFIED — [agentdeals.dev Database Free Tier Comparison 2026](https://agentdeals.dev/database-free-tier-comparison-2026), REPORTED (comparative maintenance framing) — [devtoolpicks: Turso vs Neon vs Supabase for Indie Hackers 2026](https://devtoolpicks.com/blog/turso-vs-neon-vs-supabase-indie-hackers-2026)

**Verdict**: this project already made the correct call — Supabase is the right "least-maintenance real Postgres" for a solo operator who also needs pgvector (Mem0), RLS (dashboard), and auth in one place, rather than assembling Neon+a separate vector store+a separate auth provider. For plain historical ledgers that don't need concurrency or RLS (e.g. a monthly finance-snapshot archive), JSONL/CSV in the repo + DuckDB for querying is strictly less operational overhead and should be preferred wherever Supabase's live-write guarantees aren't actually needed.

## 6. Compounding Knowledge

### Provenance as a first-class field, not an afterthought

2026 research on LLM agent memory converges on treating **every memory write as a provenance record**, not just a fact string: "memory writes should carry source and lineage metadata, including source type, timestamp, authoring agent, supporting evidence, transformation operation, confidence, and update history" — mirroring, almost field-for-field, CLAUDE.md's own `metadata` schema (`source_run_id`, `created_date`, `confidence`, `reinforcement_count`, `outcome_validated`). This is a strong external validation that the architecture's existing memory-metadata design is aligned with current best practice, not idiosyncratic. VERIFIED — [arXiv 2606.04990: From Agent Traces to Trust](https://arxiv.org/html/2606.04990)
- The same survey stresses memory quality is not just about recall but about **"source trust, write-path legitimacy, conflict status, contamination risk, and whether a memory is later activated in consequential decisions"** — i.e. a playbook that gets cited in an actual approval/decision should itself be tagged as "activated," creating a feedback loop for evaluating which playbooks are actually load-bearing versus decorative. REPORTED — [arXiv 2606.04990]

### Weekly synthesis pattern (observations → patterns)

- This is exactly the shape CLAUDE.md's `weekly_patterns.py` already implements: pull the week's raw observations + existing patterns, ask an LLM to (a) identify new emerging patterns, (b) reinforce/update existing ones with new evidence, (c) flag patterns *not* reinforced this week as decay candidates. That three-way classification (new / reinforced / decaying) matches the general **consolidation-as-classification** pattern seen in current memory-system writeups, rather than blind re-summarization.

### Decay and pruning

- Mem0's 2026 "AI Memory Confidence Score" work directly names the problem this project must solve: an agent can be **"confidently wrong" as well as confidently right** — a highly-reinforced memory (e.g. "SKU-017 always spikes for Ramadan") can become stale the moment underlying conditions change (a competitor enters, a recipe changes), and nothing in a naive reinforcement-count scheme distinguishes "still true" from "was true." VERIFIED — [Mem0: AI Memory Confidence Score](https://mem0.ai/blog/ai-memory-confidence-score-what-it-is-and-how-it-works)
- Concrete decay mechanisms recommended by current research: **(1) uncertainty quantification** — confidence should decay over time *by default* absent new confirming evidence, not stay static once set; **(2) adversarial probing** — periodically have the consolidation LLM actively try to find counter-evidence against a stored pattern/playbook rather than only looking for confirming evidence; **(3) expiration policies** — auto-retire any pattern that has gone unvalidated/unreinforced for a defined window (e.g. no supporting observation in 90 days demotes a pattern's confidence or archives it). VERIFIED — [arXiv on Always-On Agents, memory decay](https://arxiv.org/pdf/2606.30306) (as summarized in search results)
- **Recommendation for this project**: extend the existing weekly-consolidation job to (a) apply a small automatic confidence decay to every pattern not reinforced in the last N weeks, and (b) have the monthly Opus review explicitly attempt to falsify each existing playbook against the most recent 30 days of outcome data (not only look for confirming evidence) — this operationalizes "adversarial probing" cheaply, once a month, rather than needing a dedicated component.

### Evaluating whether playbooks improved outcomes

- Current practitioner guidance rejects generic public benchmarks (BEAM, LoCoMo, LongMemEval are the standard 2026 memory-recall benchmark trio) as sufficient for a real business — they measure whether an agent *recalls* the right memory, not whether **acting on it produced better outcomes**. The recommended complement is a small, **domain-specific internal evaluation set** ("20-30 golden-path" cases) — for this project, that would be: for each promoted playbook, define what "outcome improved" means in Habib-specific terms (fewer stockouts, lower ACOS, higher margin capture on price moves) and check it against `sales_daily`/`profit_daily`/`ppc_campaign_stats_daily` deltas before vs. after the playbook was first applied. VERIFIED — [Mem0: State of AI Agent Memory 2026](https://mem0.ai/blog/state-of-ai-agent-memory-2026)
- This maps directly onto CLAUDE.md's own monthly-review design (`VALIDATE`/`CONTRADICT`/`INSUFFICIENT` classification against `sales_daily`/`profit_daily`), which is already structurally the right pattern; the addition suggested by 2026 research is to store the **validation verdict itself as a provenance-linked memory** (so a future query can see "playbook X was validated on 2026-05-01 against Y data, confidence raised to 0.92") rather than a one-time confidence update with no audit trail of *why*.

### Practical caution: avoid model-collapse-style self-reinforcement

- A related 2026 concern from LLM-training literature (model collapse: successive generations trained on their own prior outputs progressively lose distributional richness) has an analogue in agent memory — if weekly/monthly consolidation only ever summarizes *previous summaries* rather than periodically re-grounding in raw `sales_daily`/`profit_daily`/`ppc_*` data, patterns can drift into confident-sounding but ungrounded narrative. REPORTED — [arXiv: model collapse discussion in 2026 synthetic-data literature](https://www.digitalapplied.com/blog/synthetic-data-generation-llm-training-decision-guide-2026)
- **Mitigation already implicit in CLAUDE.md's design**: because the monthly review re-reads actual Supabase outcome tables (not just prior Mem0 patterns) as ground truth for validation, the architecture already guards against pure self-referential drift — worth explicitly preserving this "always re-touch raw data, don't just re-summarize summaries" property as the system's memory volume grows.

## 7. Multi-User and Future Agency Use

### Repo-per-brand / repo-per-client scaling

2026 practitioner architecture for scaling an agent-driven system to multiple codebases/clients converges on a **hub-and-spoke pattern**: one canonical **"standards" repo** holding everything genuinely shared (skills, sub-agent definitions, MCP server configs, `AGENTS.md` fragments, linters), pulled into each brand/client repo either as a **git submodule** (pinned to a tag, independently updatable) or a symlinked/packaged skill directory. VERIFIED — [aixsoftware: AI Research — Multi-Repo Agentic Harnesses](https://aixsoftware.substack.com/p/ai-research-multi-repo-agentic-harnesses)
- Concrete mechanics: `git submodule add https://github.com/org/team-skills.git .claude/skills` (or equivalent path per harness) inside each brand repo; the shared repo's skills/prompts/playIooks-templates evolve independently and each brand repo chooses when to bump its submodule pointer, so a prompt fix doesn't retroactively and silently change every client's behavior mid-cycle. VERIFIED — [appsoftware.com: Centralised Approach to AI/LLM Agent Instruction Using Git Submodules](https://www.appsoftware.com/blog/a-centralised-approach-to-ai-llm-agent-instruction-using-git-submodules)
- Known limitation of pure git submodules: "manual setup and constant pulling... scales poorly as your collection grows" — fine at 2-5 brands (this project's realistic near-term horizon per its own §16.2 productization note), likely needing a lightweight package manager or skill-registry approach (as some 2026 tools like Vercel's `skills` package are starting to add) beyond that.
- This maps almost exactly onto CLAUDE.md §16.2's own stated future plan: "Shared: agent code, prompt templates, wiki structure, dashboard UI, Telegram bot framework. Per-client: Supabase project, Mem0 namespace, SP-API credentials, Telegram bot instance, L1 rules." The git-submodule pattern is the concrete implementation mechanism for the "Shared" half of that split that the CLAUDE.md brief leaves unspecified.

### Access control and namespace isolation

- 2026 multi-tenant agent-architecture literature recommends a **mandatory Tenant ID filter on every database query, vector search, and file access** — i.e., every Supabase query and every Mem0 `search()`/`add()` call should be scoped by a `brand_id`/`user_id` namespace, not just conventionally by "which repo you happen to be running in." CLAUDE.md's current single-tenant Mem0 config (`user_id="habib_distribution"`) already models this correctly for one brand — extending to N brands is a matter of parameterizing `user_id` per brand and giving each brand its own Supabase project (as §16.2 already proposes) rather than trying to multiplex several brands inside one Supabase project's rows, which would require careful RLS everywhere writes/reads happen. VERIFIED — [Fastio: Multi-Tenant AI Agent Architecture Design Guide 2026](https://fast.io/resources/ai-agent-multi-tenant-architecture/)
- Recommended layered defense per current practice: **namespace/container isolation for the agent runtime, vector-namespace or separate-database isolation for memory, credential vaulting with per-tenant scopes, and per-tenant rate limiting** — a full one-Supabase-project-per-brand model (as CLAUDE.md already plans) satisfies the memory- and data-isolation layers "for free" simply by virtue of being physically separate projects, which is a stronger and lower-maintenance isolation guarantee than trying to enforce row-level tenant filters correctly across dozens of tables in one shared project. VERIFIED — [Zylos Research: AI Agent Multi-Tenant Architecture 2026](https://zylos.ai/research/2026-05-07-ai-agent-multi-tenant-architecture/)

### Separating credentials per brand

- Concretely: one `.env` per brand repo (or per-brand secret in a shared secrets manager), never a shared `.env` across brands — each brand's SP-API refresh token, Telegram bot token, and Supabase service key must be fully distinct, matching CLAUDE.md's existing single-brand secret-management rules (§13.4) generalized per-repo. A single shared Hetzner VPS can still run all brands' cron jobs/executors/bots as long as each brand's process reads its own brand-specific `.env` (via a distinct `WorkingDirectory`/`EnvironmentFile` per systemd service, exactly the pattern already used for `habib-executor.service` and `habib-telegram.service` — just multiplied per brand).
- For agency-scale isolation beyond "same VPS, separate .envs," the credential-vaulting layer (e.g. per-tenant secrets in a vault rather than flat files) becomes worth adding once managing N `.env` files by hand becomes error-prone — CLAUDE.md's own §16.1 table already flags "Managed Agents... when you onboard first agency client and need per-tenant isolation" as the trigger for exactly this upgrade.

### Summary

| Layer | Repo-per-brand implementation |
|---|---|
| Shared code/skills/prompts | Git submodule from a canonical "standards" repo, pinned per brand, bumped deliberately |
| Data isolation | One Supabase project per brand (physical isolation, not row-level tenant filtering) |
| Knowledge isolation | One Mem0 `user_id` namespace per brand (or, if sharing infra, per-brand vector-store namespace) |
| Credentials | One `.env` per brand repo/systemd service; never shared across brands |
| Compute | Can share one VPS across brands as long as each brand's cron/executor/bot reads only its own `.env` |
| Approval channel | One Telegram bot instance (or chat) per brand/operator, so approvals from different businesses never cross-notify |

## Recommendation

**The approval channel, brief delivery, repo layout, ledger format, and knowledge-compounding routine for a solo operator, vendor-independent:**

1. **Approval channel: Telegram, via python-telegram-bot, long polling (not webhook), with a hard-coded single-chat-ID allowlist.** It is free, has native inline-keyboard buttons, needs no public HTTPS endpoint (long polling works from behind any NAT, unlike a webhook), has zero platform-approval friction (unlike WhatsApp's template review), and carries no ban risk (unlike Baileys). Enforce approver identity purely via Telegram's own numeric chat-ID allowlist plus a DB-side `status='approved'`-only execution gate (defense in depth across bot + executor); add a same-tap-twice "confirm" step for any action above a configurable dollar threshold, and always set an `expires_at` so stale approvals cannot fire later. Signal is the fallback if privacy must trump convenience; Slack/Discord/WhatsApp add no benefit for a single phone-first approver and each carries extra friction (team-oriented UX, bot-vs-webhook complexity, or per-message billing/ban risk respectively).

2. **Brief delivery: short, chunked Telegram push (respecting the 4096-char/message limit, HTML `parse_mode`, link out rather than cram) for the daily headline, plus a full brief rendered as a page in a **MkDocs (Material theme)** static wiki, auto-built and deployed by a GitHub Actions workflow on every push to `main` (triggered by the wiki-compiler consolidation job committing new markdown), hosted on **Cloudflare Pages behind Cloudflare Access** with a custom domain and an email-allowlist policy for the operator, father, and brother (free for up to 50 users, zero server to maintain, zero VPN app to install for non-technical family). Tailscale/Headscale is the fallback if the operator later wants zero public exposure at all.

3. **Repo layout: files-as-memory, OpenClaw/Zettelkasten-style, sitting alongside (not replacing) Supabase+Mem0.** Keep `AGENTS.md` as the portable, harness-agnostic instruction file (imported by `CLAUDE.md`/any other harness's config) and a short, stable `L1_RULES.md`; organize accumulated knowledge as `dossiers/` (one file per product/competitor), `playbooks/` (validated, Tier-3), `memory/MEMORY.md` + dated daily observation files (Tier-1), and `briefs/` (dated). The wiki-compiler job that already exists in CLAUDE.md's plan should materialize Mem0's rows into exactly this file tree on every run — giving every current and future harness (Claude Code, an open-source cron+Python agent, n8n, OpenClaw) the same human-readable, git-diffable, ripgrep-searchable knowledge base, with Mem0/pgvector remaining the live semantic-search index behind it.
