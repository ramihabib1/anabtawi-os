## 1. Claude Code CLI on Claude Max

### 1.1 Headless mode — VERIFIED
Claude Code's `-p`/`--print` flag runs a single non-interactive prompt-in/result-out invocation instead of the REPL. `--output-format` supports `text` (default), `json` (structured result with `session_id`, cost, metadata), and `stream-json` (NDJSON events). Tool access is scoped with `--allowedTools` (e.g. `"Bash(git:*),Read,Edit"`), and other headless-relevant flags include `--permission-mode` (e.g. `acceptEdits`/`bypassPermissions` for unattended runs), `--mcp-config` (load MCP servers from a JSON file), `--agents` (define subagents inline), and hooks configured in `settings.json` for pre/post-tool-use automation. [Headless mode docs](https://cld-docs.onlinetool.cc/en/docs/claude-code/headless.html), [claude-code101 headless tutorial](https://claudecode101.com/en/tutorial/advanced/headless-mode) — REPORTED via secondary docs mirrors (official code.claude.com/docs/en/headless page exists and is referenced throughout code.claude.com/docs/en/authentication, confirming flag names cited there are current).

### 1.2 Claude Agent SDK auth — VERIFIED, this is the single most important constraint
The Claude Agent SDK (Python and TypeScript) is a *developer* product and per Anthropic's own Claude Code legal/compliance page, developers building on the Agent SDK **must use API-key authentication** — subscription (OAuth) credentials are explicitly out of scope for it:

> "Developers building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication through Claude Console or a supported cloud provider. Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users."
— [code.claude.com/docs/en/legal-and-compliance](https://code.claude.com/docs/en/legal-and-compliance) (VERIFIED, official)

A closed, unanswered GitHub feature request confirms the community has asked Anthropic to allow Max-plan billing in the SDK and Anthropic has not granted it: [anthropics/claude-agent-sdk-python#559](https://github.com/anthropics/claude-agent-sdk-python/issues/559) (VERIFIED as to issue content/status; REPORTED as to it being closed without an official resolution comment visible).

**Practical implication for this project**: `core/anthropic_client.py`/agent code built directly against the Agent SDK or the raw `anthropic` Python package cannot legitimately run on Claude Max — it must use `ANTHROPIC_API_KEY` billing. This applies to Habib OS's existing agents as designed in the CLAUDE.md (they use the Anthropic Python SDK directly, not the CLI) — **that architecture is, and must remain, API-key billed for Claude.** The Claude Max subscription can only legitimately drive the *Claude Code CLI binary itself*, run unmodified.

### 1.3 What running the actual Claude Code CLI headless, unattended, on your own machine is allowed to do — VERIFIED
The same legal-and-compliance page draws a real distinction between the SDK/third-party-harness case above and simply running the unmodified `claude` binary with your own subscription:

> "Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription..."
> "This does not restrict how customers provision and manage their own API keys or third-party inference provider credentials — for example, configuring an API key in a development environment, secrets manager, or machine image for use by the customer's own authorized users — provided the resulting usage is billed to the key owner..."
— [code.claude.com/docs/en/legal-and-compliance](https://code.claude.com/docs/en/legal-and-compliance)

The CI/automation path is explicit and documented, not a workaround: `claude setup-token` mints a **one-year OAuth token** printed once to the terminal; exporting it as `CLAUDE_CODE_OAUTH_TOKEN` authenticates headless/CI invocations of the *CLI* against the caller's Pro/Max/Team/Enterprise subscription. Anthropic's own docs state: "This token authenticates with your Claude subscription and requires a Pro, Max, Team, or Enterprise plan. It can only make model requests, so it can't establish Remote Control sessions or fetch claude.ai connectors. MCP servers you configure locally still work." — [code.claude.com/docs/en/authentication](https://code.claude.com/docs/en/authentication) (VERIFIED, official, current as of Sept 2026).

Caveats found in the same doc:
- `CLAUDE_CODE_OAUTH_TOKEN` is **not** read in `--bare` mode (bare mode needs `ANTHROPIC_API_KEY` or `apiKeyHelper`).
- Authentication precedence: cloud-provider creds > `ANTHROPIC_AUTH_TOKEN` > `ANTHROPIC_API_KEY` > `apiKeyHelper` > `CLAUDE_CODE_OAUTH_TOKEN` > Anthropic profile/federation > `/login` subscription OAuth. **A stray `ANTHROPIC_API_KEY` in the environment silently overrides the subscription token and bills API credits instead** — this is a documented footgun, not folklore.
- One gray zone: the Usage Policy section states "Advertised usage limits for Pro and Max plans assume **ordinary, individual usage** of Claude Code and the Agent SDK" and "Anthropic reserves the right to take measures to enforce these restrictions and may do so without prior notice." Running 8 unattended department agents daily via cron, on a single human's Max subscription, is not explicitly named as prohibited, but it is a volume/automation pattern well outside "ordinary individual interactive use," and Anthropic reserves unilateral enforcement discretion. **UNKNOWN / gray area**: whether sustained daily multi-agent cron automation at business-operations scale would be judged "ordinary" if it drew scrutiny, versus merely being throttled by usage limits.

### 1.4 Routines (Anthropic's own scheduler) — VERIFIED, in research preview
Anthropic ships first-party scheduled automation called **Routines** (`/schedule` in the CLI, or claude.ai/code/routines on the web), explicitly built for exactly this use case ("Put Claude Code on autopilot... run on a schedule... react to GitHub events"). Key facts, all from [code.claude.com/docs/en/routines](https://code.claude.com/docs/en/routines) (VERIFIED, official, marked "research preview — behavior, limits, and API surface may change"):
- Available on **Pro, Max, Team, and Enterprise plans** — this is the sanctioned subscription automation path, not the SDK.
- Triggers: **Scheduled** (hourly/daily/weekly/one-off, min interval 1 hour), **API** (POST to a per-routine `/fire` endpoint with a bearer token — good for chaining departments or firing from an external orchestrator), and **GitHub** (PR/release events).
- Runs execute on **Anthropic-managed cloud infrastructure** (or a self-hosted environment if configured) — i.e. NOT on the Hetzner box; this is a materially different architecture from the CLAUDE.md's local-cron design.
- Runs autonomously with **no permission-mode picker and no approval prompts** — everything a routine's connectors/repo access allow, it can do without a human in the loop during the run. This conflicts directly with Habib OS's "no financial action without human approval" invariant unless routines are scoped read-only/advisory and a separate approval step (e.g. Telegram) still gates writes.
- **"Routines draw down subscription usage the same way interactive sessions do"** and carry an additional **daily cap on runs per account**, shown at claude.ai/code/routines. Exceeding the daily cap or subscription usage limit blocks further routine runs unless metered "usage credits" (overage billing) are enabled — which reintroduces pay-per-use billing.
- Requires **claude.ai subscription login** specifically — Console API keys and cloud-provider auth explicitly cannot use `/schedule` ("`/schedule` requires a claude.ai subscription login... API accounts aren't supported for routines").
- Alternative **Desktop scheduled tasks** exist for routines that must run against local files on your own machine rather than Anthropic's cloud (`/docs/en/desktop-scheduled-tasks`), and `/loop` for in-session local scheduling — both closer in spirit to the always-on-Hetzner-box model in CLAUDE.md, at the cost of requiring the desktop app/session to stay resident.

### 1.5 Usage limits — Max 5x / 20x — REPORTED (numbers vary by source; no single official numeric table found)
Every paid plan meters usage on two axes: a **5-hour rolling session window** and a **weekly cap across all models** (plus, per multiple secondary sources, a **second, narrower weekly cap for Sonnet-class models specifically**). Max 5x delivers roughly 5x Pro's per-session allowance; Max 20x roughly 20x. One tracking source cites "at least 225 messages/5h on Max 5x, at least 900 messages/5h on Max 20x" for short conversations, explicitly caveated as varying with message/conversation length and capacity — REPORTED, not from an official numeric table. Another source states 5-hour windows were doubled as of ~May 2026 with no peak-hour reduction on Pro/Max — REPORTED, unconfirmed against a primary Anthropic page (support.anthropic.com was unreachable from this research environment; egress-blocked). **UNKNOWN**: exact current token/message ceilings for Max 20x as of September 2026; Anthropic does not publish precise token numbers, by design, because consumption depends on model, context size, and caching.

**Operational implication**: agentic work with heavy tool use (MCP calls, file reads, multi-turn reasoning) consumes 5-hour and weekly budgets far faster than chat messages. Eight department agents × 30–60 min of agentic work each, run daily, is a plausible candidate for hitting the **weekly** cap even on Max 20x, especially if the same account is also used for interactive coding work during the day (see Section 7 for a capacity model).

### 1.6 The OpenCode/OpenClaw enforcement action — VERIFIED (dated) + REPORTED (detail/motivation)
- **Jan 9, 2026**: Anthropic deployed **server-side technical enforcement** blocking consumer-subscription OAuth tokens from working in any client other than Claude Code / Claude.ai. Third-party tools (OpenCode, OpenClaw, and the Agent SDK when used outside Claude Code) began receiving: `"This credential is only authorized for use with Claude Code and cannot be used for other API requests."` — REPORTED, corroborated across multiple independent outlets (GIGAZINE, abit.ee, ZBuild, aihackers.net, openclaw.rocks) citing the same date and error string; could not independently verify the exact date against a primary Anthropic changelog from this environment (blocked domains), so treated as REPORTED rather than VERIFIED despite consistency across sources.
- **Feb 19–20, 2026**: Anthropic **updated its documentation** (the legal-and-compliance page quoted in §1.2/1.3 above) to formally codify the policy in writing — this is the page still live and quoted verbatim above, so the *current wording* is VERIFIED even though the historical timeline is REPORTED.
- Community reaction was sharp: Ruby on Rails creator David Heinemeier Hansson (DHH) publicly accused Anthropic of "intentionally blocking OpenCode, and any other 3P harness, in a paranoid attempt to force devs into Claude Code" — REPORTED (his statement, not Anthropic's).
- **Net effect for this project**: OpenCode, Goose, Crush, or any other third-party harness **cannot** legitimately authenticate with a Claude Pro/Max OAuth token as of September 2026 — confirmed both by the technical block (REPORTED) and the current official policy text (VERIFIED). Any department agent built on a non-Anthropic harness must use a Claude **API key** if it needs Claude at all, or use a different subscription model provider entirely (Codex/ChatGPT, Grok, Gemini — see Sections 2–4).

## 2. OpenAI Codex CLI

### 2.1 Overview and licensing — VERIFIED
Codex CLI (github.com/openai/codex) is OpenAI's open-source, Apache-2.0-licensed terminal coding agent (101K+ GitHub stars as of research date), first released April 2025. It runs locally on the operator's machine and, unlike Claude Code, is fully open source top to bottom. [github.com/openai/codex](https://github.com/openai/codex) — VERIFIED (repo exists, Apache-2.0 confirmed by README per search excerpt).

### 2.2 Headless mode — VERIFIED (via developers.openai.com docs, confirmed through search excerpts; direct fetch blocked by egress proxy)
`codex exec` is the documented non-interactive entry point: it runs a prompt end-to-end without the TUI and streams results to stdout, optionally as JSON Lines with `codex exec --json`. The JSONL stream emits typed events (`thread.started`, `turn.started`, `turn.completed`, `turn.failed`, plus `item.*` events for agent messages, reasoning, shell command execution, file changes, MCP tool calls, web searches, and plan updates) — a structurally similar but not identical contract to Claude Code's `--output-format json`. Sessions can be resumed. Login for headless/SSH environments is supported via `codex login --device-auth`. Source: [developers.openai.com/codex/noninteractive](https://developers.openai.com/codex/noninteractive), [developers.openai.com/codex/cli/reference](https://developers.openai.com/codex/cli/reference) — content confirmed via search snippets; the domain itself is blocked from direct fetch in this research environment, so treat exact flag names as REPORTED-via-search-cache rather than freshly verified against live docs, though multiple independent secondary sources (computingforgeeks.com, shipyard.build, deployhq.com) corroborate the same command surface.

### 2.3 MCP and AGENTS.md — VERIFIED/REPORTED
Codex CLI supports MCP servers with parallel tool calls (official docs), and honors `AGENTS.md` files for project-level context/instructions, in the same spirit as Claude Code's `CLAUDE.md`. One notable hardening change: "untrusted projects no longer supply project-level AGENTS.md instructions" as of a recent update — i.e. Codex added a trust boundary so an arbitrary cloned repo's AGENTS.md can't silently inject instructions into an agent run unless the project is explicitly trusted. This is directly relevant to a multi-department setup where department repos/configs might not all be equally trusted. REPORTED via search snippet of official changelog; not independently re-verified against developers.openai.com/codex/changelog due to egress block.

Community MCP bridges exist to expose `codex exec` itself as an MCP tool callable from other harnesses (e.g. `codex-mcp`, `codex-as-mcp` on GitHub), meaning Codex can act as a subordinate tool inside a Claude Code or other orchestrator's tool graph — useful for a mixed-provider department design (see Section 6/7). REPORTED (community projects, unofficial).

### 2.4 ChatGPT plan sign-in and usage limits — REPORTED (numbers fluctuate; OpenAI has changed policy multiple times in 2026)
Codex CLI can authenticate with a ChatGPT account (Plus, Pro, Business/Work, Team, Enterprise) instead of an API key — "sign in with ChatGPT" links usage to the subscription's Codex allowance rather than metered API billing. As with Claude, usage is metered on a **5-hour rolling window** plus a **separate weekly cap**.

2026 has seen OpenAI flip this limit on and off for Plus:
- OpenAI **reinstated a 5-hour usage limit for Codex and ChatGPT Work on Plus subscribers starting August 25, 2026**, having apparently relaxed or suspended it earlier in the year — [9to5Mac, Aug 24 2026](https://9to5mac.com/2026/08/24/openai-restores-5-hour-codex-and-work-limits-for-chatgpt-plus-users/) (REPORTED, credible tech press).
- Pro tiers ($100/mo "Pro" and $200/mo "Pro 20x"-equivalent) get roughly **5x and 20x the Plus per-window allowance** respectively, and multiple secondary trackers state Pro tiers have had the strict 5-hour gate turned off "for the upcoming months," i.e. a softer/rolling limit rather than a hard 5-hour wall — REPORTED, e.g. [explainx.ai](https://www.explainx.ai/blog/codex-plus-5-hour-limit-returns-chatgpt-work-august-2026), [simplemetrics.xyz](https://simplemetrics.xyz/chatgpt-codex-limits-2026/).
- Concrete usage-range figures reported for Plus on the GPT-5.6 model family: roughly 15–90 "Sol"-tier requests, 20–110 "Terra"-tier, 50–280 "Luna"-tier per 5 hours (naming scheme per whoburnedmore.com's tracking) — REPORTED, unofficial third-party tracking site, treat as illustrative not authoritative.
- `/status` inside Codex CLI, or the usage panel in ChatGPT/Codex settings, is the documented way to check remaining quota. REPORTED via search snippet of official docs reference.
- **UNKNOWN**: an exact, current, official numeric table of weekly Codex-CLI hours per plan as of September 2026 — OpenAI, like Anthropic, does not appear to publish one; third-party trackers exist specifically because the official docs don't give hard numbers.

### 2.5 Model options — REPORTED
Search results reference **GPT-5.6** and **GPT-5.5** as the current Codex-tuned model family in the ChatGPT Codex product as of the research window, alongside historical references to "GPT-5.1-codex." No official model-name table was retrievable from developers.openai.com directly (egress-blocked); model naming in OpenAI's Codex product has changed multiple times in 2026, so any specific model ID from earlier in the year (e.g. GPT-5.1-codex, GPT-5.2-codex) should be treated as potentially superseded. **UNKNOWN**: definitive current default model as of Sept 3, 2026.

### 2.6 Automation/scheduled-use policy — REPORTED, more permissive in spirit than Anthropic's stance but with real limits
No OpenAI policy page explicitly says "you may not run Codex CLI in cron." The general Service Terms prohibit "automatically or programmatically extracting data" (aimed at scraping, not agent automation), prohibit **sharing account credentials**, and prohibit **reselling access or using ChatGPT to power third-party services** — [openai.com/policies/service-terms](https://openai.com/policies/service-terms/) (REPORTED — page exists and search snippet quotes this language; not independently refetched due to egress block). The "power third-party services" clause is the one to watch: a solo operator running Codex CLI, signed into their own ChatGPT plan, to run their own internal department agents for their own business is very plausibly "ordinary use of your own account for your own purposes," not "powering a third-party service" (that clause targets reselling ChatGPT access to other paying customers). This reading is REPORTED-as-inferred, not confirmed by an explicit OpenAI carve-out — there is no equivalent to Anthropic's Routines page that names scheduled/automated Codex use as an officially sanctioned pattern. OpenAI's help center confirms Codex sign-in shares ChatGPT ToS/Privacy Policy, and that "guardrails... may occasionally involve a temporary restriction on your usage" for suspected misuse, with notification — [help.openai.com/en/articles/11369540](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan) (REPORTED via search snippet; egress-blocked for direct refetch).

**Net assessment**: Codex CLI on a ChatGPT Plus/Pro plan is **less explicitly sanctioned for scheduled automation than Claude Code's Routines**, but also **less explicitly and technically blocked than third-party Claude harnesses**. There is no known equivalent of Anthropic's January 2026 server-side OAuth lockout for Codex CLI as of this research date. It sits in a documented-but-unendorsed middle ground: technically works headless via `codex exec` + ChatGPT login, not against a literal ToS clause found in this research, but automated multi-department cron use has not been explicitly blessed by OpenAI the way Routines has been blessed by Anthropic.

## 3. Grok Build CLI / Grok Code (xAI)

### 3.1 What it is — REPORTED (consistent across many secondary sources; docs.x.ai itself was not directly fetchable — egress-blocked)
**Grok Build** is xAI's terminal-native agentic coding CLI, opened in beta May 14, 2026 to SuperGrok Heavy subscribers, reaching a "1.0"/general-availability milestone around **August 7, 2026**, and **open-sourced under Apache-2.0** in mid-July 2026 (see §3.4). It runs on a dedicated coding model (`grok-build-0.1`, later `grok-4.6`/"Grok 4.3 beta" depending on source and date) inside a 16-agent "Heavy" architecture, offering up to **8 parallel sub-agents in separate git worktrees**, a **2-million-token context window**, and a "Plan Mode" that shows an execution plan for approval before code changes are made. Sources: [pasqualepillitteri.it](https://pasqualepillitteri.it/en/news/2584/grok-build-xai-cli-2026), [digitalapplied.com](https://www.digitalapplied.com/blog/xai-grok-build-cli-parallel-coding-agents), [codersera.com](https://codersera.com/blog/xai-grok-build-skills-connectors-guide-2026/).

### 3.2 Subscription gating and cost — REPORTED, tiers changed multiple times in 2026
Reported access tiers, with some inconsistency across sources (a sign the offer changed during the year):
- **SuperGrok** ($30/mo) and **X Premium+** ($40/mo) — reported by some sources as sufficient for baseline Grok Build access.
- **SuperGrok Heavy** ($299/mo full price; a promotional **"SuperHeavy" tier at $99/mo for the first six months**) — the tier the initial May 2026 beta was gated behind, and still cited by other sources as the requirement for the full 8-parallel-agent experience.
- API-key billing is also available directly against console.x.ai for headless/CI use (`GROK_CODE_XAI_API_KEY`), at a published rate around **$0.20 per million input tokens** for the `grok-build-0.1` model — REPORTED, [buildfastwithai.com](https://www.buildfastwithai.com/blogs/grok-build-xai-cli-ai-agents-2026).
**UNKNOWN**: the precise, current (Sept 2026) minimum paid tier for full headless automation use of Grok Build, since reporting is inconsistent between "$30 SuperGrok is enough" and "$299 SuperGrok Heavy required" — this should be verified directly against docs.x.ai/build/overview (blocked in this research environment) or console.x.ai before committing a department to it.

### 3.3 Headless mode, MCP, AGENTS.md/Claude Code compatibility — REPORTED
- Headless/CI operation: for headless or CI use, set `GROK_CODE_XAI_API_KEY="xai-..."` (an API key, not subscription credential, for this path) and use the documented `-p` flag for non-interactive prompts, analogous to Claude Code's `-p`. REPORTED, [codersera.com](https://codersera.com/blog/how-to-install-grok-build-cli-2026/).
- **Native MCP support**, plus a notable interoperability claim from xAI's own docs (per search snippet): "Grok is fully compatible with Claude Code with zero configuration needed" — it auto-discovers Claude Code marketplaces, plugins, skills, MCP servers, subagents, hooks, and instruction files (i.e. it reads `CLAUDE.md`/`.claude/` configuration natively). If accurate, this materially reduces department-charter porting cost between Claude Code and Grok Build specifically. REPORTED via search snippet purportedly quoting docs.x.ai; not independently confirmed by direct fetch.
- **AGENTS.md, plugins, hooks, and skills "work out of the box"** per the same sourcing — suggesting Grok Build has adopted (or is compatible with) both the AGENTS.md convention and something resembling Anthropic's Agent Skills format. REPORTED, unverified against primary docs.
- **ACP (Agent Client Protocol, Zed's standard) support** is claimed for "bots and orchestration." REPORTED.

### 3.4 Reliability and — critically — a security incident — VERIFIED via multiple independent press outlets, treat as REPORTED/high-confidence
This is the single most important finding for a business deployment holding financial/inventory/customer data:

**In July 2026, security researcher "cereblab" used `mitmproxy` to inspect Grok Build's network traffic and found it silently uploaded far more data than a coding task required.** Concretely reported:
- A task that needed **~192 KB** of context to answer resulted in **5.10 GiB** uploaded to an xAI-controlled Google Cloud Storage bucket (`grok-code-session-traces`) — roughly a **27,800x** overshoot.
- The upload included the **full git repository, including commit history** (i.e. previously-deleted files/secrets still in history were exposed), and **`.env` files with credentials were transmitted unredacted**.
- A "privacy toggle" in Grok Build's settings **did not prevent** the uploads.
- xAI's response: a **server-side kill-switch** to stop the uploads, followed by **open-sourcing Grok Build under Apache-2.0** on **July 15, 2026** as a transparency/damage-control move — but researchers who reviewed the published source confirmed **the exfiltration code path is still present**, merely gated off by the same remote server-side flag (i.e. not structurally removed, and re-enable-able without a client update).

Sources (multiple independent outlets corroborating the same researcher and figures): [thinaer.io](https://thinaer.io/blog/ai-data-leakage-what-the-grok-build-leak-actually-proves/), [developersdigest.tech](https://www.developersdigest.tech/blog/grok-build-open-source-damage-control), [manojsm.com](https://www.manojsm.com/blog/xai-grok-build-cli-git-repo-upload-leak-2026/), [xploitwire.com](https://xploitwire.com/article/grok-build-exfiltration-when-ai-tools-overreach-their-access), [techtimes.com](https://www.techtimes.com/articles/320671/20260716/grok-build-open-sourced-after-covert-upload-code-exfiltrate-repos-stays.html), [qpulse.quasarcybertech.com](https://qpulse.quasarcybertech.com/news/4668/xai-grok-build-cli-exfiltrated-full-git-repositories-to-cloud-storage). Given six-plus independent outlets citing the same researcher, numbers, and bucket name, this is treated as **REPORTED at high confidence** — not officially confirmed by an Anthropic-style compliance page from xAI itself, but far too consistently corroborated to dismiss.

**Direct relevance to Habib OS**: this repo's own `.env` holds Supabase service keys, Anthropic/OpenAI keys, SP-API refresh tokens, and Telegram bot tokens. A CLI with a demonstrated history of exfiltrating full repos including `.env` contents — even if patched server-side — is a materially higher supply-chain/data-exposure risk than Claude Code or Codex CLI for any department agent with filesystem access to this codebase, regardless of subscription vs. API billing. This is a **hard blocker for trust, not just a cost/quota question**, until xAI provides a verifiable, audited fix (structural code removal, not a remote flag) and a public post-mortem.

### 3.5 Other reliability reports — REPORTED
- A CLI hanging bug: Grok Build "sometimes gets stuck indefinitely on 'Waiting' or 'Responding' even when a turn is completed," requiring a full app quit rather than Ctrl-C to recover — relevant to unattended cron use, since a hung process can silently block a scheduled slot rather than fail cleanly. [x.com/techdevnotes](https://x.com/techdevnotes/status/2063631051390378197) (single-source social-media report, REPORTED at lower confidence).
- Reasoning on complex multi-step logic is described as "shaky," with missed edge cases, per hands-on reviews after 50+ hours of use. REPORTED, [composio.dev summary via search snippet].
- Terminal-only at time of most reviews; GUI/IDE support was slated for Q3 2026. REPORTED.

**Net assessment for Habib OS**: Grok Build is technically capable (MCP, Claude Code compatibility, headless mode) and its SuperGrok subscription tier is one the client already pays for, but the July 2026 exfiltration incident and unresolved hang bug make it the **weakest choice by trust/reliability** among the four major providers surveyed here for a business system handling supplier data, financials, and API credentials, until there's a verified, code-level fix and a track record post-incident. It may still be usable for a low-sensitivity, low-blast-radius department (e.g. a read-only competitor-price-scanning agent that never touches `.env` or Supabase service keys) if the operator is comfortable with the residual risk.

## 4. Gemini CLI — IMPORTANT: effectively deprecated for individual accounts as of June 18, 2026

### 4.1 What Gemini CLI was, and what happened to it — VERIFIED (via official GitHub docs) + REPORTED (via press, consistent across 7+ outlets)
`github.com/google-gemini/gemini-cli` is Google's open-source terminal AI agent. Its own quota/pricing doc (fetched directly, VERIFIED) states free-tier limits as:
- **Personal Google account (Gemini Code Assist for Individuals)**: 1,000 model requests/user/day, spanning the Gemini model family.
- **Unpaid API key**: 250 requests/user/day, **Flash model only**.
- **Gemini Code Assist Standard** (Workspace): 1,500 requests/user/day.
- **Gemini Code Assist Enterprise** (Workspace/Cloud): 2,000 requests/user/day.
[github.com/google-gemini/gemini-cli/blob/main/docs/resources/quota-and-pricing.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/resources/quota-and-pricing.md) — VERIFIED, official, fetched directly.

**However**, at Google I/O on **May 19, 2026**, Google announced it was consolidating developer tooling under a new brand, **Antigravity**, and retiring the standalone Gemini CLI for individual users. On **June 18, 2026**, Gemini CLI **stopped serving requests entirely** for: free/unpaid users, **Google AI Pro** subscribers, and **Google AI Ultra** subscribers — with **no grace period**. Multiple sources state plainly that "any script, cron job, GitHub workflow, or pipeline that called the `gemini` command on an affected tier... stopped working on June 18, 2026." REPORTED, corroborated by [The Register](https://www.theregister.com/ai-ml/2026/05/20/bye-bye-gemini-cli-google-nudges-devs-toward-antigravity/5243605), [inventivehq.com](https://inventivehq.com/blog/gemini-cli-deprecated-antigravity-cli-migration), [digitalapplied.com](https://www.digitalapplied.com/blog/gemini-cli-to-antigravity-cli-migration-june-18-2026-guide), [aibuilderclub.com](https://www.aibuilderclub.com/blog/google-kills-gemini-cli-june-18-2026), [The New Stack](https://thenewstack.io/google-antigravity-cli/).

**The one carve-out**: organizations on **Gemini Code Assist Standard or Enterprise** licenses (Workspace/Cloud-billed, not individual consumer subscriptions) kept their Gemini CLI access unchanged. REPORTED, [inventivehq.com migration guide].

**Direct relevance**: the CLAUDE.md research brief names `github.com/google-gemini/gemini-cli` as a research target, and it is a reasonable free-tier fallback in principle — but **as of September 2026, individual-account Gemini CLI as historically known is dead**. The client cannot rely on it via a personal Google AI Pro/Ultra subscription; that path was shut off with zero warning window three months ago. Any Gemini-based department must move to **Antigravity CLI** (see §4.2) or a Workspace/Cloud-billed Code Assist Standard/Enterprise seat, which is a materially different cost/commitment shape than "log in with a personal Google account."

### 4.2 Antigravity CLI (the replacement) — REPORTED
Antigravity CLI (binary `agy`) is Google's Go-based successor, positioned as faster and built for **asynchronous, multi-agent background workflows** — actually a better structural fit for scheduled department agents than the old Gemini CLI was. Key reported facts:
- **Not open source** — "Antigravity CLI isn't open source, at least not from what Google has published," a notable regression from Gemini CLI's Apache-2.0 openness. REPORTED, [inventivehq.com].
- **Headless mode exists**, rendering tool calls/edits/reasoning as structured rows rather than scraped terminal text; separate documentation covers custom auth providers and air-gapped enterprise installs for CI/CD. REPORTED, [continuumcode.ai].
- **MCP support** was added in early 2026, letting agents call external tools/services (GitHub, databases, APIs) — REPORTED.
- **Usage limits refresh every 5 hours**, same rolling-window shape as Claude/Codex. Reported guidance: the **$19.99/mo "AI Pro"** tier is realistically too constrained for serious agentic runs ("quota walls will interrupt serious agent runs"), while the **$100/mo "AI Ultra"** tier is described as "the realistic working threshold for multi-agent parallel workflows." REPORTED, [vibecoding.app / buildfastwithai.com summaries].
- Google separately announced **raised Antigravity rate limits specifically for AI Pro/Ultra subscribers** later in 2026 — REPORTED, [blog.google/feed/new-antigravity-rate-limits-pro-ultra-subsribers].

**UNKNOWN**: whether Antigravity CLI's terms explicitly permit unattended cron/scheduled automation the way Claude Code's Routines do, or explicitly forbid it — no primary Google terms page on this was retrievable in this research pass (developers.googleblog.com and docs.cloud.google.com were reachable for the Code Assist quota page but a specific Antigravity ToS/AUP page addressing automation was not located).

### 4.3 Practical assessment for this project
Gemini/Antigravity is the **least suitable of the four majors for this specific engagement** as scoped: the client's paid stack is Claude Max, ChatGPT, and SuperGrok — **not** a Google AI Pro/Ultra or Workspace Code Assist seat. Standing up a Gemini-family department would mean (a) adopting Antigravity CLI, a closed-source tool with an unstable ~14-month track record of the underlying CLI product itself being deprecated and replaced, and (b) paying for a fourth subscription (~$20–100/mo) the client doesn't already hold. If cost/redundancy ever justifies a fourth provider, Antigravity's $100/mo AI Ultra tier is the one worth piloting — the free/Pro tiers are both explicitly reported as inadequate for agentic workloads and, in Gemini CLI's case, no longer even reachable for individuals.

## 5. Multi-Provider Open-Source Harnesses

### 5.1 OpenCode (sst/opencode, now anomalyco/opencode) — subscription auth broken by Anthropic, REPORTED with a confusing/conflicting timeline across sources
OpenCode is an open-source, provider-agnostic terminal agent (formerly under `sst/opencode`, now tracked at `anomalyco/opencode` per GitHub issue URLs found). It historically supported logging in directly with a Claude Pro/Max **or** ChatGPT subscription, alongside dozens of API-key-based providers — this was its main differentiator versus Claude Code.

**Timeline as reported (dates conflict across sources — flagged explicitly)**:
- **Jan 9, 2026**: Anthropic silently deployed a server-side check causing OpenCode's stored Claude Pro/Max OAuth tokens to fail with `"This credential is only authorized for use with Claude Code and cannot be used for other API requests."` Reported as reversed shortly after community backlash. [dev.to/mcrolly](https://dev.to/mcrolly/anthropic-kills-claude-subscription-access-for-third-party-tools-like-openclaw-what-it-means-for-3ipc).
- **Feb 19, 2026**: Anthropic formalized the restriction into an updated "Authentication and credential use" ToS section (this is the section still live today, quoted verbatim in §1.2–1.3 above) — REPORTED as to date, VERIFIED as to current wording.
- **March 19, 2026**: An OpenCode maintainer merged a PR titled "anthropic legal requests" that **removed the Anthropic OAuth plugin, Claude system prompt, and all Claude Pro/Max auth code from the OpenCode codebase itself** — i.e. OpenCode's own maintainers pulled the feature rather than fight it. REPORTED, [ridakaddir.com](https://ridakaddir.com/blog/post/did-anthropic-kill-opencode-claude-subscription-ban).
- **April 4, 2026, 12:00 PM PT**: A separate/later source states this is when Anthropic's block on Claude Pro/Max subscription access for third-party tools took full effect, announced less than 24 hours earlier by Boris Cherny (head of Claude Code at Anthropic) — REPORTED, [KERSAI](https://kersai.com/anthropic-killed-third-party-claude-access-heres-every-workaround-that-still-works/).
- Live GitHub issues from the OpenCode fork as recently referenced show developers still hitting `429`s and OAuth callback failures trying to use Claude Pro/Max login, e.g. [anomalyco/opencode#18362](https://github.com/anomalyco/opencode/issues/18362), [#18329](https://github.com/anomalyco/opencode/issues/18329) — confirming the login path is unreliable/non-functional in practice, independent of the exact enforcement date.

**Bottom line (VERIFIED at the policy level via code.claude.com, REPORTED at the historical-timeline level)**: as of September 2026, **OpenCode cannot use a Claude Pro/Max subscription**. It still works with a Claude **API key** (pay-per-token), and — per general reporting — is unaffected for OpenAI/ChatGPT-style third-party auth in the same way, though ChatGPT login support in OpenCode was reportedly also narrower than advertised at various points in 2026 (not independently confirmed here). OpenCode remains a legitimate multi-provider harness for **API-key-billed** work across Anthropic, OpenAI, and other providers, and for **local/open-weight models**, but it cannot serve as a "run department agents on the Claude Max subscription" solution.

### 5.2 Goose (Block → Agentic AI Foundation / Linux Foundation) — VERIFIED-adjacent, strong MCP-native fit, BYOK only
- **Governance change**: in early 2026, Goose's governance moved from Block into the **Agentic AI Foundation under the Linux Foundation**; the GitHub repo now redirects `block/goose` → `aaif-goose/goose`. REPORTED, [blog.marcnuri.com](https://blog.marcnuri.com/goose-on-machine-ai-agent-cli-introduction).
- **License**: Apache-2.0, free, open source — "no required Goose subscription just to install." REPORTED, [theaiagentindex.com](https://theaiagentindex.com/agents/goose).
- **Provider model is BYOK (bring your own key) only**: Goose supports Claude, OpenAI, Gemini, local Ollama models, and 30+ others through its provider system, but always via **API keys**, not subscription OAuth logins — REPORTED, no source claims a Claude Max or ChatGPT Plus login path for Goose. This makes Goose's cost model strictly pay-per-token for any hosted model, i.e. it cannot draw down the client's existing Max/ChatGPT/SuperGrok subscriptions at all; it needs API keys and API billing regardless of provider.
- **MCP-native**: MCP is described as Goose's "primary extension model," shipping 70+ built-in extensions with 1,700+ community MCP servers available. REPORTED, [developersdigest.tech](https://www.developersdigest.tech/blog/github-trending-goose-2026-06-07).
- **Headless + scheduling**: the CLI runs the same "Recipe" concept headlessly as the desktop app's chat view, with configurable approval gates for multi-step tasks — a built-in approval-gate primitive that maps naturally onto Habib OS's "no financial action without approval" invariant. REPORTED, [vibecodinghub.org](https://vibecodinghub.org/blog/goose-review).
- **53.7k GitHub stars, 500+ contributors** as of Q3 2026 — REPORTED, indicates a maturing, credibly maintained project, not experimental.

**Bottom line**: Goose is technically the best-fitting open harness for a portable, MCP-native, approval-gated multi-department design — but it is **API-key billed only**, so it does not reduce cost versus using each provider's own CLI on a subscription; it only adds portability/uniformity at the cost of giving up subscription billing entirely for whichever model backs it.

### 5.3 Crush (Charmbracelet) — REPORTED
Crush is Charm's terminal agentic coding tool, TUI-based, supporting multiple LLM providers via API key (Anthropic, OpenAI, Gemini, etc.) plus MCP servers over three transports (stdio, http, sse). ## 6. Standards That Keep Departments Portable Across Harnesses

### 6.1 AGENTS.md — REPORTED, widely adopted, project-scoped
AGENTS.md is a plain-Markdown, project-root convention for giving any agent CLI the context it needs about a codebase/project — build commands, conventions, do's and don'ts. It is analogous to (and in Anthropic's own ecosystem, largely interchangeable in spirit with) `CLAUDE.md`. It is described as "project-scoped context," distinct from portable, reusable Agent Skills (§6.2). Codex CLI, Claude Code (which will read a repo's `AGENTS.md` in addition to `CLAUDE.md` in many setups), Grok Build, and most others in this survey read it. REPORTED across multiple sources cited in §2–3.

### 6.2 Agent Skills / SKILL.md — VERIFIED as an open standard, REPORTED on adoption breadth
Anthropic opened its `SKILL.md` **Agent Skills** format as a public, vendor-neutral standard on **December 18, 2025**: a directory containing a `SKILL.md` file with YAML frontmatter plus Markdown instructions, using a three-tier progressive-disclosure loading architecture (skills are indexed cheaply, then loaded in full only when relevant — directly comparable to how this session's own skill listing works). It is now stewarded at **agentskills.io**, open to ecosystem contribution rather than solely Anthropic-controlled. [The New Stack](https://thenewstack.io/agent-skills-anthropics-next-bid-to-define-ai-standards/), [paperclipped.de](https://www.paperclipped.de/en/blog/agent-skills-open-standard-interoperability/) — REPORTED, consistent across sources.

**Adoption, as of March 2026** (~12 weeks after release): reportedly **32 tools** support the spec, explicitly including **Claude Code, OpenAI's Codex CLI and ChatGPT, Microsoft VS Code/GitHub Copilot, Google's Gemini CLI, JetBrains Junie, AWS Kiro, Block's Goose, Sourcegraph's Amp, Snowflake, Databricks, ByteDance TRAE, and Mistral AI.** REPORTED, [agentman.ai ecosystem report](https://agentman.ai/blog/agent-skills-ecosystem-report-2026), [anomity.ai governance analysis](https://anomity.ai/blog/agent-skills-open-standard-adoption-governance/). Grok Build's documentation (per §3.3) separately claims "skills... work out of the box," suggesting xAI has also adopted or is compatible with the format, though this wasn't in the explicit 32-tool list found.

**Practical implication for Habib OS**: a department's operating procedure (e.g. "how to calculate FBA days-of-supply and what counts as a critical threshold," or "how to format a PPC approval request") is best captured as a `SKILL.md` package rather than baked into agent Python code or a single provider's system prompt — that package is now genuinely portable across Claude Code, Codex CLI, and (per vendor claims) Grok Build, and via Goose too.

### 6.3 MCP (Model Context Protocol) — VERIFIED as widely deployed, REPORTED on scale figures
MCP is the mature, dominant standard for connecting an agent to external tools/data (Supabase, SP-API wrappers, Telegram, etc.). Its latest spec is dated **November 25, 2025**. As of April 2026, reporting describes MCP as having "critical mass" with **10,000+ servers** and universal tool support across essentially every harness surveyed in this report (Claude Code, Codex CLI, Grok Build, Gemini/Antigravity, OpenCode, Goose, Crush, Cline). [morphllm.com](https://www.morphllm.com/comparisons/acp-vs-mcp-vs-a2a). This is the one standard in this survey that is unambiguously safe to build a multi-department architecture on today, regardless of which CLI ends up running each department.

### 6.4 A2A (Agent-to-Agent Protocol) — REPORTED, newer, cross-organization framing
A2A reached **v1.0 in April 2026** and is reportedly backed by **150+ organizations**. It defines how independent agents discover each other and exchange tasks/results as peers across framework and organizational boundaries — the "phone line" in one source's power-strip/desk/phone-line analogy (MCP = tools, ACP = editor workspace, A2A = inter-agent coordination). REPORTED, [digitalapplied.com protocol map](https://www.digitalapplied.com/blog/ai-agent-protocol-ecosystem-map-2026-mcp-a2a-acp-ucp). For an 8-department single-operator system, A2A is likely **premature** — it's built for coordinating agents across different companies/vendors, not for one operator's own departments talking to each other through a shared Supabase database, which the existing CLAUDE.md architecture already handles more simply ("No agent-to-agent communication. Each agent is independent; they share state via Supabase only" — a design choice this research validates rather than contradicts).

### 6.5 ACP (Agent Client Protocol, Zed) — REPORTED, editor-integration-focused, likely irrelevant here
Created by Zed in August 2025, ACP connects agents to code editors (25+ agents reportedly support it) so any ACP-compliant agent can plug into any ACP-compliant editor UI. Note there are **two different things both abbreviated ACP** in current usage: Zed's Agent Client Protocol (editor integration) and IBM's Agent Communication Protocol (an internal agent message bus, closer in purpose to A2A). Grok Build's marketing claims "full ACP support for bots and orchestration" (§3.3) without specifying which ACP it means — worth clarifying before relying on it. Since Habib OS's department agents are batch/cron processes with no interactive editor surface, **ACP (either flavor) is not directly relevant** to this project.

### 6.6 What a department charter should look like to run unchanged across Claude Code, Codex, Goose, and OpenCode
Based on the standards above, a portable department definition should separate into layers that map cleanly onto each harness's own primitives:

1. **Business logic and procedure → `SKILL.md`.** Each department's playbook (e.g. "Inventory Agent playbook") as an Agent Skill package: YAML frontmatter (name, description, when-to-trigger) plus Markdown procedure. This is the layer with the broadest confirmed cross-tool support (32 tools as of March 2026).
2. **Project/environment context → `AGENTS.md`** (mirrored as `CLAUDE.md` where a tool prefers that name — Claude Code reads both patterns in practice) — repo layout, how to run things, coding conventions, L1 business rules that must always load.
3. **Tool access → MCP servers**, declared in a portable `.mcp.json` wherever a harness supports project-scoped MCP config (Claude Code does; confirm per-tool for Codex/Grok/Goose) — this is what lets a Supabase-query tool or an SP-API-read tool be reused unchanged across harnesses.
4. **Orchestration/scheduling stays outside the standard entirely** — this is the part that does **not** port. Claude Code's Routines, Codex's own scheduling story (weaker/DIY via cron + `codex exec`), and Goose's Recipes each have their own trigger/scheduling model. The safest portable design is what CLAUDE.md's own architecture already does: **keep scheduling as plain cron invoking each CLI headlessly**, and never depend on a vendor's hosted scheduler (Routines) for logic that must be provider-agnostic. Anthropic Routines execute on Anthropic's cloud with no approval gate during the run (§1.4) — a second reason to keep the trigger layer local and cron-based rather than migrating to it wholesale.
5. **The approval gate is bespoke, not standardized.** None of MCP/AGENTS.md/Agent Skills/A2A/ACP define a human-approval primitive equivalent to Habib OS's `approval_requests` table + Telegram flow. That invariant must continue to be enforced in the application layer (Supabase + Executor), identically regardless of which CLI produces the recommendation — which is exactly how CLAUDE.md already designs it. This is the correct design and should not change even as the underlying agent runtime becomes multi-provider.

## 7. Cost and Capacity Model

### 7.1 The workload
8 departments × 1 run/day × ~30–60 minutes of agentic work (multi-turn reasoning + MCP tool calls against Supabase/SP-API/Telegram-equivalents). A 30–60 min agentic session with tool use is not a handful of chat messages — it's realistically **tens of tool-call round trips**, each carrying growing conversation history unless context is actively managed. As a rough per-run estimate for planning purposes (own estimate, not sourced — **UNKNOWN/estimated**): a single 45-minute department run with 20–40 tool calls and a few thousand words of Supabase data injected per turn plausibly consumes **150K–500K total tokens** (input+output combined, uncached) at typical CLI verbosity, before any prompt-caching savings. Across 8 departments/day that is roughly **1.2M–4M tokens/day**, or **8M–28M tokens/week**.

### 7.3 Subscription capacity risk assessment

**Claude Max 20x**: Per §1.5, Max 20x offers roughly 20x Pro's 5-hour session allowance plus a separate weekly cap (with a narrower Sonnet-specific sub-cap reported by some trackers). Running 8 agentic sessions of 30–60 minutes each, sequentially per CLAUDE.md's own design ("Sequential agent runs... to avoid resource contention"), means the account accumulates **4–8 hours of continuous agentic tool-calling per day** on a single subscription. Even spread across a full day, this is very plausibly enough to **exhaust the weekly cap** well before the week resets, especially since:
- The same human (Rami) may also want to use Claude Code interactively during the day for actual development work on this same account, competing for the same weekly budget.
- Anthropic's own "ordinary, individual usage" framing (§1.3) suggests this volume is already outside the intended envelope, which raises both a capacity risk and a policy-posture risk simultaneously.
- Routines (§1.4) explicitly state "Routines draw down subscription usage the same way interactive sessions do" plus an *additional* per-account daily run cap — so moving to Routines does not sidestep the weekly ceiling, it adds a second ceiling on top.
**Verdict**: Claude Max 20x alone is **very likely insufficient** to run all 8 departments' full daily agentic workload every day of the week without hitting caps, especially in a week that also includes real interactive coding sessions. It's a reasonably comfortable fit for **2–4 lighter-weight departments** run once daily, not all 8.

**ChatGPT Pro ($200/mo tier)**: Per §2.4, Pro tiers reportedly have the strict 5-hour gate loosened/removed "for the upcoming months," which if still true in September 2026 gives more headroom for long, bursty department runs than a hard-walled 5-hour session model — but a weekly cap almost certainly still exists in some form, and OpenAI does not publish exact numbers either. **Verdict**: plausibly the single most elastic subscription in the mix today for absorbing multiple long department runs, but this is REPORTED and could change (OpenAI already flipped the Plus 5-hour limit on/off once in 2026); treat as a working assumption to be validated with real usage telemetry (`/status`) in week one, not a guarantee.

**SuperGrok / SuperGrok Heavy**: Given the unresolved trust issue in §3.4 (data exfiltration to xAI cloud storage, patched only by a remote flag, not structurally removed) and the reported hang bug, this is not a tier to be capacity-planned around for financial/inventory-sensitive department work regardless of how generous its quota is. If used at all, restrict to a low-sensitivity department and treat any capacity headroom as a bonus, not a load-bearing part of the plan.

**Gemini/Antigravity**: Not part of the client's existing subscription stack (§4.3); excluded from the primary allocation.

### 7.4 A mixed-provider allocation that respects both trust and capacity

Given the above, a defensible allocation of 8 departments across the three subscriptions the client already pays for:

| Departments (illustrative) | Backend | Billing | Rationale |
|---|---|---|---|
| 2–3 highest-value, most sensitive (Inventory, Financial/Pricing, PPC — i.e. anything that produces `approval_requests`) | **Claude Code CLI**, `CLAUDE_CODE_OAUTH_TOKEN` on Max | Max subscription, watched against weekly cap | Best-documented approval-adjacent tooling, most mature MCP ecosystem, Anthropic's own Routines infrastructure exists as an upgrade path later; keep these few so they fit inside the weekly cap even with interactive dev use on the same account |
| 2–3 medium-sensitivity, read/analysis-heavy (Competitor Intel, Listing Health, Reviews) | **Codex CLI**, ChatGPT login | ChatGPT Plus/Pro subscription | Spreads load off the Claude account; Pro's looser 5-hour gate (as reported) suits longer analysis runs; keep away from any workflow that must produce a `price_change` or `ppc_bid_change` approval unless the operator is comfortable duplicating Claude's role there |
| 1–2 low-sensitivity, no-credential, ideally read-only (general web/competitor price scanning, public review scraping) | **Grok Build CLI**, SuperGrok subscription, with `.env`/secrets excluded from its working directory | SuperGrok subscription | Isolate Grok Build in its own working directory with no access to Supabase service keys, SP-API tokens, or `.env` — mitigates the exfiltration risk in §3.4 while still using the subscription the client already pays for |
| Consolidation / weekly & monthly review (cross-department synthesis) | **Claude API key (Sonnet 5 weekly / Opus 5 monthly)**, not subscription | Metered API billing | This work already sits outside "ordinary Claude Code usage" in nature (batch synthesis across all departments' data) and the Agent-SDK-vs-CLI distinction in §1.2 makes API billing the *only* compliant path if this logic is coded directly against the Anthropic SDK, as CLAUDE.md already designs it — the API-key requirement for the Agent SDK is not a capacity workaround, it's the only permitted authentication mode for that code path |

This spreads load across three independently-capped subscription pools rather than concentrating 8 hours/day of agentic work on one Max account, reduces the odds of any single weekly cap being the failure point, and keeps the least-trustworthy tool (Grok Build) away from the system's most sensitive data by construction rather than by policy alone.

### 7.5 Minimum API-key fallback needed
Regardless of allocation, plan for a **metered API fallback on at least the Anthropic side**, because:
1. The Agent-SDK/consolidation code path (§7.4 row 4) *requires* an API key by policy — this is not optional infrastructure, it's mandatory for the CLAUDE.md architecture as designed today (`anthropic` Python SDK, not Claude Code CLI).
2. When a subscription's weekly cap is hit mid-day, the only way to keep that day's remaining department runs on schedule is a same-provider API key as overflow (Anthropic's own "usage credits" overage billing serves this role for Routines/Max — §1.4 — but is off by default and re-introduces metered billing anyway).
3. Any Anthropic Agent-SDK-based code Habib OS already runs (the existing three department agents per CLAUDE.md) is *already* API-key billed today, independent of anything in this report — that spend is a fixed cost, not a variable one contingent on subscription headroom.

**Practical minimum**: keep one funded `ANTHROPIC_API_KEY` (Console) sized for the existing 3 agents' documented ~$15–40/month (CLAUDE.md §15) plus headroom for whichever new departments get built directly against the Agent SDK/Anthropic Python SDK rather than the Claude Code CLI, and treat that as the non-negotiable floor spend regardless of how well the Max/ChatGPT/SuperGrok subscriptions cover CLI-driven departments.

## Recommendation

**Which CLIs can legitimately serve as department backends on subscriptions:**
- **Claude Code CLI** (not the Agent SDK) — YES, on Claude Max, via `claude -p` headless invocations authenticated with `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`), or via first-party **Routines** (`/schedule`) if you accept cloud execution and no in-run approval gate. This is Anthropic's own documented, sanctioned pattern (VERIFIED, §1.3–1.4), not a workaround. Constraint: watch the weekly cap; don't run all 8 departments here.
- **Codex CLI** — YES, on a ChatGPT Plus/Pro/Business login via `codex exec`, in a documented-but-not-explicitly-endorsed gray zone that is nonetheless far less restricted than Anthropic's third-party stance (no known technical block, no explicit ToS clause against scheduled personal use). Good second pool for medium-sensitivity, analysis-heavy departments.
- **Grok Build CLI** — CONDITIONALLY YES, on SuperGrok, for low-sensitivity/no-credential departments only, until xAI structurally fixes and independently verifies the July 2026 data-exfiltration issue (§3.4). Do not point it at this repo's `.env`, Supabase service keys, or SP-API tokens.
- **Gemini CLI (individual)** — NO, as of Sept 2026 it is shut off for personal Google AI Pro/Ultra accounts (§4.1); would require adopting closed-source Antigravity CLI and a subscription the client doesn't currently hold.

**Which cannot:**
- **Any third-party harness with a Claude Pro/Max login** (OpenCode chief among them) — technically blocked and explicitly prohibited by Anthropic policy since H1 2026 (§1.6, §5.1).
- **The Claude Agent SDK / raw Anthropic Python SDK on a Max subscription** — explicitly requires API-key billing per Anthropic's own compliance page (§1.2); this includes Habib OS's *existing* three agents as architected in CLAUDE.md.
- **Goose, Crush, Aider, Cline, Qwen Code, Kimi CLI, Amp** — none can spend a Claude Max/ChatGPT/SuperGrok subscription; all are BYOK/API-key or run on their own separate subscription/credit products (§5.10).

**How to allocate departments across providers**: put your 2–3 most sensitive, approval-producing departments (inventory, pricing, PPC) on Claude Code CLI/Max; 2–3 medium-sensitivity analysis departments on Codex CLI/ChatGPT; 1–2 low-sensitivity, credential-free departments on Grok Build/SuperGrok; and run cross-department weekly/monthly consolidation on the Anthropic API key regardless, since that logic is Agent-SDK-shaped by design and is not eligible for subscription billing in the first place. This spreads the weekly-cap risk across three independently-metered pools instead of concentrating ~4-8 hours/day of agentic work on one account, and it keeps the least-trusted tool away from the system's credentials by construction.

**Minimum API-key fallback needed**: a funded `ANTHROPIC_API_KEY` sized for at least the existing agents' ~$15-40/month (per CLAUDE.md's own cost model) plus headroom for any new department built directly against the Agent SDK — this is not optional, it is the only permitted auth mode for that code path, and it also serves as overflow capacity when a CLI's subscription weekly cap is hit mid-day. Standing up equivalent small API-key budgets for OpenAI and xAI as a second-tier fallback (a few dollars/month of headroom) is cheap insurance against the same weekly-cap risk on those subscriptions once real usage telemetry comes in from week one.
