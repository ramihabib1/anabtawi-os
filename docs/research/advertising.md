## 1. The Official Amazon Ads MCP Server (Open Beta since Feb 2, 2026)

### What it is
Amazon Ads launched the Amazon Ads MCP Server into open beta on **February 2, 2026**. It is a standards-based translation layer, hosted by Amazon, that converts natural-language prompts from any MCP-compatible agent (Claude, ChatGPT, Gemini, Amazon Q, or a custom agent) into structured Amazon Ads API calls, executes them against the advertiser's live account, and returns results in the conversation. **VERIFIED** (multiple independent secondary sources agree on date/mechanism: [Amazon Ads Newsroom](https://advertising.amazon.com/library/news/amazon-ads-mcp-server-open-beta), [AdExchanger](https://www.adexchanger.com/marketers/amazon-ads-opens-a-beta-test-for-its-new-mcp-server/), [Digiday](https://digiday.com/media-buying/ad-tech-briefing-amazon-launches-mcp-server-for-agent-driven-advertising/), [Marketing Dive](https://www.marketingdive.com/news/amazon-enables-communication-between-ads-platform-and-ai-agents/811566/), [eMarketer](https://www.emarketer.com/content/amazon-s-mcp-server-could-give-larger-foothold-ad-tech-space); the primary Amazon page itself could not be fetched directly from this environment — egress to advertising.amazon.com is blocked — so its exact wording is REPORTED via secondary citation, not independently confirmed word-for-word).

### Tool list
Reported at **50+ tools** spanning Sponsored Products, Sponsored Brands, Sponsored Display, DSP, and Amazon Marketing Cloud (AMC), organized under prefixes: `cp_` (campaigns), `sp_` (Sponsored Products), `dsp_` (DSP), `amc_` (AMC workflows/queries), `ac_` (account/profile). **REPORTED** ([Digiday](https://digiday.com/media-buying/ad-tech-briefing-amazon-launches-mcp-server-for-agent-driven-advertising/), corroborated by [Futurum Group](https://futurumgroup.com/insights/amazon-ads-mcp-server-debuts-streamlining-ai-managed-campaign-execution/)).

Capability categories described consistently across sources:
- **Campaign lifecycle**: create/update/delete campaigns, ad groups, keywords, product targets, negatives — end-to-end Sponsored Products campaign creation from a single prompt. **REPORTED**
- **Bids & budgets**: bid and budget adjustments via natural language. **REPORTED**
- **Reporting**: performance reports and "query with plain English" reporting tools; search-term-level reporting implied under Sponsored Products reporting but no source enumerates a distinct "search-term report" tool by name. **REPORTED / UNKNOWN at tool-name granularity**
- **AMC**: AMC workflow/query tools (`amc_` prefix) — but AMC access requires a provisioned AMC instance, an entitlement most sub-$50K/mo advertisers won't have. **REPORTED** ([sentrykit.com via search synthesis](https://sentrykit.com/blog/amazon-ads-mcp-server-sellers/))
- **DSP**: DSP tools exist (`dsp_` prefix) but DSP API approval separately requires ~$50K+ annual ad spend and a 1-2 week approval process, gating most small brands out. **REPORTED**
- **Billing/financial data**: access to billing and financial data is explicitly called out in Amazon's own framing. **REPORTED** ([Digiday](https://digiday.com/media-buying/ad-tech-briefing-amazon-launches-mcp-server-for-agent-driven-advertising/))
- **Account settings / international expansion**: a dedicated "expand campaign to another marketplace" tool is highlighted as a flagship use case (e.g., expand a US+Canada campaign to a new country with one prompt). **REPORTED**

No source seen in this research enumerated the full 50+ tool names verbatim (Amazon's own API docs page, which would presumably list every tool, was not fetchable from this environment). **UNKNOWN**: exact complete tool manifest.

### Third-party/community MCP servers (not the official Amazon one)
Multiple independent, non-Amazon MCP servers targeting Amazon Ads also exist and are easy to confuse with the official one:
- `marketplaceadpros/amazon-ads-mcp-server` (GitHub) — directly fetched and read. Covers campaigns/ad groups/keywords/product ads/targeting for SP/SB/SD, plain-English reporting, and paid "Recommendations"/"Experiments" features gated behind a MarketplaceAdPros subscription. Auth is a single `BEARER_TOKEN` obtained from MarketplaceAdPros.com (i.e., it proxies through their SaaS, not raw Ads API credentials). Supports local npm/stdio, HTTP streaming, or LibreChat deployment. Marketplace coverage and rate limits are undocumented in the README. **VERIFIED** (fetched directly: [github.com/marketplaceadpros/amazon-ads-mcp-server](https://github.com/marketplaceadpros/amazon-ads-mcp-server))
- `ppcprophet/amazon-ads-mcp`, `Imsamiullah09/amazon-ads-mcp`, `amekala/adspirer-mcp-server` (aka "Amazon Advertising MCP Server" on PulseMCP), `KuudoAI/amazon_ads_mcp` — independent open-source implementations wrapping the Amazon Ads API directly (BYO Ads API credentials), rather than Amazon's own hosted server. **REPORTED** (existence confirmed via GitHub/PulseMCP/Glama.ai search listings; not deep-audited individually).
- Sellermetrics.app, Adzviser, Marketplace Ad Pros, and agentcentral.to publish Claude-specific setup guides/wrappers around either the official or a third-party server. **REPORTED**

For a solo-operator agent, this is an important distinction: "Amazon Ads MCP server" in casual usage may refer to Amazon's own hosted beta, or to any of several unofficial community/SaaS wrappers with very different auth, cost, and trust models.

### Authentication and access level
- Base requirement: an **active Amazon Ads API credential set** — a Login with Amazon (LWA) security profile registered in the Amazon Developer Console, used to obtain a refresh token for the Ads API. Approval of the LWA profile for Ads API access is reported to take **1–3 business days**. **REPORTED** ([Sellermetrics.app guide, via search synthesis](https://sellermetrics.app/amazon-ads-mcp-with-claude/))
- Any seller or agency with such credentials can use the MCP server itself — no separate MCP-specific approval gate beyond having working Ads API access. **REPORTED**
- Elevated features are gated by *existing* Ads API entitlement tiers, not something the MCP server changes: **AMC** tools need a provisioned AMC instance; **DSP** tools need DSP API approval, reported to require **>$50K/year ad spend** and a **1–2 week** separate approval process. For a $2K–10K/month brand (~$24K–120K/year), DSP access is a stretch goal at the low end and plausible only near the top of that range. **REPORTED**

### Marketplace / region coverage
No source found gives an explicit marketplace allow-list for the MCP server. Because it is a translation layer over the existing Ads API (which already supports Amazon.ca alongside Amazon.com under the North America region), and Amazon's own promotional example explicitly describes expanding a **US + Canada** campaign to a new country via the MCP server, **Canada is implicitly covered**. **REPORTED**, not explicitly documented; **UNKNOWN** whether any tools are US-only in the beta.

### Rate limits
No official published numbers were retrievable (Amazon's docs page was not fetchable from this environment). One third-party implementation exposes a configurable `AMAZON_ADS_RATE_LIMIT_RPS` environment variable, implying the *underlying* Ads API's standard rate limits apply and the MCP layer just proxies them with its own client-side throttle knob. **REPORTED** ([search synthesis referencing glama.ai-hosted server env vars](https://glama.ai/mcp/servers/@foxglovebrands/geenie-proxy/blob/3faa8f210046d79a3bcd3b0c8f3e206611b41995/.env.example)). **UNKNOWN**: official Amazon-stated RPS/quota for the hosted MCP server itself.

### Known bugs / limitations reported by sellers and agencies
- **Reporting latency / async gaps**: report-pull requests can sit pending; some report generation takes ~10–15 minutes even though simple campaign creation is reported to complete in seconds. **REPORTED**
- **Access is gated to the already-large advertisers**: "most advertisers spending under $50,000/month don't have direct API access," which the MCP server does not change — it inherits the Ads API's existing developer-approval gate, making it "effectively inaccessible to the majority of Amazon sellers and many mid-sized brands." This is a significant caveat for a $2K-10K/month brand: **the operator needs to already qualify for Ads API developer access, independent of MCP.** **REPORTED** ([search synthesis citing ClearAds Agency / sentrykit.com](https://clearadsagency.com/what-is-amazons-mcp-server-and-how-does-it-change-advertising-for-sellers/))
- **Narrow data window / no cross-domain awareness**: the MCP only sees advertising data. It does not know inventory levels (so it can't tell you that scaling a campaign is wrong three weeks before a stockout), doesn't know landed cost or FBA fees (so it can compute ACOS but not true post-fee margin), and lacks Buy Box status. This directly matters for Habib Distribution OS: **the Amazon Ads MCP cannot replace the Inventory Agent's Supabase-based margin/stockout data — it must be combined with, not substituted for, the existing inventory and profit_daily tables.** **REPORTED** ([sentrykit.com "Here's What It Can't See"](https://sentrykit.com/blog/amazon-ads-mcp-server-sellers/))
- **Agent behavior risk in internal testing**: Amazon's own internal testing reportedly showed agents taking inefficient or risky paths — e.g., pulling excessive AMC data (cost risk) or calling deprecated API endpoints. This is a direct argument for guardrails (spend/change caps) regardless of Amazon's own tool design. **REPORTED**
- **Non-trivial implementation cost even with MCP**: estimated at 40-80 developer hours for initial integration plus 5-10 hours/month maintenance, i.e., MCP reduces but does not eliminate integration effort. **REPORTED**
- **Ecosystem positioning**: Digiday frames Amazon's MCP approach as a comparatively closed, single-platform ecosystem, in contrast to cross-platform initiatives like AdCP (Ad Context Protocol) that aim to unify multiple ad platforms behind one protocol — relevant if Habib later adds Walmart Connect or other channels behind one agent interface. **REPORTED**

### How to connect to Claude
- **Claude Desktop, claude.ai (web connectors), and Claude Code (CLI)** all support MCP servers natively; guides describe a roughly 10-minute, no-code connection process (register/confirm Ads API credentials → point the MCP client config at Amazon's hosted MCP endpoint or a third-party wrapper → authorize). **REPORTED** ([sellerlabs.com "10-Minute Setup Guide"](https://www.sellerlabs.com/blog/connect-claude-to-amazon-seller-account/), [marketplaceadpros.com "Amazon Ads in Claude — Desktop, Code & Cowork Setup"](https://marketplaceadpros.com/amazon-ads-claude/))
- Amazon **hosts the MCP server infrastructure itself** on behalf of advertisers, and states it will be natively integrated into Amazon's own campaign management tools, while still allowing advertisers to "bring their own" LLM/agent (i.e., Claude via MCP is an intended, sanctioned pattern, not a workaround). **REPORTED**
- For **Managed Agents** (Anthropic's hosted multi-tenant agent product, relevant to Habib's own future productization plan in CLAUDE.md §16.2): no source found describes Amazon Ads MCP-specific guidance for Managed Agents deployment. **UNKNOWN**.

## 2. Amazon's Own "Ads Agent" (unBoxed Nov 2025) and Seller Assistant

### Ads Agent
Announced at Amazon Ads **unBoxed 2025** (November 2025), **Ads Agent** is Amazon's own in-console AI assistant — not an MCP server, not something a third-party agent connects to. It is a conversational experience baked into the Amazon Ads UI. **REPORTED** ([Amazon Ads: "Boost advertising efficiency with Ads Agent"](https://advertising.amazon.com/resources/whats-new/unboxed-2025-introducing-ads-agent), [Amazon Ads: "Simplify campaign targeting with the help of Ads Agent"](https://advertising.amazon.com/resources/whats-new/unboxed-2025-campaign-targeting-with-ads-agent), [Amazon Ads: "Accelerate Amazon Marketing Cloud workflows with Ads Agent (beta)"](https://advertising.amazon.com/resources/whats-new/unboxed-2025-ads-agent-in-amazon-marketing-cloud))

What it does:
- **Natural-language targeting**: describe targeting intent in plain English or upload a campaign brief document; Ads Agent suggests relevant Amazon audience segments and keywords, replacing manual targeting research. **REPORTED**
- **Pacing at scale**: automates budget pacing adjustments across hundreds of campaigns. **REPORTED**
- **AMC analytics via natural language**: generates SQL queries for Amazon Marketing Cloud (both audience-building SQL and, per the unBoxed AMC-specific announcement, analytics SQL) from plain-English questions — a meaningful accessibility win since AMC natively requires hand-written SQL. **REPORTED**
- **Transparency/control**: summarizes proposed changes before acting; requires review/approval before changes are made — i.e., human-in-the-loop by default at launch. **REPORTED**
- **Availability at launch**: limited to specific console surfaces — Amazon Marketing Cloud and Multimedia Solutions with Amazon DSP — not a general campaign-management copilot across the whole console at launch. **REPORTED**

A related unBoxed announcement, **Creative Agent**, is a separate conversational tool inside Creative Studio for generating multimedia ad assets (scripts, images, multi-scene video with voice-over and licensed music, performance predictions) from prompts — creative generation, not bid/budget/targeting management. **REPORTED** ([Amazon Ads: "Transform campaign and asset development with Creative Agent"](https://advertising.amazon.com/resources/whats-new/unboxed-2025-creative-agent), [WinBuzzer](https://winbuzzer.com/2025/09/17/amazon-unveils-agentic-ai-to-automate-ad-creation-for-millions-of-sellers-xcxwbn/))

### Seller Assistant
Distinct from Ads Agent, **Seller Assistant** is Amazon's broader agentic AI layer for independent sellers (announced separately, per aboutamazon.com), covering account health, inventory, and business-growth actions beyond advertising — e.g., autonomously coordinating inventory orders, drafting growth plans, fixing account issues, with human approval required for most actions at launch and a stated rollout of **auto-approve mode for routine tasks in Q2 2026**. **REPORTED** ([About Amazon: "Amazon unveils new agentic AI-powered Seller Assistant"](https://www.aboutamazon.com/news/innovation-at-amazon/seller-assistant-agentic-ai))

### Complement or conflict with the MCP server / Claude-based agent?
Sources are unanimous: **complementary, not conflicting**. The framing repeated across secondary sources: *"If Ads Agent is Amazon's in-house AI assistant, the MCP Server is the door Amazon opened so that third-party AI tools can walk in."* Ads Agent operates **inside** Amazon's own console UI on Amazon's own reasoning; the MCP Server is the **API-level doorway** that lets an external agent (Claude, in Habib's case) read/write the same underlying account programmatically, outside the console. There is no functional overlap that would cause the two to fight over the same action — Ads Agent isn't reachable by Claude at all; it's a human-facing UI feature. **REPORTED** ([search synthesis citing Autron.ai](https://autron.ai/blog/amazon-ppc-automation-in-2026-what-the-ads-agent-and-mcp-server-mean-for-sellers), [Marketing Dive](https://www.marketingdive.com/news/amazon-enables-communication-between-ads-platform-and-ai-agents/811566/))

**Implication for Habib Distribution OS**: Ads Agent is not a tool Rami's Claude-based PPC Agent can call — it's a parallel, human-operated convenience inside Amazon's own console that Rami (or father/brother) could optionally use by hand. It does not change the architecture; the PPC Agent still needs its own MCP/API access. Ads Agent's natural-language AMC SQL generation is worth knowing about as a manual fallback for ad-hoc deep-dive questions Rami might ask directly in Amazon's console, separate from the automated Claude agent pipeline.

## 3. Amazon Ads API Beyond the MCP — Marketing Stream, Reports v3, Brand Metrics; the "Thin Wrapper" Option

### Amazon Marketing Stream
A push-based (not pull/poll) delivery mechanism for near-real-time Ads data. Delivers **hourly** performance-metric updates (traffic and conversion, dimensioned by placement and hour of day) plus **as-they-happen** campaign-change event notifications, for Sponsored Products, Sponsored Brands, Sponsored Display, and Amazon DSP. Delivery is via AWS services — **SQS** or **Amazon Data Firehose** — so the advertiser owns the downstream storage/pipeline. Reduces reporting latency from the traditional next-day-or-later batch reports down to minutes, useful for same-day underspend/overspend and promo-period monitoring. Access is available to "agencies, tech providers, and direct advertisers integrated with the Amazon Ads API" — i.e., gated behind the same base Ads API developer access as everything else, not a separate approval tier. **REPORTED** ([Amazon Ads: "A complete guide to Amazon Marketing Stream"](https://advertising.amazon.com/library/guides/amazon-marketing-stream), [AWS: "Unlock real-time advertising insights with Amazon Marketing Stream and AWS"](https://aws.amazon.com/blogs/industries/unlock-real-time-advertising-insights-with-amazon-marketing-stream-and-aws))

For Habib: Marketing Stream is **not exposed as an MCP tool** (it's an AWS-native push pipeline, not a request/response API a chat agent would call turn-by-turn) — it would require its own always-on AWS ingestion component (SQS consumer or Firehose→S3/Supabase sync job), architecturally similar to the existing `sync/` layer in CLAUDE.md rather than something the Claude PPC Agent calls directly. Given the Hetzner CX22 / solo-operator constraint and the fact that daily-batch Reports v3 data already satisfies the existing 06:00 UTC PPC Agent cadence, Marketing Stream is a **future consideration**, not a v1 need — it would matter more once dayparting/promo-day monitoring requires sub-daily reaction time.

### Reports API (v3) and Brand Metrics API
- **Sponsored ads reporting API v3** is the standard batch reporting endpoint (campaign/ad group/keyword/search-term/placement-level performance, async report generation + download) — this is almost certainly what the MCP server's "reporting" tools wrap under the hood. **REPORTED** ([Amazon Ads: "Sponsored ads reporting FAQ (version 3)"](https://advertising.amazon.com/API/docs/en-us/guides/reporting/v3/faq))
- **Brand Metrics API** (open beta) is a separate, brand-level reporting endpoint returning metrics by `categoryNodeTreeName`/`categoryNodePath`/`brandName` over a date range or lookback period, in CSV or JSON — brand-share/competitive-visibility style metrics rather than campaign performance. Calling with an empty request body returns the latest available date's report across all brands/metrics for the advertiser. **REPORTED** ([Amazon Ads: "Brand Metrics API open beta overview"](https://advertising.amazon.com/API/docs/en-us/brand-metrics/overview), [python-amazon-ad-api docs](https://python-amazon-ad-api.readthedocs.io/en/latest/api/brand_metrics.html))
- No source found confirms whether the official MCP server's tool set currently exposes Brand Metrics specifically (as opposed to generic Sponsored ads reporting) — **UNKNOWN**.

### The "thin MCP wrapper" option — build your own vs. use Amazon's
A recurring theme across sources examining third-party MCP servers (KuudoAI, agentcentral, others) is a documented trade-off, not just a marketing claim:
- Amazon's own MCP server is described as unusually complete for a first-party launch ("more ambitious than Google's initial release"), covering execution (create/update campaigns, bids, budgets, keywords) end to end. **REPORTED**
- Thin/independent wrappers built directly on the raw Ads API tend to handle the "happy path" well but are reported to be brittle on edge cases — and Amazon's Ads API surface is described as having "more reasonable mistakes than almost any other large API surface" (malformed responses, inconsistent error codes, deprecated-but-still-live endpoints). Building and maintaining your own thin wrapper means **you** own both the wrapper bugs and the underlying API's rough edges — "who fixes this when it breaks" matters even for a solo operator, and self-built means the pager is Rami's. **REPORTED** ([search synthesis citing adsuploader.com's Meta-Ads-MCP-analogous framing](https://adsuploader.com/blog/meta-ads-mcp-vs-cli))
- The pattern reported as best practice for "sophisticated advertising teams": use **MCP for execution workflows** (campaign creation, keyword/bid/budget changes — the conversational, turn-by-turn actions) and a **separate pre-processed analytics layer built directly on the Reports API** for performance analysis and strategic decision support (batch, scheduled, structured — exactly the shape of Habib's existing `sync/` + `agents/ppc_agent.py` pattern in CLAUDE.md, which already pulls `ppc_campaign_stats_daily`/`ppc_keyword_stats_daily` via scheduled sync rather than live API calls per agent run). **REPORTED**

**Implication for Habib**: this validates the existing CLAUDE.md architecture almost exactly — keep the daily sync layer (direct Reports v3 calls, async, batch, written to Supabase) as the analytics backbone, and add the **official Amazon Ads MCP server** as the PPC Agent's/Rami's execution surface for the conversational/action side (bid changes, budget changes, keyword/negative additions) that today goes through hand-rolled SP-API write calls in `executor/sp_api_client.py`. It argues against building a custom thin MCP wrapper from scratch, given Amazon's official server already exists, is reported as unusually capable, and offloads API-edge-case maintenance to Amazon rather than to Rami.

## 5. Keyword Research & Rank Tracking With API Access

### Free: Amazon Brand Analytics via SP-API
The most important finding in this section: **Amazon's own first-party search-behavior data is available free via the Selling Partner API's Reports v2 "Analytics Reports" category**, gated only by **Brand Registry** enrollment (already a prerequisite for most SP-API report types) — not a separate paid subscription. Five Brand Analytics report families are confirmed available: **Search Catalog Performance**, **Search Query Performance (SQP)**, **Market Basket**, **Amazon Search Terms** (i.e., "Top Search Terms"), and **Repeat Purchase**. **VERIFIED-adjacent / REPORTED** (multiple sources corroborate; the Amazon developer changelog itself was cited but not independently fetched from this environment): ([Amazon SP-API changelog: "Added new Search Query Performance and Search Catalog Performance Analytics Report types"](https://developer-docs.amazon.com/sp-api/changelog/update-added-new-search-query-performance-and-search-catalog-performance-analytics-report-types), [ClearAds Agency: "API Access to Search Query Performance (SQP) Reports"](https://clearadsagency.com/api-access-to-search-query-performance-sqp-reports/), [Jarvio: "How to Read and Use Amazon's Search Query Performance Report"](https://jarvio.io/blog/search-query-performance-report))

- **Search Query Performance (SQP)**: query-first view — for a given search query, shows total market impressions/clicks/cart-adds/purchases and Habib's own product's *share* of each (impression share, click share, cart-add share, purchase share) relative to all sellers competing on that query. This is the single most valuable free dataset for PPC keyword prioritization: it directly shows where Habib is under-indexed on high-volume queries relative to competitors, which is exactly the kind of signal the PPC Agent's system prompt (CLAUDE.md §9.2) should be pulling into its analysis alongside `ppc_keyword_stats_daily`. **REPORTED**
- **Search Catalog Performance**: ASIN-first view — for a given product, shows performance (impressions, clicks, click rate, cart adds, purchases, conversion rate, median price at each funnel stage) across *all* search traffic, not just paid. Useful for the Listing & Competitor Intel Agent (CLAUDE.md §9.3) to separate organic vs. paid contribution to BSR/traffic trends. **REPORTED**
- **Amazon Search Terms ("Top Search Terms")**: the classic weekly top-searched-terms-by-category report, now report-API accessible instead of only a Seller Central CSV download. **REPORTED**
- Programmatic access via SP-API (not manual CSV download) went live **February 26, 2025**, which predates this research window — i.e., by September 2026 this is a mature, stable API surface, not a beta. **REPORTED**

**Implication for Habib**: this should be added to the existing `sync/` layer (CLAUDE.md §4.1) as a new weekly sync job (Search Query Performance is inherently a lagged, aggregate weekly/period metric, not a daily one) feeding a new Supabase table, at **zero incremental subscription cost** — it uses the same SP-API credentials the Inventory/Orders/Sales sync jobs already hold. This is very likely higher-leverage than any paid keyword tool for a 15-SKU brand, because it is first-party Amazon data (not a third-party tool's estimate/scrape of Amazon rank).

## 6. Best-Practice Campaign Architecture for a Small Brand in 2026 (Advertising Playbook)

Synthesized from multiple 2026 agency/practitioner sources; all claims below are **REPORTED** (practitioner consensus, not a single authoritative Amazon source) unless noted. Sources: [Influencer Marketing Hub: "Amazon PPC Campaign Structure for 2026"](https://influencermarketinghub.com/amazon-influencer-marketing/amazon-ppc-campaign-structure/), [Eva: "Amazon Advertising Campaign Structure: 2026 Profit Guide"](https://eva.guru/blog/amazon-advertising-campaign-structure-guide/), [Velocity Sellers: "Amazon PPC Campaign Structure 2026"](https://www.velocitysellers.com/2026/06/17/amazon-ppc-campaign-structure-account-architecture-2026/), [Pare: "Amazon PPC Campaign Structure Is Broken in 2026"](https://pare.so/blog/amazon-ppc-campaign-structure-one-campaign-multiple-goals-2026), [ScaleInsights: "Amazon Auto Campaign Match Types"](https://scaleinsights.com/learn/amazon-auto-campaign-match-types), [Daniks.AI: "Amazon PPC Match Types"](https://daniks.ai/blog/amazon-ppc-match-types), [CaptenAMZ: "Amazon Negative Keywords"](https://captenamz.com/blog/amazon-negative-keywords/), [Atom11: "Amazon PPC Dayparting Guide"](https://www.atom11.co/blog/amazon-ppc-dayparting-guide), [Off-Hours: "Amazon PPC Automation Rules"](https://www.off-hours.app/blog/amazon-ppc-automation-rules), [AdLabs: "The Amazon PPC Dayparting Guide"](https://adlabs.app/guides/amazon-dayparting-guide/).

### 6.1 Core principle: structure by business role, not by convenience
The dominant 2026 consensus (a shift from older "one campaign per match type" thinking) is to structure campaigns by **strategic intent**, isolating: discovery, rank acquisition, brand defense, conquesting (competitor ASIN targeting), retargeting, and DSP/AMC audience work — each with its own budget, so a losing campaign can never quietly drain a winning one's headroom, and performance signals stay legible per intent.

### 6.2 Funnel/tier architecture (launch → ranking → defense → catch-all), for a ~15-SKU brand
A practical **four-campaign-per-hero-SKU** structure, synthesized across sources:

| Tier | Campaign type | Match type | Purpose | Typical bid posture |
|---|---|---|---|---|
| **Discovery** | 1 Auto campaign + 1 Broad Match campaign | Auto (all 4 sub-types: Close Match, Loose Match, Complements, Substitutes) + Broad | Harvest new search terms Amazon's algorithm and semantic matching surface; broad match now benefits from Amazon's 2025-2026 AI-powered semantic matching engine (synonyms, related intent, not just literal term variants) | Moderate bids (~50% of core bids); modest daily budget (e.g., $25/day per campaign scale to spend level) |
| **Phrase (testing)** | Phrase Match campaign | Phrase | Middle tier: proven search terms harvested from Discovery graduate here to confirm consistent conversion before committing to Exact | Bid slightly below Exact-tier winners |
| **Performance / Rank acquisition** | Exact Match campaign | Exact | Highest-bid, highest-ACOS-tolerance tier — for keywords the brand actively wants to *rank* for organically, not just harvest sales; only keywords with statistically significant conversion history graduate here from Phrase | Highest bids in the account, deliberately above target ACOS in the short term to buy rank |
| **Brand defense** | Branded campaign | Exact, own brand terms + own ASINs | Low-bid, protect brand-name search and buy box against competitor conquesting on the brand's own name | Low bids — defensive, not growth-seeking |
| **Catch-all / conquesting** | Competitor ASIN / category targeting (Sponsored Product/Display "Product Targeting") | ASIN/category target | Intercept competitor-branded searches and category browsers | Bid to margin-adjusted target ACOS, monitored closely for cannibalization vs. incremental |

**Critical structural rule repeated across sources**: branded and non-branded traffic must **never share a campaign** — they convert and cost too differently, and blending them makes both unreadable for optimization. This maps directly onto the PPC Agent's need in CLAUDE.md to compute "whether a keyword is cannibalizing organic sales" — that computation is only possible if branded is isolated from day one.

### 6.3 Negative keyword flow
- **Negative exact** and **negative phrase** are the two negative match types available; the flow is top-down: search terms that fail to convert in a lower-precision campaign (Auto/Broad/Phrase) get added as negatives in that *same* campaign and any upstream campaign, so the term is not paid for twice.
- **Statistical-significance discipline**: the most commonly cited practitioner error is negating a keyword after only 3 clicks and zero sales — not enough data. A defined click/spend threshold (tied to the account's typical conversion rate) should gate any negative-keyword action, not a fixed small click count. This is directly encodable as an L1-adjacent rule for Habib's PPC Agent (e.g., "do not recommend negating a search term with fewer than N clicks or $X spend, computed from trailing 90-day account CVR").

### 6.4 Budget allocation by funnel stage
One source proposes an approximate top/mid/bottom-funnel spend split of **20-25% top-funnel (discovery/awareness), 25-30% mid-funnel (phrase/testing), 45-55% bottom-funnel (exact/performance + brand defense)** — directionally useful as a starting allocation for Habib's ~15 hero SKUs, to be tuned against actual margin data once volume accrues. **REPORTED**, single-source figure, treat as a starting heuristic not a hard rule.

### 6.5 Target ACOS by margin tier
Best practice explicitly rejects "industry-average ACOS targets" in favor of **product-level margin-derived targets**: target ACOS should be set as a function of each SKU's actual contribution margin, not a blanket account-wide number. This aligns exactly with CLAUDE.md's existing L1 rule of a 15% minimum FBA margin threshold — the natural extension is a per-SKU target-ACOS formula such as `target_ACOS = contribution_margin_pct - desired_net_margin_after_ads`, computed from the existing `product_cost_history`/`profit_daily` tables, rather than a single account-wide target.

### 6.6 Dayparting and budget/bid rules — guardrail patterns
- **Bid rules vs. budget rules are different levers**: bid rules adjust individual keyword/target bids by time-of-day/day-of-week without touching the daily budget cap (better fit for Sponsored Products, driven by hourly conversion-rate data); budget rules raise/lower the whole campaign's daily cap and suit Sponsored Brands during promotional events.
- **Minimum/maximum bid guardrails** ("hard safety rails") are considered essential — a floor to avoid losing visibility, a ceiling to avoid runaway cost during competitive bid wars or algorithm errors.
- **Daily spend caps** protect against cost surges during peak days or competitor-driven bid spikes.
- **Data-maturity gate before automating**: a campaign needs a minimum run of consistent performance (one source specifies **at least 10 days**) before dayparting/bid-rule automation is layered on — automating too early means "the algorithm is guessing."
- **Gradual guardrail tightening** is preferred over dramatic cuts, which can starve the algorithm of the data volume needed to re-learn.
- **Rollout discipline**: test dayparting on one campaign before extending account-wide; not every campaign benefits — brand-awareness/organic-boosting campaigns may not need rigid time-of-day scheduling the way direct-response/bottom-funnel campaigns do.

### 6.7 Implication for the Habib PPC Agent's system prompt
Sections 6.2-6.6 above should be encoded, largely verbatim as structural policy, into the PPC Agent's system prompt (CLAUDE.md §9.2) alongside the existing L1 rules — specifically: (a) never propose merging branded and non-branded targeting into one campaign; (b) require a minimum click/spend threshold before recommending a negative keyword; (c) require a minimum 10-day performance history before recommending dayparting/rule automation on a given campaign; (d) compute per-SKU target ACOS from margin data rather than a single account-wide number; (e) respect explicit bid ceiling/floor and daily-spend-cap parameters (see final Guardrails section).

## 7. Walmart Connect Advertising — API and MCP Options

### Walmart Connect Ads API
Walmart Connect exposes **Sponsored Search** and **Display Ads** APIs via the Walmart Developer Portal, covering campaign and ad group creation, bid and budget adjustments, campaign scheduling, and performance reporting — functionally comparable in scope to the Amazon Ads API's Sponsored Products surface. **REPORTED** ([Walmart Developer Portal: "Introduction to Walmart Connect - Sponsored Search APIs"](https://developer.walmart.com/advertising-partners-search/docs/introduction-to-walmart-connect-ads-apis), ["Introduction to Walmart Connect - Display Ads APIs"](https://developer.walmart.com/advertising-partners/docs/introduction-to-walmart-connect-ads-apis))

**Access gate**: unlike Amazon's Ads API (open to any advertiser/agency with API credentials), Walmart Connect's Ads APIs are restricted to members of the **Walmart Connect Partner Network (WCPN)** — a partner-tier program, not a direct advertiser self-serve credential. The onboarding path is: apply to become a WCPN partner (or work through an existing WCPN partner/solution provider) → sandbox authentication/testing → production launch. **REPORTED** ([Walmart Developer Portal](https://developer.walmart.com/advertising-partners-search/docs/introduction-to-walmart-connect-ads-apis)) — this is a materially higher access bar than Amazon Ads API for a solo operator building an in-house agent, and worth flagging early for Habib's "future Walmart Canada expansion" plan (CLAUDE.md §16.1): **direct API access may require going through a WCPN-approved partner/aggregator rather than Rami registering credentials solo**, unless Habib itself pursues WCPN partner status.
- As of the **January 2026** release notes, Walmart Connect added read-only API access to shared targeting item sets and audiences across advertiser accounts within the same organization — a recent, actively developed API surface, not a static legacy one. **REPORTED** ([developer.walmart.com January 2026 Release Notes](https://developer.walmart.com/advertising-partners/changelog/january-2026-release-notes))

### Walmart Connect MCP options
No evidence found of an **official, Walmart-built** MCP server (unlike Amazon's first-party server). What exists is entirely **third-party**:
- **Vinkius "Walmart Connect Ads MCP"** — 8 tools reported to give agents "full control over Sponsored Search advertising campaigns": real-time CPC/ROAS monitoring, multi-campaign daily budget adjustment, keyword bid optimization, performance reporting. Marketed as "no API keys, no infrastructure, connect in under 2 minutes" — implying it proxies through Vinkius's own hosted credentials/service layer rather than the advertiser's direct WCPN partner credentials, which raises the same trust/data-custody question as the MarketplaceAdPros Amazon wrapper in §1. **REPORTED** ([vinkius.com "Walmart Connect Ads MCP"](https://vinkius.com/mcp/walmart-connect-ads))
- **Intentwise "Walmart MCP" (AI Gateway)** — brings Walmart retail + Walmart Connect advertising data into Claude/ChatGPT for diagnostics/custom dashboards; framed as read/analytics-oriented rather than write/execution-oriented. **REPORTED** ([intentwise.com "Walmart MCP"](https://www.intentwise.com/walmart-mcp))
- **General product/shopping MCP servers** (`taazkareem/walmart-mcp`, `DomingosNgongo/walmart-mcp`, Apideck's Walmart MCP) — these target Walmart's **retail/product catalog** data (search, item lookup, stock, reviews, store locations) for shopping-assistant use cases, **not advertising** — not relevant to a PPC agent. **REPORTED**, noted here mainly to prevent confusing "a Walmart MCP server" in a generic sense with a Walmart *advertising* MCP.

### Implication for Habib
Walmart Connect advertising automation is materially less mature than Amazon's in two ways: (1) no first-party Amazon-equivalent MCP server exists yet, and (2) base API access itself requires WCPN partner-tier approval rather than open self-serve developer credentials. For the "future Walmart Canada expansion" phase (CLAUDE.md §16.1's stated trigger: "when Walmart integration is active — new sync layer + marketplace-specific agent logic"), the realistic near-term options are: (a) go through an existing WCPN partner/aggregator (several of the §4 PPC platforms — Perpetua, Teikametrics, Pacvue — already have Walmart integrations and could serve as that partner layer rather than Habib building direct WCPN access), or (b) use a third-party Walmart MCP wrapper (Vinkius/Intentwise) with the same due-diligence caution as any credential-proxying third-party MCP. Building a Habib-owned direct WCPN integration is realistically a Phase-2-or-later undertaking, not a v1 item.

## Recommended Stack for the Advertising Department

### MCP(s) the agent holds
1. **Amazon Ads MCP Server (official, Amazon-hosted)** — primary and only advertising-execution MCP for the PPC Agent. Covers SP/SB/SD campaign, ad group, keyword, negative, bid, and budget CRUD plus reporting, gated behind existing Amazon Ads API (LWA) credentials Habib already needs regardless. Route all agent-proposed writes through the existing `approval_requests` → Telegram → Executor flow exactly as CLAUDE.md already specifies — **the MCP server does not change the golden approval-invariant**, it only changes what tool the PPC Agent calls to *propose* an action; execution should still be mediated by Habib's own Executor, not a direct agent→MCP→Amazon write path, to preserve the audit-log/approval architecture already built. Do not connect a third-party wrapper (MarketplaceAdPros, KuudoAI, etc.) that proxies through someone else's SaaS credentials for a live ad account — added trust surface and cost with no capability Amazon's own server lacks.
2. **No Walmart Connect MCP yet.** Defer until Walmart Canada launch is imminent; when it is, prefer routing through a WCPN-partner platform Habib already needs for other reasons (e.g., Perpetua, which already spans Amazon + Walmart) over standing up direct WCPN partner status or a third-party credential-proxying wrapper (Vinkius/Intentwise).

### Data tools to buy
- **Nothing new required for launch.** Add a weekly SP-API Brand Analytics sync job (Search Query Performance, Search Catalog Performance, Amazon Search Terms) to the existing `sync/` layer — first-party, free, and directly usable by both the PPC Agent and the Listing & Competitor Intel Agent. This is the single highest-leverage, zero-incremental-cost addition identified in this research.
- **Amazon Marketing Stream** — defer to a later phase; valuable once same-day promo/dayparting reaction time matters, but adds an AWS SQS/Firehose ingestion component the CX22/solo-operator setup doesn't need yet given daily-batch Reports v3 already satisfies the current cadence.
- If Rami wants human-driven keyword research for new SKU launches, a **single mid-tier paid tool with confirmed API access** (Helium 10 Enterprise, Jungle Scout Growth Accelerator/Brand Owner, or DataDive Standard) is reasonable — but treat as a manual research aid for the human-approved launch-campaign build, not an agent-integrated data source, since SP-API Brand Analytics already covers ongoing keyword performance monitoring for free.

### What NOT to buy, and why
- **Pacvue, Quartile, Intentwise's Optimization Platform** — priced and scoped for $50K-$100K+/month, multi-brand agency/enterprise operations; their pricing floors alone ($895-$2,000+/mo, ~$1,000+/mo) would consume 10-100% of Habib's entire monthly ad budget before any incremental result.
- **Any all-in-one automated-bidding SaaS (Perpetua, Teikametrics, m19 full tier, Scale Insights, Ad Badger, Adbrew, Xnurta) as a replacement for the Claude PPC Agent** — these run their own proprietary, closed automation loop. Since none expose that automation logic via MCP (only Pacvue does, and it's out of budget), a Claude agent could at best read their dashboards, not coordinate with or override their decisions — creating a second, opaque brain fighting the first for control of the same bids/budgets. The entire value proposition of Habib's architecture (Mem0-accumulated, outcome-validated, Supabase-integrated knowledge) is undermined if a black-box third-party algorithm is simultaneously changing bids underneath it.
- **Helium 10 / Jungle Scout / DataDive API tiers as agent-integrated sources** — real API cost is the Enterprise/upper-tier price, not the advertised entry price, and the same underlying search-behavior signal (query-to-ASIN performance) is available free and more directly from SP-API Brand Analytics.
- **Standalone rank trackers (ZonGuru, Nozzle)** for a 15-SKU catalog — SP-API Search Query Performance already gives share-of-search by query per ASIN, a more actionable metric than position-only rank tracking, at no incremental cost.

### Guardrails (bid caps, budget caps, change-rate limits) — for the PPC Agent's system prompt and Executor
1. **Bid ceiling and floor per SKU tier**, set from the per-SKU margin-derived target ACOS (§6.5): no recommended bid may push projected ACOS more than a fixed margin buffer (e.g., 5 percentage points) above the SKU's break-even ACOS, and no bid recommendation below a floor that would forfeit auction visibility entirely.
2. **Daily and campaign-level spend caps**, enforced at the Executor/approval level, not just advisory in the prompt — no single approval may raise a campaign's daily budget by more than a fixed percentage (e.g., 25-30%) in one action; larger jumps require a second, explicit confirmation.
3. **Change-rate limiting**: no more than one bid/budget change per keyword/campaign per rolling 24-48 hours, and no dayparting/automation-rule recommendation for a campaign with fewer than 10 days of consistent performance history (§6.6) — encode this as a hard precondition check in `fetch_data()`, not just prompt guidance.
4. **Negative-keyword statistical-significance threshold**: no negative-keyword recommendation below a minimum click/spend threshold derived from the account's trailing-90-day average conversion rate (§6.3), to prevent premature negation on noisy small-sample data.
5. **Branded/non-branded isolation as a structural constraint**, not just a recommendation: reject (at the agent or Executor validation layer) any proposed campaign/ad-group structure that would combine branded and non-branded targeting.
6. **All price and PPC recommendations continue to require approval regardless of amount or direction**, per the existing L1 rule (CLAUDE.md §5.6) — the Amazon Ads MCP server's execution capability makes this more important, not less, since it lowers the friction of a bad autonomous write; the guardrails above bound the *size* of any single approved action, they do not replace the approval gate itself.
7. **DSP and AMC tools remain out of scope** until Habib's ad spend and entitlements (>$50K/year reported DSP threshold) justify the added complexity and cost — do not enable these MCP tool categories in the agent's tool allow-list prematurely.
