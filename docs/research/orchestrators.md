## 1. Paperclip (paperclip.ing / github.com/paperclipai/paperclip)

**What it is (VERIFIED via GitHub README/docs):** Node.js/TypeScript, MIT-licensed, self-hostable orchestration server + React UI that models AI agents as "employees" in a company org chart. Tagline: "Bring Your Own Agent: Any agent, any runtime, one org chart. If it can receive a heartbeat, it's hired." Launched ~March 4, 2026; crossed 30k GitHub stars within three weeks and stood at ~79.9k stars as of this research (VERIFIED star count from live GitHub page fetch; growth timeline REPORTED via Ry Walker research blog and ToolCenter/AIToolTier reviews). Maintained by a pseudonymous developer (@dotta) with no disclosed company/funding/paid tier as of mid-2026 (REPORTED, rywalker.com).
Sources: https://github.com/paperclipai/paperclip , https://paperclip.ing/ , https://rywalker.com/research/paperclip , https://github.com/paperclipai/paperclip/blob/master/README.md

**Core features (VERIFIED from repo/docs):**
- Org chart for agents — hierarchical roles, permissions, reporting structure — maps directly onto a "Chief of Staff + 7 department heads" design.
- Heartbeat execution — each hired agent is invoked on a scheduled heartbeat (cron-like) with budget checks before firing.
- Budget & cost control — token/cost tracking scoped by company, agent, project, goal, issue, provider, and model; budget policies with warning thresholds and hard stops; overspend auto-pauses agents and cancels queued work.
- Approval workflows — "board approval" gates, execution policies with review/approval stages, decision tracking, agent pause/resume/terminate, full audit log (append-only).
- Work/ticket system — issue-based coordination with dependencies (this is the closest built-in analog to "typed inter-agent requests"; agents open/close tickets against each other rather than a formal RPC schema).
- Multi-organization support with data isolation (relevant if he ever runs a second brand).
- Skill management — runtime skill injection.
- MCP exposure — Paperclip exposes its own REST API as an MCP server (`@paperclipai/mcp-server`) so a human (or a Claude Code/Desktop session) can manage issues, agents, goals, approvals and costs via MCP tools. This is Paperclip acting as an MCP *server for management*, not Paperclip agents acting as MCP *clients* against arbitrary tool servers (see gap below).
Sources: https://github.com/paperclipai/paperclip/blob/master/docs/adapters/overview.md , https://github.com/elevateinformatics/paperclip-mcp , https://dev.to/truongpx396/paperclip-deep-dive-a-build-guide-for-an-ai-company-control-plane-dda

**Adapter list and subscription-auth support (VERIFIED from docs/reference/adapters/*.md):**

| Adapter key | Underlying tool | Invocation | Subscription/OAuth auth path |
|---|---|---|---|
| `claude_local` | Claude Code CLI | local subprocess | **Yes** — honors an existing `CLAUDE_CODE_OAUTH_TOKEN` (Claude Max/Pro subscription login) or `ANTHROPIC_API_KEY`; docs explicitly list OAuth token as first-class |
| `codex_local` | Codex CLI | local subprocess, Paperclip-managed `CODEX_HOME` | **Yes** — "inherit the host Codex login by default... a ChatGPT-subscription login" is linked automatically; a per-agent `OPENAI_API_KEY` overrides it if set |
| `gemini_local` | Gemini CLI | local subprocess | API key documented; OAuth path not confirmed in fetched docs (UNKNOWN) |
| `kimi_local` | Kimi Code CLI | local via ACP | not specified |
| `opencode_local` | OpenCode | local subprocess | multi-provider, unspecified per-provider auth |
| `cursor` | Cursor CLI | background-mode subprocess | not specified |
| `hermes_local` / `hermes_gateway` | Nous Hermes agent | local CLI or HTTP/SSE | not specified |
| `openclaw_gateway` | OpenClaw | gateway HTTP endpoint | not specified |
| `process` / `http` | arbitrary shell command / webhook | generic | N/A (bring your own auth) |
| `droid_local` (external/community adapter) | Factory Droid | npm-installable plugin | not specified |

This is the single most important finding for the client: **Paperclip's Claude Code adapter (`claude_local`) is explicitly designed to run department agents as subprocesses of the `claude` CLI using the operator's own Claude Max OAuth session, not the Anthropic API** — matching the "no API-only billing" requirement exactly for at least the Claude and (via Codex) ChatGPT backends. This is corroborated independently by Anthropic's own Claude Agent SDK docs, which since mid-2026 document `CLAUDE_CODE_OAUTH_TOKEN`/`claude setup-token` specifically as a way to run the SDK against a Pro/Max plan instead of API billing (see §6 below).
Sources: https://github.com/paperclipai/paperclip-docs/blob/main/docs/reference/adapters/codex.md , https://github.com/paperclipai/paperclip/tree/master/packages/adapters

**Scheduling:** Heartbeats are Paperclip's native scheduling primitive (interval- or cron-like per agent), plus webhook triggers. No external cron needed, but nothing stops running it under systemd/cron as well for the git-state-sync and MCP-server processes it depends on.

**Self-host requirements (VERIFIED):** Node.js ≥24.11, pnpm ≥9.15, PostgreSQL (external or embedded), local or S3-compatible object storage. This is a materially heavier footprint than the client's current Hetzner CX22 Python stack — running Postgres + a Node monorepo + N local CLI subprocesses (Claude Code, Codex, etc., each with their own memory footprint) on 2 vCPU/4GB is a real risk; CX32 or better is advisable if Paperclip becomes the top-level orchestrator for 8 always-heartbeating agents.

**Maturity / maintenance burden:** Young (six months old as of Sept 2026), extremely fast-growing (stars, commit velocity — 4,107 commits) but single-maintainer-led with no company backing, which is itself a lock-in/continuity risk in the opposite direction (bus factor, not vendor factor). Community-reported issues as of ~Sept 1 2026: 153 open issues in one tracked snapshot — 43 bugs, 5 security/auth issues, 21 adapter issues, plus heartbeat/automation, deployment, and cost-tracking bugs (REPORTED, GitHub Discussion #610 analysis — not independently re-verified issue-by-issue). Reddit commentary (REPORTED, unverified thread) describes inconsistent output quality and a user who found it "performing a lot worse than just using Claude Code" directly after a weekend test; also a documented general finding that adding more agents increases coordination overhead and can reduce net effectiveness — relevant to the 8-department design (this argues for lean, mostly-independent department agents with a thin Chief-of-Staff synthesis step, matching the CLAUDE.md's own "compiler agent" deferred-feature note).
Sources: https://github.com/paperclipai/paperclip/discussions/610 , https://freecode.academy/topics/paperclip-ai-a-practical-review-of-the-multi-agent-orchestrator (REPORTED, secondary)

**Gaps relevant to this client's exact requirements:**
- Git-repo-of-markdown-files as shared state is NOT Paperclip's native model — Paperclip's shared state lives in its own Postgres-backed issue/goal/approval tables. A markdown-in-git layer would have to be built alongside it (agents write markdown to the repo as a side effect, or a sync script materializes Postgres state to markdown), meaning some custom glue either way.
- "Typed requests between agents" isn't a first-class schema in Paperclip; the closest primitive is the issue/ticket system (issue assigned agent-to-agent), which is not strongly typed by default — would need a project-specific issue template/JSON-schema convention.
- Paperclip agents acting as MCP *clients* against your own SP-API-adjacent MCP servers depends entirely on whether the underlying CLI adapter (Claude Code CLI, Codex CLI) supports MCP client config — both do natively (Claude Code and Codex CLI both support `mcpServers` config) — so Paperclip inherits MCP-client capability transitively through the adapter rather than providing it itself. This is a reasonable fit but means the MCP wiring is done at the Claude Code/Codex config level, with Paperclip only orchestrating *when* and *with what heartbeat/budget* the CLI runs.

## 2. OpenClaw (formerly Clawdbot → Moltbot → OpenClaw; github.com/openclaw/openclaw)

**Identity (VERIFIED):** MIT-licensed, "local-first personal AI assistant," now stewarded by the nonprofit OpenClaw Foundation with corporate sponsorship including OpenAI, GitHub, NVIDIA, and Vercel (REPORTED sponsorship list, corroborated by VentureBeat/Gigazine coverage of the Anthropic dispute below). ~389k GitHub stars (VERIFIED, live repo fetch), one of the fastest-growing repos in GitHub history — 100k+ stars within a week of its January 2026 launch (REPORTED, CNBC/jitendrazaa). Name changed twice under legal/trademark pressure: Clawdbot → Moltbot → OpenClaw (REPORTED, CNBC, Wikipedia).
Sources: https://github.com/openclaw/openclaw , https://en.wikipedia.org/wiki/OpenClaw , https://www.cnbc.com/2026/02/02/openclaw-open-source-ai-agent-rise-controversy-clawdbot-moltbot-moltbook.html

**Architecture and features (VERIFIED from repo):**
- "Trusted gateway, untrusted execution, deterministic policy" model — a local Gateway process controls policy (which tools/skills may run, which channels are paired) while the actual skill/tool execution happens in a more isolated environment.
- Messaging channels: WhatsApp, Telegram, Slack, Discord, Google Chat, Signal, iMessage — directly covers the client's desired Telegram approval channel, and could consolidate the existing custom `tgbot/` module if the client ever wanted to drop the bespoke python-telegram-bot code.
- Heartbeat/cron scheduler wakes the agent at a configurable interval to run without being prompted (REPORTED, corroborated across multiple guides) — functionally equivalent to Paperclip's heartbeats or plain cron.
- Memory/workspace stored as **markdown files in a directory designed to be a git repo** (default `~/clawd`) — this is the closest match of any project surveyed to the client's explicit "share state through a git repo of markdown files" requirement; it is OpenClaw's native persistence model, not a bolt-on.
- Skills marketplace, ClawHub (clawdhub.com) — community skill packages; this is also the project's biggest liability (see security below).
- Multi-provider model backends (VERIFIED from repo + docs search): Anthropic Claude, OpenAI GPT-5.x/Codex, Google Gemini, xAI Grok, Mistral, DeepSeek, plus local models via Ollama or any OpenAI-compatible endpoint — meaning SuperGrok/xAI is natively supported as a backend option, which none of the other orchestrators surveyed explicitly advertise.
Sources: https://github.com/openclaw/openclaw , https://www.gradually.ai/en/changelogs/openclaw/ , https://releases.sh/openclaw

**The Anthropic/OpenAI subscription-OAuth saga (VERIFIED via multiple press sources, cross-corroborated):** This is directly relevant to the client's "use existing subscriptions locally" requirement and is a cautionary tale about doing it through anything other than the vendor's own CLI.
- **Jan–Feb 20, 2026:** Anthropic updated its consumer Terms of Service to state that OAuth tokens obtained via Free/Pro/Max plans are for use "exclusively with Claude Code and Claude.ai," and that using them with any other product — including the Claude Agent SDK and third-party harnesses like OpenClaw — is unauthorized.
- **April 4, 2026, 3PM ET:** Anthropic enforced this — Claude Pro/Max/Team subscriptions stopped authenticating inside OpenClaw, OpenCode, NanoClaw, and other third-party harnesses. The same day, OpenAI made Codex free across all paid ChatGPT tiers — reported by multiple outlets as a deliberate competitive move (Anthropic tightening exactly as OpenAI opened up).
- **May 13, 2026:** Anthropic reversed course, announcing an "Agent SDK credits" tier: Pro ($20/mo credit), Max 5x ($100/mo), Max 20x ($200/mo) usable via the Agent SDK, `claude -p`, Claude Code GitHub Actions, and re-authorized third-party apps including OpenClaw by name.
- **June 15, 2026:** Anthropic paused the *separate credit-pool* mechanic; subscription-authenticated Agent SDK/`claude -p`/third-party usage instead draws down from the same usage limits as the subscriber's normal Claude Code/Claude.ai usage (i.e., no extra allowance, but usage is folded back into the plan rather than blocked or metered separately).
- **As of Sept 2026 (this research):** the net effect is that OpenClaw running Claude via subscription OAuth is once again *permitted*, but it shares one pool of weekly/5-hour rate limits with the operator's own interactive Claude Code and claude.ai use — a real capacity constraint for 8 department agents plus a Chief of Staff all wanting daily runs, and a policy Anthropic has already changed three times in under six months (materially higher policy-risk than driving the same subscription through the official `claude` CLI directly, which was never blocked).
- OpenAI, by contrast, never revoked ChatGPT-subscription (Codex) use in third-party harnesses and instead made Codex free across paid tiers the same day Anthropic clamped down — a more permissive, more stable stance for xAI/OpenAI-flavored department agents (REPORTED, MindStudio/Gigazine).
Sources: https://gigazine.net/gsc_news/en/20260220-anthropic-third-party-block/ , https://www.mindstudio.ai/blog/anthropic-vs-openai-agent-token-access-openclaw , https://venturebeat.com/technology/anthropic-reinstates-openclaw-and-third-party-agent-usage-on-claude-subscriptions-with-a-catch , https://gigazine.net/gsc_news/en/20260514-anthropic-claude-agent-sdk-credits/ , https://groundy.com/articles/anthropic-bans-third-party-use-subscription-auth-three-stage-repricing/

**2026 security incidents (VERIFIED/REPORTED, multiple independent security-industry sources cross-corroborating each other):**
- **CVE-2026-25253** (CVSS 8.8): a one-click remote-code-execution chain, exploitable via a crafted WebSocket link even against instances bound to localhost; a single click could hand an attacker full control of the OpenClaw instance. Patched in v2026.1.29 (Petronella, Adversa AI, cybersecuritynews.com).
- **Internet exposure:** Censys, Bitsight, and Hunt.io scans independently found 30,000+ internet-exposed OpenClaw instances, many with no authentication at all, in the weeks after launch.
- **"ClawHavoc" supply-chain campaign:** first disclosed by Koi Security on Feb 1, 2026. Multiple threat actors registered as ClawHub developers and mass-uploaded trojanized skills (disguised as crypto bots, productivity tools, social utilities) primarily delivering the Atomic macOS Stealer (AMOS). Initial count: 341 malicious skills (~12% of the registry); by Feb 16, 2026 scans found 824+ malicious skills across 10,700+ total skills.
- **Current hardening guidance (REPORTED, vendor/community hardening guides — AccuKnox "ClawArmor," Nebius, Cloud Security Alliance labs, adibirzu/openclaw-security-monitor):** never bind the gateway to `0.0.0.0` in production; always enable token auth with a random token; default-deny inbound firewall; sandbox every tool execution; use DM/channel pairing before any messaging channel can issue commands; full-disk encryption; keep long-lived credentials off the agent host entirely (vault/broker pattern); patch critical CVEs within 24 hours since self-hosted instances do not auto-update.
- **Current version:** 2026.8.2 as of this research, with continued fast release cadence (REPORTED, gradually.ai/releases.sh changelogs).
Sources: https://cybersecuritynews.com/clawhavoc-poisoned-openclaws-clawhub/ , https://unit42.paloaltonetworks.com/openclaw-ai-supply-chain-risk/ , https://conscia.com/blog/the-openclaw-security-crisis/ , https://accuknox.com/blog/introducing-clawarmor-for-openclaw-instances , https://adversa.ai/blog/openclaw-security-101-vulnerabilities-hardening-2026/

**Fit as a department scheduler + Telegram approval channel:** Strong on paper (native cron/heartbeat, native Telegram channel, native markdown-git memory, multi-provider including Grok) but the trust model is wrong for this client's use case out of the box: OpenClaw's skill marketplace and its history of RCE-class vulnerabilities make it a poor place to hold Amazon SP-API and marketplace credentials unless heavily hardened (no ClawHub skills from the public registry; gateway never exposed to the internet; each department's tool access scoped tightly). Running it purely as a *local* scheduler+messaging layer with no ClawHub skills installed, MCP servers for actual work, and the gateway bound to localhost/Tailscale only, mitigates most of the above — but that is materially more ops discipline than the client's stated "no DevOps team, must fail with a clear Telegram alert" constraint implies he wants to take on.

## 3. Hermes Agent, NanoClaw, and other 2026 "always-on personal agent" projects

### Hermes Agent (Nous Research, github.com/NousResearch/hermes-agent)

**VERIFIED (repo fetch):** MIT license. ~240.5k stars, 49.2k forks, 27,615 commits — released Feb 25, 2026 and reached this scale in about six months, one of the fastest-growing OSS repos of 2026 alongside OpenClaw (REPORTED growth-rate framing, Vellum/aibuilderclub). Terminal UI, multi-platform messaging (Telegram, Discord, Slack, WhatsApp, Signal), agent-curated memory with "Honcho dialectic user modeling," full-text session search, ability to spawn isolated subagents for parallel workstreams, built-in cron scheduler ("daily reports, nightly backups, weekly audits... running unattended"), autonomous skill creation (an agent that solves something can save it as a reusable skill, similar to OpenClaw's ClawHub model but self-generated rather than marketplace-downloaded, which is a meaningfully smaller supply-chain attack surface). Full MCP client support ("connect any MCP server for extended capabilities") — this is a first-class capability, unlike Paperclip where MCP-client behavior is inherited transitively through the CLI adapter. Runs on a $5 VPS, Docker, SSH, Singularity, Modal, Daytona, or Vercel Sandbox; requires Python 3.11, Node.js, ripgrep, ffmpeg.
Sources: https://github.com/NousResearch/hermes-agent , https://hermes-agent.nousresearch.com/docs/integrations/providers , https://www.vellum.ai/blog/official-hermes-agent-breakdown

**Model backend / subscription auth (VERIFIED via open GitHub issues on the repo, which is the clearest primary-source evidence found in this entire survey of how subscription-CLI backing actually gets implemented):**
- Hermes' documented multi-provider path (Nous Portal, OpenRouter, OpenAI-compatible endpoints, "switch with `hermes model` — no code changes") is **API-key/API-compatible only**; subscription auth is not part of the stable provider list.
- However, three open feature-request issues on the repo (#48320, #78563, #47199) describe — with real implementation detail from maintainers/contributors — a `claude-code` provider that **shells out to the local `claude` CLI as a subprocess** rather than calling the Anthropic API, specifically to consume Max/Pro subscription quota "without requiring separate 'extra usage' credit." Documented technical specifics from the issue threads: Hermes already reads Claude Code's own OAuth credential file (`~/.claude/.credentials.json`); because the integration spawns the actual `claude` binary as a subprocess rather than sending an `Authorization` header as an HTTP client, **it does not trigger Anthropic's third-party-billing restriction** described in §2 above — this is presented explicitly as the reason the approach is viable post-ban. Practical costs of this approach, per the same threads: `--dangerously-skip-permissions` is mandatory because `claude` stalls on permission prompts in non-interactive/headless mode; tool calls come back embedded in free text rather than JSON-RPC (the adapter must inject tool definitions into the system prompt and regex-extract results); each Hermes turn maps to one `claude -p` invocation with no streaming; and there is no native tool-calling through Claude Code itself in this mode (Hermes' own tool layer substitutes).
- **This CLI-subprocess-not-API-client pattern (confirmed independently for Hermes here and for Paperclip's `claude_local`/`codex_local` adapters above) is the general, reproducible technique for running any of these orchestrators on subscription billing without violating Anthropic's or OpenAI's terms** — and it is the same shape of solution the client would need to build himself if no packaged orchestrator did it for him.
Sources: https://github.com/NousResearch/hermes-agent/issues/48320 , https://github.com/NousResearch/hermes-agent/issues/78563 , https://github.com/NousResearch/hermes-agent/issues/47199

**Isolation model:** Not container-per-agent by default (unlike NanoClaw) — subagents are spawned as processes/threads within the same host context. Security posture for a credential-holding deployment is therefore closer to OpenClaw's than to NanoClaw's unless the operator adds container isolation manually. No large-scale security-incident reporting was found for Hermes Agent as of this research (UNKNOWN/absence of evidence, not evidence of absence — it is younger and smaller than OpenClaw, so may simply not yet have attracted the same adversarial attention).

### NanoClaw (github.com/dh7/NanoClaw, community forks under nanocoai/)

**VERIFIED (repo fetch):** MIT license. Positioned explicitly as "a lightweight alternative to OpenClaw that runs in containers for security." Runs directly on Anthropic's Agent SDK (not a subprocess wrapper) — each messaging group/context gets its **own isolated container** (Docker Sandboxes on macOS Apple Silicon/Windows WSL, or native Apple Container on macOS, Docker elsewhere), its own `CLAUDE.md` memory file, and its own isolated filesystem — "an agent in a family WhatsApp group and one connected to a work repository" no longer share an environment, which The New Stack (REPORTED, secondary) frames as a direct architectural response to OpenClaw's lack of isolation. Task scheduler component (`src/task-scheduler.ts`) supports natural-language recurring jobs ("send an overview of the sales pipeline every weekday morning at 9am"). Multi-channel: WhatsApp, Telegram, Discord, Slack, Gmail. Supports "agent swarms for collaborative tasks" — the closest built-in primitive to genuine multi-agent department coordination found among the personal-agent-class tools (vs. orchestrator-class tools like Paperclip).
**Authentication (VERIFIED):** uses `ANTHROPIC_AUTH_TOKEN` (API key) via environment variable and "any Claude API-compatible model endpoint" — **NanoClaw does not use subscription OAuth**; because it runs on the raw Agent SDK as an HTTP client (exactly the pattern Anthropic's ToS restricts), subscription billing is not a legitimate option for it post-February-2026 policy, only API-key billing. This directly conflicts with the client's "no API-only billing" constraint unless he specifically wants to pay per-token for some departments.
**Maturity:** Small relative to OpenClaw/Hermes — under 10,000 stars as of this research (REPORTED aggregate figure from search), 330 commits on the primary fork (VERIFIED repo fetch); a second/renamed community org (`nanocoai/nanoclaw`) exists with an identical description, suggesting the project has forked or been mirrored, which is itself a minor provenance/trust signal to note.
Sources: https://github.com/dh7/NanoClaw , https://thenewstack.io/nanoclaw-minimalist-ai-agents/ , https://github.com/nanocoai/nanoclaw

### Other 2026 "always-on personal agent" projects (lighter treatment — REPORTED, not independently repo-verified beyond what's noted)

- **ZeroClaw** (github.com/zeroclaw-labs/zeroclaw) — Rust, compiles to a single binary, described (REPORTED, gradually.ai/bitdoze aggregator reviews) as "~99% smaller footprint than OpenClaw," multi-channel (Discord, Telegram, Matrix, email, webhooks, CLI), installable as a systemd/launchctl/Windows service for always-on operation. Framed in community round-ups as the "spiritual successor to NullClaw." Maturity and security track record are thin compared to OpenClaw/Hermes; no independent CVE/incident reporting found (UNKNOWN).
- **OpenFang** (github.com/RightNow-AI/openfang, formerly under rightnow-ai) — Rust, 14-crate workspace, ~137k LOC, "Hands" tool-execution system, 40 channel adapters, described by reviewers as having "more security layers than anything else" surveyed, but still pre-1.0 (v0.1.x) with reviewers explicitly warning of rough edges. REPORTED only.
- **Nanobot** (github.com/HKUDS/nanobot, University of Hong Kong Data Intelligence Lab, Feb 2026) — ~4,000 lines of Python vs. OpenClaw's ~430,000 lines of TypeScript, MCP-native, WebUI, multi-agent workflows, ~32,800 stars. Positioned as the "read the whole codebase in an afternoon" alternative. REPORTED only; not independently repo-fetched in this pass.
- None of ZeroClaw/OpenFang/Nanobot were found (in the time available) to have documented, working subscription-OAuth backends for Claude/ChatGPT/Grok comparable to the Hermes/Paperclip CLI-subprocess pattern — treat subscription support for these three as UNKNOWN pending direct verification if the client wants to shortlist one.
Sources: https://github.com/zeroclaw-labs/zeroclaw , https://github.com/rightnow-ai/openfang , https://github.com/HKUDS/nanobot , https://www.bitdoze.com/openfang-setup-guide/ , https://effoma.com/blog/open-source-ai-agents-openclaw-zeroclaw-picoclaw/

## 5. Human-in-the-loop and approval tooling

**HumanLayer** (github.com/humanlayer/humanlayer) — **VERIFIED via GitHub repo/CLAUDE.md fetch and multiple corroborating sources.** Started as an open-source SDK/API that lets an agent pause before a "high-stakes function call" (a database write, an outbound email, a financial action) and request human approval via Slack, email, or other channels, deterministically blocking execution until a decision returns. As of 2026 the company has expanded this into "CodeLayer," a broader IDE/desktop app for orchestrating **Claude-Code-based** coding agents (Go daemon `hld` + Tauri/React desktop app `CodeLayer.app` + TypeScript `humanlayer` CLI), enabling multiple parallel Claude Code sessions with the same approval-gate mechanism. The original approval SDK remains open source and is usable standalone, independent of the newer IDE product. Delivery-to-decision mechanism: HumanLayer's approval call is a synchronous-feeling but actually async webhook/polling pattern — the agent's tool call is intercepted, a message goes out over the configured channel (Slack thread, email, etc.) with approve/deny affordances, and the SDK call blocks/resumes when a webhook fires back from that channel — architecturally the same shape as the client's own existing `approval_requests` table + Telegram bot polling loop, just packaged as a reusable library instead of bespoke code. No first-party Telegram channel was confirmed in the fetched sources (UNKNOWN whether Telegram is a supported channel out of the box vs. Slack/email only) — would likely need a small custom channel adapter to route to Telegram specifically, similar effort to what's already built in `tgbot/`.
Sources: https://github.com/humanlayer/humanlayer , https://github.com/humanlayer/humanlayer/blob/main/humanlayer.md , https://deepwiki.com/humanlayer/humanlayer

**Paperclip's approval flow** (see §1) — a first-class "board approval" workflow with review/approval stages built directly into the org-chart/ticket model, decision tracking, and budget-tied hard stops; the delivery channel (Telegram vs. Slack vs. web UI) is pluggable at the notification layer rather than baked in, so a Telegram delivery adapter would still need to be written or reused (REPORTED, not confirmed whether an official Telegram notification channel ships out of the box — UNKNOWN).

**n8n human-in-the-loop** (see §4) — the most turnkey no-code option: a "Send and Wait for Response" node with an "Approval" response type natively renders Approve/Reject buttons in Telegram (or Slack/Gmail/generic Chat) and pauses the workflow's execution until the callback arrives, resuming with the decision available as workflow data. This is functionally a drop-in replacement for the bespoke `tgbot/handlers.py` approve/reject callback logic already running in the client's stack, if he ever migrates orchestration to n8n.

**Simple Telegram bot patterns (the client's existing approach)** — `python-telegram-bot` polling loop + `InlineKeyboardMarkup`/`CallbackQueryHandler`, backed by a database table of pending approvals (`approval_requests`) that the bot polls and updates — this is architecturally identical to what HumanLayer and n8n do internally, just hand-rolled. Given the client already has this working end-to-end through Phase 3, the marginal value of switching to HumanLayer or n8n purely for the approval mechanic is low; the value of those tools would come from the *broader* orchestration/scheduling/MCP layer around the approval step, not the approval primitive itself.

## 6. Running a department as a subprocess of a subscription CLI — evidence and failure modes, per backend

The client's core ask — run each department on `claude -p`, `codex exec`, `grok -p`, or `gemini -p` as a subprocess rather than paying per-token API rates — is legitimate for some backends and actively blocked by policy for others as of Sept 2026. Findings by backend:

**Claude (`claude -p` / Claude Code CLI):** **VERIFIED/REPORTED, strongest evidence found in this survey.**
- Anthropic's own consumer ToS (updated Feb 20, 2026, enforced Apr 4, 2026) restricts *third-party tools/harnesses* and the raw *Agent SDK* from authenticating with Pro/Max/Team subscription OAuth tokens — but the restriction targets acting as an HTTP client against the API with a borrowed token, not running the actual first-party `claude` binary as a subprocess.
- Two independent open-source projects (Paperclip's `claude_local` adapter, §1; Hermes Agent's in-progress `claude-code` provider, §3) converge on the identical technique and the identical justification: **spawn the real `claude` CLI binary as a subprocess and let it use its own already-authenticated OAuth session** (Paperclip explicitly documents reading `CLAUDE_CODE_OAUTH_TOKEN`; Hermes' GitHub issues document reading `~/.claude/.credentials.json` directly) rather than re-implementing an API client with that token. Both explicitly frame this as the difference between "using Claude Code" (allowed) and "using the Agent SDK/a harness with Claude Code's token" (restricted).
- **Known failure modes (REPORTED across issue threads and rate-limit trackers):** `--dangerously-skip-permissions` is required for headless/non-interactive runs, since `claude` otherwise stalls on a permission prompt with nothing to answer it; tool-calling has to be done Hermes/Paperclip's own way (text-embedded, regex-extracted) rather than through Claude Code's native tool loop, because the subprocess is a black box beyond stdin/stdout; the OAuth session can expire and needs periodic re-auth (`claude setup-token` / interactive login), which is awkward on a headless box and needs a human to redo periodically; usage draws from the same weekly/session Claude Code limits as the operator's own interactive use — 8 departments running daily, plus a Chief-of-Staff synthesis pass, plus weekly/monthly consolidation, is a meaningful chunk of a single Max plan's pooled quota, and there is no per-department sub-allocation — one runaway department can starve the rest for the week.
- Net: **legitimate and demonstrated in the wild for Claude specifically when done via CLI subprocess, not raw API/OAuth-token reuse.**

**ChatGPT/Codex (`codex exec`):**
- OpenAI's posture is more permissive: Codex became free across all paid ChatGPT tiers on the same day (Apr 4, 2026) Anthropic tightened its own policy, and OpenAI has not been reported blocking third-party harnesses from Codex-CLI subscription auth the way Anthropic and (as found below) Google did.
- Paperclip's `codex_local` adapter documents inheriting "the host Codex login... a ChatGPT-subscription login" automatically, with a per-agent `OPENAI_API_KEY` only overriding it if explicitly set — i.e., subscription-first by default.
- **Known failure modes (REPORTED, rate-limit tracker sources):** Codex enforces a rolling 5-hour usage window plus a weekly cap; OpenAI suspended the rolling 5-hour window on July 12, 2026 in favor of weekly-cap-only accounting; *every surface shares one pool* — local CLI, IDE sessions, and cloud chat sessions all draw from the same window, so, as with Claude, 8 departments hitting Codex daily competes with the operator's own interactive use of the same ChatGPT plan. Headless/CI use is explicitly supported (`codex exec`, streaming-json-style output), which is more automation-friendly out of the box than Claude Code's plain-text output.
- Net: **legitimate, better-documented for automation, but subject to the same shared-quota ceiling as Claude.**

**Grok (Grok Build CLI, SuperGrok):**
- Grok Build launched ~May 25, 2026 in beta specifically for SuperGrok/X Premium+ subscribers; the CLI install is free but functionally requires an active SuperGrok or X Premium+ subscription to run at all.
- Headless mode is a first-class, documented feature: `grok -p "..." --output-format streaming-json` for CI/CD and scripting, with structured output describing files touched, commands run, and results — the most automation-native output format of the four backends surveyed.
- SuperGrok Heavy tier unlocks up to 8 parallel subagents — coincidentally exactly matching an 8-department fan-out, if the client's SuperGrok tier is Heavy (REPORTED spec, not independently confirmed against current pricing page).
- No evidence found (in the time available) of xAI restricting third-party/automated use of subscription auth the way Anthropic and Google did — treat as **REPORTED-permissive, not proven risk-free** (xAI is a much younger CLI product; policy could tighten as it did for the other two).
- Net: **most automation-friendly interface of the four, least evidence of either restriction or of anyone actually wiring it into a multi-agent orchestrator yet — early and thin on real-world integration precedent.**

**Gemini (`gemini -p` / Gemini CLI):**
- **This is the clearest cautionary tale in the survey.** Google explicitly banned proxying Gemini CLI OAuth tokens through third-party tools in February 2026, began enforcing detection on March 25, 2026, and **mass-suspended accounts** that used the pattern — including paying Google AI Ultra subscribers. By June 2026, Google went further and deprecated the OAuth login flow entirely for Google AI Pro/Ultra/Code-Assist-individual tiers, removing "Login with Google" as an option for those accounts. Headless/CI use is documented but requires falling back to `GEMINI_API_KEY` (i.e., ordinary metered API billing) once cached OAuth credentials aren't usable.
- Net: **subscription-backed automation via Gemini CLI is currently the least viable of the four — actively enforced against, with account-suspension consequences, not just a ToS clause on paper.** The client should not build a department on Gemini subscription auth; if he wants a Google-model department, it would need to be plain `GEMINI_API_KEY` billing (contradicting his "no API-only billing" preference for that one backend specifically) or omitted.

## Recommendation

**No single surveyed orchestrator satisfies all of the client's stated requirements simultaneously** — org-chart/department modeling, typed inter-agent requests, markdown-git shared state, Telegram approvals, MCP-server action, legitimate subscription billing across Claude/ChatGPT/Grok, and container-level credential isolation, all at once, with low solo-operator maintenance burden. Each candidate is strong on a different subset:

- **Paperclip** is the only project purpose-built for the "org chart of department agents with budgets and approvals" mental model the client wants, and it is the *best-evidenced* project for running Claude and ChatGPT departments on real subscription billing via genuine CLI subprocesses (`claude_local`/`codex_local`) rather than API-key billing — directly satisfying "no API-only billing" for two of his three backends. Its weaknesses are real: it is six months old with a single pseudonymous maintainer (a different kind of lock-in/continuity risk than the vendor lock-in he's avoiding), it is Postgres/Node-heavy for a CX22, it has no native markdown-git state model (would have to be bolted on as a sync step), and community reports of coordination overhead with many agents are a genuine warning for an 8-department deployment specifically.
- **OpenClaw** is the best native match for markdown-git memory and multi-channel/Telegram messaging, and uniquely supports Grok as a backend option — but its security track record (a CVSS-8.8 one-click RCE, 30,000+ exposed instances, an 800+-skill supply-chain poisoning campaign, and three policy reversals on Claude subscription access in six months) makes it a poor default choice for a box holding live Amazon marketplace credentials, unless run with the skill marketplace entirely disabled and network exposure locked down — effectively discarding most of what makes it distinctive.
- **Hermes Agent** sits in between: native MCP, native cron, native multi-channel messaging, a much smaller and self-generated (not marketplace-pulled) skill surface, and an actively-being-built Claude-CLI-subprocess billing path that uses the same legitimate technique as Paperclip's — but it lacks any org-chart/department abstraction and its Claude-subscription support is not yet shipped/stable (open issues, not merged features, as of this research).
- **n8n** is the strongest *general automation platform* fit: mature, low-maintenance, single-container, with the best turnkey Telegram-approval UX and native MCP client node of anything surveyed — but it has zero concept of "departments" or agent-to-agent typed requests; the client would be building that modeling himself in workflow JSON, and its AI Agent node defaults to API-key billing (subscription billing would require the same community CLI-subprocess node pattern used elsewhere).
- **NanoClaw** has the best security architecture (container-per-context) of anything surveyed but structurally cannot do subscription billing (built on the raw Agent SDK, which is exactly what Anthropic's policy restricts for OAuth reuse), forcing API-key billing — a direct conflict with the stated no-API-only-billing preference.

**Given all of this, the pragmatic recommendation is not to adopt any one of these as the top-level orchestrator wholesale, but to build a minimal custom orchestrator that borrows the single proven idea common to Paperclip and Hermes — CLI-subprocess subscription billing — and pairs it with the client's already-working Supabase/Telegram approval spine, rather than replacing that spine with a less mature or less secure system.** Concretely, a minimal custom orchestrator needs only:

1. **A department-agent runner** — essentially what `agents/base.py` already is, generalized to 8 departments, where `analyze()` shells out to `claude -p` (reading the operator's own `CLAUDE_CODE_OAUTH_TOKEN`), `codex exec` (inheriting the host ChatGPT login), or `grok -p --output-format streaming-json`, chosen per department, with `--dangerously-skip-permissions`/equivalent flags for headless operation and JSON-only output instructions matching the existing prompt conventions. Gemini should be excluded from subscription billing entirely given Google's enforcement history, or used only with metered API billing if a Gemini-backed department is wanted.
2. **A shared markdown-git state layer** — a simple convention (one directory per department in a repo, committed after each run, e.g. `state/finance/2026-09-03.md`) with a small Python helper (`git add && git commit && git push`) called at the end of each agent's run; this is a few dozen lines, not a framework, and is exactly OpenClaw's model minus OpenClaw's attack surface.
3. **Typed inter-agent requests** — a lightweight JSON-schema convention (a `requests/` directory or a small `inter_agent_requests` Supabase table, mirroring the existing `approval_requests` pattern) rather than adopting Paperclip's issue-ticket model wholesale; this keeps the single-source-of-truth principle the client's own architecture already commits to (Supabase, not a second orchestration database).
4. **Approvals and Telegram** — keep the client's existing Telegram bot and `approval_requests`/Executor pattern exactly as built; it already does everything HumanLayer or n8n's approval node would add, and changing it introduces migration risk for no new capability.
5. **MCP for action** — each department's CLI subprocess gets its own `mcpServers` config (Claude Code and Codex CLI both support this natively) scoped to only the MCP servers that department needs (Finance gets read-only financial-data MCP servers; Advertising gets the PPC/ads MCP server; none get direct SP-API write access, preserving the existing Executor-only-writes invariant) — this is the credential-isolation boundary that none of the ready-made orchestrators provide out of the box for this exact shape of deployment.
6. **Scheduling** — plain cron/systemd timers, exactly as already deployed; none of the surveyed heartbeat/scheduler systems offer a decisive advantage over what's already running.

This keeps the system in the spirit of the existing CLAUDE.md's own principles — "solo operator first," "simplicity over cleverness," "one source of truth" — while adopting the one genuinely new, well-evidenced technique from this survey (CLI-subprocess subscription billing) that the existing architecture does not yet use. If the client later wants the org-chart/budget/approval visualization Paperclip provides, the lowest-risk path is to run Paperclip in parallel as a *read-only dashboard/control-plane view* over the same Supabase state (via its MCP server) rather than making it the execution engine — capturing its UI value without inheriting its youth, its Postgres footprint, or its adapter-plugin supply chain as a new source of truth.
