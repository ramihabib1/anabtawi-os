## 3. The MCP server (VERIFIED from https://github.com/Deltologic/datadoe-mcp unless noted)

**Hosting/auth:** Hosted only — endpoint `https://mcp.datadoe.com/mcp/v1`, transport HTTP Streamable, auth is a static API key in header `datadoe-mcp-key` (created at app.datadoe.com/integrations/mcp). No OAuth-to-client; DataDoe owns SP-API developer registration, Amazon OAuth, refresh tokens and rate-limit handling. Not self-hostable; not open source (the GitHub repo is docs only).

**Client setup (VERIFIED):**
- Claude Code: `claude mcp add datadoe --transport http --url https://mcp.datadoe.com/mcp/v1 --header "datadoe-mcp-key: <KEY>"`
- Claude Desktop / claude.ai: `mcpServers.datadoe = { url, headers: { "datadoe-mcp-key": ... } }`
- Also documented: Cursor, VS Code/Copilot, Codex CLI, Gemini CLI, ChatGPT, n8n, NanoClaw, CrewAI, OpenAI Agents SDK, Claude Agent SDK, OpenClaw, Gumloop, Hermes, Excel/Word/PowerPoint + Claude (guides at datadoe.com/hub/docs).

## 7. Limitations, complaints, gaps

- **No independent user reviews found.** No Reddit threads, G2 reviews, Trustpilot, or Product Hunt discussion with third-party (non-DataDoe, non-Deltologic) commentary turned up in search. The only "head-to-head" comparisons found (vs. AgentCentral, vs. Amazon's native MCP) are published by Deltologic/DataDoe itself — self-serving by construction, and the specific numbers in them (e.g., ad-data retention windows) could not be cross-verified independently. Treat competitive claims skeptically. UNKNOWN/REPORTED-only.
- **Company is young and small.** Product appears to have shipped as a chat copilot in 2025 and pivoted to an MCP/data-layer positioning in 2026; no evidence of headcount, customer count, or funding beyond "Deltologic ~30 engineers." UNKNOWN.
- **Vendor lock-in / no self-hosting.** The MCP server is hosted-only; the public GitHub repo is an explicit no-op schema stub (see Section 4 caveat) — there is no way to run DataDoe's actual data pipeline yourself or audit its query/caching logic. All data flows through DataDoe's infrastructure and their BigQuery-sync arrangement, not a customer-controlled pipeline. VERIFIED (repo) + REPORTED (architecture).
- **Ad-data retention windows** (if the 95-day SP / 60-day SB-SD figures are accurate) would meaningfully limit long-horizon PPC trend analysis compared to a system that stores its own history in Supabase indefinitely (as this project's `ppc_campaign_stats_daily` does). REPORTED, single source.
- **Write-action safety depends on user configuration.** Actions are disabled by default and must be explicitly enabled per type — a reasonable safe default — but once enabled, the approval loop lives inside DataDoe's action model (`dryRun` + `actions_start`), not in this project's own `approval_requests` table / Telegram flow. Any DataDoe-driven write (price change, PPC bid, listing edit) would bypass the Habib OS approval invariant (Section 13.1 of this project's architecture) unless Habib OS is the only thing ever calling `actions_start`, and even then the audit trail lives in DataDoe, not in this project's `audit_log`. This is an architectural friction point, not a documented "complaint," but it is a real gap for this specific client. Inference from VERIFIED tool behavior.
- **Pricing transparency:** flat $97/mo is unusually simple and cheap versus AgentCentral's usage tiers ($39-$199+), which is attractive, but the 2,000-token write-action allowance and 10M-row read cap are hard limits without clearly published overage pricing. REPORTED, UNKNOWN details.
- **Marketplace claims are inconsistent across DataDoe's own pages** (23 vs. 21 marketplaces on different pages) — a small but real documentation-quality flag. REPORTED (self-contradiction observed across https://www.datadoe.com/pricing and https://www.datadoe.com/enterprise).
- **AMC (Amazon Marketing Cloud) support is unclear** — mentioned once in a blog post as available for "advanced brands" via custom queries, not listed as a standard table/tool in the README. Likely a bespoke/enterprise add-on rather than a self-serve MCP capability. UNKNOWN.
- **Walmart/Shopify/TikTok Shop coverage is unverified for MCP access specifically** — those integrations are referenced on marketing pages but the README (the actual MCP tool/data contract) is Amazon-only. If true, they likely surface only in the BI/dashboard/BigQuery layer, not as MCP-queryable entities today. REPORTED/UNKNOWN split as already flagged in Section 2.

## Recommendation for an AI-run Amazon company: what DataDoe should own, and what it cannot do so must come from elsewhere

**What DataDoe is well-suited to own:**
1. **Amazon Vendor Central data access.** This is DataDoe's clearest differentiator — Vendor Central's Retail Analytics/EDI surface is notoriously painful to integrate directly, and none of the alternatives surveyed (open-source or hosted) claim Vendor Central coverage. If/when Habib Distribution adds a Vendor Central relationship, DataDoe (or building this in-house) is the realistic option.
2. **Ad-hoc, exploratory Claude Code/Claude Desktop querying for a human operator** ("show me units at risk of stockout," "pull returns for SKU X") — a genuinely useful complement to the scheduled agents this project already runs, especially for Rami's father/brother who won't write SQL or read the dashboard.
3. **Cross-account/agency-style aggregation** if Habib Distribution ever manages a second brand or client account — multi-tenant `sellers_and_vendors_list` is built for that, and this project's own architecture explicitly defers "Managed Agents / per-tenant isolation" (Section 16.1) until that point.
4. **DSP and raw Ads Marketing Stream data**, which the current architecture doesn't sync at all today.

**What DataDoe cannot (or should not) do for this project — must stay in Habib Distribution OS itself:**
1. **The approval invariant.** Section 13 of this project's own architecture is a hard requirement: no financial action without explicit human approval, enforced at agent/executor/Telegram levels using `approval_requests`. DataDoe's `actions_start`/`dryRun` model is a *different* approval mechanism living in a third-party system with its own audit log — wiring DataDoe writes into Habib OS's approval flow would mean either (a) never calling `actions_start` directly and only using DataDoe for reads, funneling any resulting recommendation through the existing `approval_requests` → Executor → SP-API path, or (b) accepting a second, parallel, less-visible action/audit system. Given the project's explicit "no parallel systems that drift" principle (Executive Summary), **DataDoe should be read-only in this architecture**, full stop.
2. **The knowledge/memory layer.** DataDoe has no Mem0-equivalent concept of atomic-fact extraction, deduplication, confidence scoring, or promotion from observation → pattern → playbook. It is a data-access layer, not a learning system. Mem0 + the consolidation jobs (Section 10) must remain custom-built; DataDoe at most becomes one more *data source* an agent's `fetch_data()` step could optionally call.
3. **Cost/architecture control at scale.** The existing sync layer (Section 4) already owns SP-API reads into Supabase with full historical retention (no 60/95-day ad-data ceiling as reportedly exists on DataDoe) and zero recurring third-party fee beyond infra. Replacing that sync layer with DataDoe reads would trade a sunk, already-working, fully-owned pipeline for a $97-1,164/year recurring dependency with an unverified freshness SLA, a closed-source pipeline nobody at Habib Distribution can audit or fix at 2am, and (per Section 13.2 of this project's own architecture) a violation of the principle that agents should not depend on new external services without a compelling gap they fill.
4. **PPC/pricing execution.** The Executor already owns SP-API/Ads API writes with an audit trail in `audit_log`. There's no case for letting DataDoe's Ads-write actions run in parallel to `executor/sp_api_client.py` — two systems capable of changing bids/prices is exactly the "parallel systems that drift" failure mode the architecture was written to avoid.

**Net verdict:** DataDoe is a plausible **read-only, human-driven exploration tool** bolted on for ad-hoc questions (and a real option if Vendor Central ever comes online), not a replacement for any layer of the existing Habib Distribution OS. Do not route agent `fetch_data()` calls, approval flows, or SP-API writes through it. If Vendor Central integration becomes a near-term need, weigh DataDoe's $97/mo hosted convenience against extending the project's own `sync/` layer with Vendor Central's Retail Analytics/EDI feeds directly — the latter keeps the "one source of truth is Supabase" invariant intact but costs more engineering time up front.
