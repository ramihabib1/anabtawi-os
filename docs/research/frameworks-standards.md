# Provider-Agnostic Agent Frameworks & Interoperability Standards — Research (Sept 2026)

Scope: solo technical operator building a "company of AI agents" for Amazon e-commerce
ops (finance, supply chain, advertising, catalog, pricing, customer, compliance),
using MCP servers as tools, a git repo of markdown as shared state/memory, and a
human approval gate. Must not be locked to one model vendor.

Legend: **VERIFIED** = confirmed against an official doc/repo/release note cited inline.
**REPORTED** = stated in a credible secondary source (blog, news, benchmark) not
independently cross-checked against a primary source. **UNKNOWN** = could not find
a reliable source as of research date; flagged explicitly rather than guessed.

Research date: September 3, 2026.

### Framework-level conclusions for this use case

- **Vendor-lock risk is not just "which LLM API" — it is also framework-vendor risk.** The AutoGen → Microsoft Agent Framework transition (legacy AutoGen frozen into maintenance mode, 54.5k-star project superseded by a new API in the same year) is the clearest 2026 evidence that even an OSS-labeled framework from a large vendor can be deprecated out from under a solo operator with no warning beyond a blog post. (REPORTED, sourced from Microsoft's own devblog + third-party analysis: https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-version-1-0/, https://agentmarketcap.ai/blog/2026/04/13/microsoft-autogen-maintenance-mode-agent-framework-sunset-2026)
- **LangGraph's OSS/commercial line sits inside the "server runtime," not the graph library** — the library (nodes/edges/checkpointer/`interrupt()`) is MIT and fully self-hostable for free; only `langgraph-api` (the packaged server) requires a commercial key. A solo operator can build directly on the MIT-licensed graph library with a self-managed Postgres checkpointer and skip `langgraph-api` entirely, avoiding the licensing boundary. (Needs direct verification against LangChain's license file before committing — flagged REPORTED here, sourced from a third-party blog analyzing the license: http://rvernica.github.io/2026/03/langchain-license)
- **Only Agno ships a native scheduler + HITL + multi-tenant runtime in one OSS package** (AgentOS) — a meaningfully different profile from LangGraph/CrewAI/ADK/Mastra, which all assume you bring your own cron/Temporal and your own approval UI.
- **Pydantic AI is the strongest "vendor-agnostic infrastructure" bet among the frameworks**, because durable execution is explicitly delegated to independent, swappable backends (Temporal, DBOS, Prefect) rather than a framework-proprietary engine, and the model layer, tool layer (MCP), and durability layer are three separately swappable seams.
- **Claude Agent SDK, OpenAI Agents SDK (without LiteLLM), and default Microsoft Agent Framework are all "single-vendor by default, multi-vendor by retrofit."** Of these, OpenAI Agents SDK + the official LiteLLM extension is the most credibly documented multi-vendor retrofit (an *official* LiteLLM integration page exists), whereas Claude Agent SDK is explicitly called out by multiple sources as the wrong pick for cross-vendor portability.

## 2. Model Routing Layers

### Comparison table

| Router | Self-host? | Open source | Per-department routing config | Fallbacks | Spend caps | Logging | Fronts subscription-backed CLIs? |
|---|---|---|---|---|---|---|---|

| **Cloudflare AI Gateway** | **No** — managed only | No | Manually ordered fallback array per request; universal OpenAI-compatible endpoint across 20+ providers | Retries + fallback (manual ordering, can fall back to a different model entirely) | Spend limits + analytics; Guardrails for prompt/response moderation | Analytics dashboard, exact-match response caching | No |

### Analysis

- **For a solo operator wanting one self-hosted config file that maps each of 8 departments to a specific provider/model with fallbacks, spend caps, and logging — LiteLLM proxy is the clear fit.** It is the only router in this set that is simultaneously self-hostable, fully open source at the core, supports named per-department model groups, enforces hard pre-call budget caps, and (uniquely) has a documented path to ride a Claude subscription's included usage instead of metered API billing for cost control. (VERIFIED for self-host/config/fallbacks/budgets: https://docs.litellm.ai/docs/proxy/reliability, https://www.litellm.ai/, https://wavect.io/blog/self-host-litellm-production-2026/)
- **Portkey is the second self-hostable option** and became meaningfully more attractive in March 2026 when it open-sourced its full gateway — worth a second look given LiteLLM's Elastic-license enterprise features vs. Portkey's now-Apache-2.0 stance, though Portkey's April 2026 acquisition by Palo Alto Networks (REPORTED) introduces its own vendor-continuity question for a solo operator who cares about the *router* not being orphaned either.
- **OpenRouter, Vercel AI Gateway, and Cloudflare AI Gateway are all hosted-only** — useful as a quick multi-model front door but they reintroduce a *routing-layer* vendor dependency even while solving the *model* vendor dependency, which cuts against the "not locked to one vendor" goal at the infrastructure level. They are reasonable as a fallback/burst layer behind a self-hosted LiteLLM instance, not as the primary router for a system meant to survive vendor churn.
- **Subscription-backed CLIs (e.g., Claude Max) as a cost lever:** LiteLLM's OAuth-forwarding pattern is real and documented, but Anthropic's April 2026 restriction on third-party harnesses using Max subscription limits (REPORTED, not independently verified against Anthropic's current terms) means this should be treated as **fragile and subject to unilateral vendor policy change** — exactly the lock-in risk the operator is trying to avoid. Recommendation: budget for metered API pricing per department as the durable baseline; treat subscription-forwarding as an opportunistic, revocable cost optimization, not infrastructure to depend on.

### What to standardize a department on, for portability

1. **Tools → MCP.** Every department's tools (Amazon SP-API wrappers, internal DB queries, etc.) should be exposed as MCP servers, not as framework-specific tool objects. This is already the plan in this repo's architecture and is the single highest-leverage portability decision — virtually every framework and every major agent product in 2026 speaks MCP.
2. **Cross-agent handoffs → A2A, if/when department agents need to call each other directly** rather than only via the shared git-markdown state. Given the CLAUDE.md design explicitly avoids agent-to-agent communication in favor of shared state, A2A is not urgent today, but keeping department agent interfaces "A2A-shaped" (a well-defined task-request/response schema) costs little and preserves the option.
3. **Reusable procedures/playbooks → Agent Skills (SKILL.md).** This is a strong fit for the "playbooks" tier in the existing Mem0 knowledge design — a validated playbook (e.g., "Ramadan Stocking Protocol") expressed as a SKILL.md is portable across *any* SKILL.md-reading agent (Claude Code, Codex, Gemini CLI, Cursor, etc.), unlike a Mem0 memory record which is tied to Mem0 + whatever queries it.
4. **Project/department-level agent instructions → AGENTS.md**, in addition to (or instead of, if simplifying) a Claude-specific CLAUDE.md — this is the direct fix for "does not survive a change of model vendor" at the instruction layer, since virtually every 2026 coding/ops agent reads AGENTS.md natively.
5. **Traces/cost/observability → OpenTelemetry GenAI conventions for the stable parts (model calls) today**, while treating agent-level span attributes as subject to change; do not build critical alerting logic on attribute names that are still pre-1.0.

### Recommendation for a solo operator wanting human-readable, vendor-independent memory

Given the existing architecture already treats "a git repo of markdown as shared state and memory" as the design center, the evidence here supports **keeping markdown-in-git as the ground truth**, and treating any vector/graph memory system (Mem0, per current CLAUDE.md; or Cognee if graph reasoning is later needed) as a **derived index over that ground truth**, not the other way around:

- Plain markdown in git has zero vendor lock-in, is diffable/auditable/human-editable, and any current or future LLM can read it directly from a checkout — this satisfies "human-readable, vendor-independent" better than any product in this table.
- Where semantic recall over a growing corpus is genuinely needed (which markdown+grep can't do well past a certain size), Mem0 self-hosted over Supabase pgvector (already the current design) is a reasonable *retrieval accelerator*, provided its output is always compiled back into markdown (the existing `wiki_compiler.py` pattern) so the human-readable artifact remains authoritative and the vector store can be rebuilt/replaced without losing knowledge.
- Zep should be avoided specifically because it is now hosted-only — a disqualifying trait for this operator's stated constraint, independent of its (reported) benchmark edge on temporal reasoning.
- The Anthropic memory tool and Claude Code's auto-memory are worth studying as *design patterns* (a model actively curating a directory of memory files) but should not be adopted as the literal mechanism, since both are Claude-specific surfaces — the equivalent pattern (an agent with a "write to your memory files" tool) can be built provider-agnostically as an MCP tool that writes markdown into the git repo.

## 7. Multi-Agent Communication Patterns: Messaging vs. Shared State/Blackboard

### What Anthropic's own engineering posts say

- **"Building Effective Agents"** (Anthropic engineering blog) lays out five workflow patterns — Prompt Chaining, Routing, Parallelization, Orchestrator-Workers, Evaluator/Optimizer — and its central philosophy claim, repeatedly echoed by practitioners, is that **"the most successful implementations weren't using complex frameworks or specialized libraries. Instead, they were building with simple, composable patterns."** — VERIFIED: https://www.anthropic.com/engineering/building-effective-agents
- **"How we built our multi-agent research system"** describes Claude Research as an **orchestrator-worker** system: a lead agent plans, spins up 3-5 specialized subagents in parallel, and synthesizes with a separate citation pass. Key production lessons: multi-agent systems only win when the task decomposes into **independent, parallelizable** subtasks; a 90.2% improvement over single-agent was measured on Anthropic's internal research eval, but at **~15x the token cost** of a single chat interaction, with token usage alone explaining ~80% of performance variance. Early production iterations suffered from agents spawning excessive subagents and conducting redundant searches — coordination is genuinely hard and prompts needed concrete rules (1 agent for simple fact-finding, 2-4 for comparisons, 10+ for complex research) — VERIFIED: https://www.anthropic.com/research/multiagent-systems (referenced via multiple summarizing sources)
- **"When to use multi-agent systems (and when not to)"** and its companion **"Multi-agent coordination patterns: Five approaches and when to use them"** (Claude/Anthropic blog) make the messaging-vs-shared-state distinction explicit and directly relevant to this project's design:
  - Multi-agent beats single-agent specifically when: **context pollution** would degrade a single agent's performance, tasks can genuinely **run in parallel**, or **specialization** improves tool selection/focus. Outside these three situations, "coordination costs typically exceed the benefits" — VERIFIED: https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them
  - **Message-based coordination**: agents send messages, wait for responses, synchronize through explicit communication — the default assumption in most multi-agent frameworks (LangGraph handoffs, AutoGen GroupChat, CrewAI Flows-with-explicit-steps).
  - **Shared-state coordination**: "removes the intermediary by letting agents coordinate through a persistent store that all can read and write directly. Choose shared state when agents' work is collaborative and findings should flow between them in real time." Notably, **Claude Code's own "Agent Teams" feature uses exactly this model** — agents read/write a shared file on disk, and "the file itself becomes the communication layer, which is more robust than direct messaging for coding tasks" — VERIFIED (quoted directly from the Anthropic/Claude blog per search summary): https://claude.com/blog/multi-agent-coordination-patterns

### What the academic/research literature says about blackboard systems specifically

Blackboard architectures — a shared, structured workspace where agents post partial results/hypotheses and other agents "volunteer" to act on what they observe, with no central coordinator needing to know every agent's capabilities in advance — are an active 2026 research area for LLM multi-agent systems, including applications to software-engineering agent teams and data-science/data-lake exploration (Google Research). REPORTED/academic sourcing: arXiv 2510.01285 ("LLM-based Multi-Agent Blackboard System"), arXiv 2507.01701, Google Research's "Blackboard Multi-Agent Systems for Information Discovery in Data Science." This confirms blackboard-style coordination is a recognized, actively-studied pattern, not an idiosyncratic invention — but note these are largely research papers/preprints, not production case studies at the scale of Anthropic's own posts, so treat the *research* citations as REPORTED rather than as strong production evidence.

### What LangGraph/CrewAI/AutoGen docs say about supervisor vs. swarm/handoff vs. shared state

- **LangGraph supervisor pattern**: a central orchestrator node receives inputs, delegates to sub-agents, collates responses — simpler to reason about and debug, but every handoff adds a "translation" round-trip, compounding latency.
- **LangGraph swarm pattern** (`langgraph-swarm`): eliminates the central supervisor; agents hand off directly to each other via `Command(goto=..., graph=Command.PARENT)`, while still **sharing state** across the handoff. One case study reported ~40% end-to-end latency reduction and fewer LLM calls switching supervisor→swarm. LangGraph's own guidance: **start with supervisor** (simpler, more accurate routing) and **graduate to swarm** only once data shows latency is the bottleneck and misrouting is rare — REPORTED: https://focused.io/lab/multi-agent-orchestration-in-langgraph-supervisor-vs-swarm-tradeoffs-and-architecture
- CrewAI's model (Crews = role-based, largely sequential/hierarchical process patterns; Flows = explicit event-driven state machine) is architecturally a hybrid: Crews resemble message-passing role delegation, Flows resemble shared, explicit process state with defined transitions — closer to a lightweight blackboard for the *steps* of a single defined pipeline, though not a general free-form blackboard.
- Legacy AutoGen's **GroupChat** is the canonical message-passing multi-agent pattern in this survey — a shared conversation transcript that every agent reads and appends to, functionally a very simple form of shared state (the transcript *is* the blackboard) even though the framework is usually described as "conversational"/message-based.

### Confirming or challenging the "shared-filesystem/blackboard + typed request files + coordinator meeting" design

The evidence assembled here **confirms rather than challenges** the CLAUDE.md architecture's core choice ("No agent-to-agent communication. Each agent is independent; they share state via Supabase only.") and the broader idea of a git-markdown blackboard plus an inbox of typed request files plus a periodic coordinator "meeting":

1. **It matches Anthropic's own stated criterion for shared state**: the department agents' "work is collaborative and findings should flow between them" over time (inventory informs pricing, competitor intel informs PPC, etc.) — exactly the case Anthropic's blog says shared state fits, and Claude Code's own flagship multi-agent feature (Agent Teams) uses this same shared-file model in production.
2. **It sidesteps the failure mode Anthropic explicitly reported** in the research-system post — excessive inter-agent messaging, redundant work, and coordination overhead — by having each department agent read/write independently against one persistent store instead of negotiating in real time.
3. **It is consistent with the "start simple, graduate only under evidence" guidance** every framework surveyed converges on (LangGraph: start supervisor, not swarm; Anthropic: multi-agent only when parallelism/specialization/context-pollution justify it). Eight sequential, mostly-independent department agents running once or a few times a day is a batch-analysis workload, not a real-time collaborative task — the domain where Anthropic's own post says coordination costs (of any kind, message or otherwise) usually exceed benefits **unless kept minimal**, which a blackboard-plus-inbox design does.
4. **One gap worth naming**: none of the production sources found (Anthropic's Claude Research, Claude Code Agent Teams) describe a distinct **"typed request files" inbox pattern** or a **synchronous "coordinator meeting"** step as a named, citable pattern — those two elements are closer to the academic blackboard literature's "agents post requests, others volunteer" model than to anything in Anthropic's own production write-ups, which use *pure* shared state without a formal inbox/request-file layer. This isn't a contradiction, but it means the "typed request file" and "coordinator meeting" refinements should be understood as **this operator's own extension** of the blackboard pattern (a reasonable and well-precedented one, given the academic blackboard model explicitly supports posted requests) rather than something directly validated by Anthropic's production case studies. Recommend treating the periodic "coordinator meeting" as a **read-only synthesis pass over the blackboard** (much like Anthropic's weekly/monthly consolidation jobs already in this repo's design) rather than a live multi-agent negotiation — that keeps it aligned with the low-coordination-cost lesson from Anthropic's own multi-agent post.

## Recommendation: The Thinnest Vendor-Agnostic Stack for 8 Departments

**Framework: none (or, if a library is wanted purely for developer convenience, Pydantic AI as a thin per-agent harness — never LangGraph's `langgraph-api`, never Claude Agent SDK as the backbone).** The evidence across §1 and §7 converges on the same point already embedded in this project's own architecture: for scheduled, mostly-independent batch analysis (not real-time collaborative reasoning), a full orchestration framework buys little and costs a real maintenance/lock-in tax. A department agent is: (a) a scheduled Python (or any language) process, (b) that calls an LLM through a router, not a framework SDK, (c) using MCP servers as tools, (d) reading/writing markdown files in the git blackboard. If per-agent structure is wanted, Pydantic AI is the safest pick — MIT license, genuinely multi-provider, built-in MCP client, and its durable-execution story is explicitly delegated to independent, swappable backends (Temporal/DBOS/Prefect) rather than a proprietary engine, so adopting it does not re-introduce framework lock-in.

**Router: LiteLLM proxy, self-hosted.** The only option that is simultaneously self-hostable, OSS at the core, supports named per-department model groups pointed at different providers, enforces hard pre-call budget caps, logs fallback vs. direct-served requests, and exports to any OTel-compatible backend. One YAML file (`litellm-config.yaml`) becomes the single place "Department X uses Claude Sonnet, Department Y uses GPT-5, Department Z uses a local Llama" is decided — changing a department's model vendor is a one-line config edit, not a code change.

**Standards to write departments to:**
- **MCP** for every tool a department agent touches (SP-API wrapper, DB query, filesystem, whatever) — this is the standard with, by far, the deepest and most durable cross-vendor adoption confirmed in this research (every framework surveyed has an MCP client; the spec itself has now been through multiple hardened revisions with OAuth 2.1 + CIMD).
- **AGENTS.md** at the root of the git repo (in addition to, or eventually instead of, a Claude-specific CLAUDE.md) — the single cheapest hedge against "this doesn't survive a change of model vendor," since it's read natively by essentially every 2026 coding/ops agent.
- **Agent Skills (SKILL.md)** for validated, reusable procedures (the "playbook" tier of the knowledge system) — portable across any SKILL.md-reading client, unlike a memory-store-specific record.
- **A2A-shaped interfaces** (well-defined request/response schemas) for the rare cases where department agents must hand off directly, even while the default remains shared state — keeps the door open without adopting A2A's machinery on day one.
- **OpenTelemetry GenAI conventions** for model-call spans now (stable); treat agent-level span attributes as provisional.

**Memory: git-committed markdown as ground truth, everywhere.** Every department's observations, patterns, and playbooks are markdown files in the repo, human-readable and diffable by construction. Layer a self-hosted vector index (Mem0-over-Postgres, as already planned, or a simpler local embedding index) purely as a *retrieval accelerator* over that markdown corpus, always compiling its output back into markdown so the vector store is disposable/rebuildable and never the sole copy of any fact. Avoid Zep (hosted-only) and avoid depending directly on Anthropic's memory tool or Claude Code's auto-memory as mechanisms — both are Claude-specific surfaces; borrow the *pattern* (a tool that writes memory files) and implement it as a plain MCP tool any model can call.

**Scheduler: cron/systemd timers for the daily batch triggers (as already built), plus DBOS as a lightweight, Postgres-native durable-execution library for any specific workflow that must checkpoint/retry across a crash** (e.g., a multi-step SP-API write sequence in the Executor). This adds zero new servers to operate and reuses the existing Supabase Postgres. Avoid Temporal self-host (reported ~0.4 FTE ops tax — disqualifying for a solo operator) and treat Inngest's self-host claims as unverified pending a direct check of current docs.

**Observability: Langfuse, self-hosted (MIT core), instrumented via OpenLLMetry/OTel so the instrumentation itself is backend-swappable.** Covers run history, cost per department (via per-department LiteLLM virtual keys correlated in traces), and traces on failure, in one Docker container next to the existing Hetzner services.

**Bottom line on "how departments survive a change of model vendor":** write every department's *logic* as (1) markdown instructions in `AGENTS.md`/department-specific markdown files, not framework-specific system-prompt objects; (2) tool access exclusively through MCP servers, never a framework's native tool-calling API; (3) LLM calls routed through the self-hosted LiteLLM config, never a hardcoded `Anthropic()`/`OpenAI()` client instantiated inside agent code; and (4) all durable knowledge as markdown in git, with any vector/graph store treated as a cache. Under that discipline, replacing Claude with GPT, Grok, or a local model for any one department is a router config change and a markdown prompt edit — not a rewrite.
